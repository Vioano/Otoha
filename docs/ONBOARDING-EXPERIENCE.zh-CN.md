# 五分钟团队接入体验

2026-11-07。本文记录用户在当前 Codex 会话中直接说明的长期产品要求，并区分实施建议和未定问题；不是已发布能力或验收结果。

## 用户明确的目标

任何团队的组织者只需把 Otoha 的 GitHub 链接交给自己常用的 Agent，说明想用它开展团队协作。Agent 自行发现、下载和操作 CLI，根据 CLI 的实际反馈，主动询问缺失条件、配置团队并验证可用。CLI 同时可由人直接操作，主要面向 Agent 操作。

用户不需要预先知道应该提供哪些信息。用户原话：“他们甚至都不需要知道该给agent讲什么”；“是agent自己使用了CLI之后，根据CLI给的反馈，一步步主动给团队的人员提问”。

人回答自己知道的现实情况：有多少成员、几台电脑、有哪些现成设备和账号、谁管理团队、哪些机器可以常开、资料希望留在哪里。服务器、数据库、网络穿透和传输配置的技术组合由产品与 Agent 处理，不把这些术语变成用户必须学习或作答的选项。费用、资料归属、设备占用和成员权限仍是需要人表达的实际选择。

**普通、不复杂的团队，完整流程目标为五分钟以内，包含及时响应的队友接入。** 计时包括了解条件、下载、网络、通信、传输、数据库及其他默认必要能力的初始化与基本可用检查。不是每一步各五分钟，也不是只计算邀请码兑换的时间。用户希望通常像和一个人聊天，问清几项情况后，两三分钟到五分钟完成。

默认提供一套好用的配置。复杂团队，或队长主动要求深入讨论时，可以延长对齐时间；不能因为配置失败或超时，事后把普通团队改称复杂团队。

兼容不同厂商、不同能力的 Agent，不以强模型或熟悉源码的作者会话为前提。用户明确提出用较弱模型盲测，也要达到五分钟全套可用的目标，并举豆包类 Agent 为兼容对象。宿主能否调用工具与模型理解、执行指引的能力分别验证；不能用提示词宣称补出了宿主没有的执行能力。

## 实施建议：CLI 持续提供可执行反馈

这不是只增加一页安装说明或固定问卷。CLI 应保存初始化进度，检查能够直接获得的条件，并在各阶段返回：已经确认什么、缺少哪些信息、下一步能做什么、需要人决定什么、实际验证结果和中断后的继续入口。Agent 把这些反馈转成自然提问，回答“不知道”时也能继续检查或换一种易懂的问法。

可用如下对话检验措辞，而不固定所有团队的提问顺序：

> 用户：我们四个人，想一起开发一个项目。
>
> Agent：你们有哪些电脑？有没有一台可以一直开着？
>
> 用户：都有电脑，没有服务器，也不能保证一直开机。
>
> Agent：队长关机后，其他人还需要继续工作吗？资料是否可以放在托管设备上？

Agent 应根据答案和检查结果给出适合的默认方案，之后询问成员与权限、生成个人接入材料，并指导各成员的 Agent 完成加入。新建团队与加入已有团队是两条必要入口；没有邀请不能一律要求先找邀请。

人用的终端交互与 Agent 使用的结构化反馈应基于同一进度、权限和实际检查结果。具体命令、字段、问答形式和默认策略仍待设计，不把本文写成已发布 CLI 协议。

软件负责确定性的安装、配置、检查和恢复，减少模型临时研究技术方案和自行拼接命令。可并行的准备与成员接入应并行；重复执行沿用已有身份和进度。错误应给出具体、有限的下一步，不把整份底层日志交给弱模型自行推断。

## 网络可达属于接入体验

用户随后明确：“内网穿透需要内置在其中，作为一个功能”。**内网穿透作为 Otoha 内置功能，是用户已定要求；网络可达的检测、配置、连接验证和必要的恢复引导纳入接入体验。** 连接范围和设备条件由 Agent 问清，用户无需分别安装、学习和配置一个穿透产品才能开始协作。具体实现仍待验证。

优先复用成熟的直连、中继或穿透提供者，而不把自研穿透协议作为前提。固定提供商、依赖如何打包、中继由谁运营及费用由谁承担仍未决定。一个团队的手工 SSH、DNS 或证书排错经历不是交付给所有用户的默认流程。

2026-11-07 用户进一步授权首版采用 frp，将穿透和默认中继接入内置到 Otoha，完成后按本文五分钟目标做较弱模型盲测。首版采用随产品分发、由 Otoha 管理的连接引擎，先验证中继稳定闭环，再评估 P2P 优化。frp 提供 TCP、HTTP/HTTPS 等代理及 P2P 能力；其官方文档明确 XTCP 打洞受 NAT 条件影响，可靠连接可采用 STCP，并支持失败后回落。参见[官方概览](https://gofrp.org/en/docs/overview/)与[XTCP 边界](https://gofrp.org/en/docs/features/xtcp/)。首版选择不锁定永久提供者或商业运营方式，实现与盲测结果分别记录。

内置功能主要连接没有公网地址的队长电脑或私服，为获授权的队友提供 Otoha 通信、图谱 API、仓库传输及按需工作页访问。只开放已配置的 Otoha 服务，不将整个局域网或数据库管理端口作为默认共享范围。中继连通与中心可用分别判断；队长关机后继续协作，需要有另一处持续在线的中心，穿透本身不提供离线托管。

五分钟目标也约束默认架构：应评估预构建运行时、可直接使用的连接入口、自动资源检查与配置等办法，减少每队重复部署的工作。这些是候选策略，不等于已经决定托管商业服务，也不表示任何外部账号申请或资源购买都能在五分钟内完成。

## 验收方式

- **起点：** 干净、未读源码的 Agent 会话首次收到 Otoha 产品链接和协作意图。模型、宿主、工具权限、设备、现有账号及登录状态预先记录；测试作者不在旁补命令。
- **终点：** 队长和及时响应的队友都已完成接入，网络、通信、传输与数据库等默认必要能力已启动并经过实际操作检查；启用的代码仓库、图谱等能力也分别验证。不以配置文件存在、进程启动或邀请生成代替全员可用。
- **时钟：** 记录端到端实际经过的时间，包括对话、模型思考、下载、配置、检查和及时的人工响应。各阶段耗时可另列，但不能从总时间中扣除或在队员加入时重新计时。外部阻塞如实记录为本次未达标或预先明确的不支持范围。
- **样本：** 分别覆盖新团队从零建立、已有资源复用和成员加入，并使用不同宿主及较弱模型。普通团队范围在测试前定义，首次成功率、失败原因和超时均保留，不能只报告最快一例。
- **恢复：** 加入或初始化中断后从真实进度继续，保留身份、已有工作和未知结果，不重新创建团队来掩盖失败。弱模型也应能按反馈继续。
- **复杂团队：** 另记用户主动要求的深入对齐时间和原因，保持与默认五分钟场景分开；是否已经基本可用仍按实际检查判断。
