# 将人工反馈落实为工程检查

2026-11-12。用户明确要求：人工反馈和纠错如果能落实为 lint，就应落实。本文将它接入原话保存、Agent 工作流程、仓库检查与可选图谱。2026-11-15，用户进一步要求将中性观察、题包与确定性判定拆分，通用接口见[审查协议](REVIEW-PROTOCOL.zh-CN.md)；专项检查仍沿用已有工具，不新增常驻模型或规则数据库。

## 用户要求与实施原则

收到反馈后，Agent 既要修正当前结果，也要判断同类错误能否由机器可靠识别。能用项目已有 lint 表达的，应修改对应配置或规则，避免只写进聊天或文档；需要运行才能判断的，用回归测试。主观体验保留实际验收，不为了覆盖率编造一个无法验证真实要求的正则表达式。

这由已有执行 Agent 在正常工作中完成。数据库保存原文和关联，lint/测试执行确定性检查；数据库不理解自然语言，不在每条聊天到达时直接生成并执行代码。明确且在已授权范围内的纠错直接落实，不把每项技术修改变成一次审批。

## 最薄工作流程

```text
人工反馈／纠错
    ↓ 查原话和后续修订，理解当前要求与范围
项目已有 linter 配置／小型检查脚本／回归测试
    ↓ 用违规例、合规例和例外范围验证
现有检查命令与 CI
    ↓ 具体位置、规则 ID、原因与结果
Agent 修正当前工作；来源关系可供后续追溯
```

Agent 接到纠错时依次完成：

1. 通过原话库的 search/read/changes 或当前已取得的直接人类消息，核对当前意图、适用对象、条件和后续改口。自动采集入口尚未接通时，当前对话中的明确纠错也可以先落实。
2. 寻找项目已有检查器，优先调整配置。代码结构规则用相应语言的静态检查或 AST；行为约束用回归测试；仅在现有工具不合适时增加小脚本。
3. 给规则稳定 ID 和明确范围。至少用一个实际违规例证明会失败，一个合规例证明会通过；有重要例外时补例外，避免把局部纠错扩大成全项目禁令。
4. 把检查接到项目现有入口，在相关改动完成和交付前执行。报告这次检查实际覆盖什么；规则尚未实现、未运行、运行失败和通过分别说明。

典型选择：

| 人的反馈 | 合适的落实方式 |
| --- | --- |
| 某类文件不得使用指定 API／导入某个模块 | 已有 linter 的文件范围与规则，必要时增加 AST 检查 |
| 产品入口统一命名，历史版权出处保留 | 有目录范围与例外的名称 lint |
| 重启后不得丢失已经确认保存的消息 | 回归／集成测试，验证真实持久化与恢复 |
| 不要再把程序投递当成人类发言 | 已知触发场景的采集契约／集成测试；关键词 lint 不能证明消息来源 |
| 页面更清楚、操作更自然 | 具体体验与前端验收；明确的尺寸、标签或可访问性部分可另做自动检查 |

## 与原话库、图谱和通信共用

| 现有部分 | 在这条流程里的职责 |
| --- | --- |
| 人类原话库 | 留存原文，查找被纠正的问题及后续修订；可关联派生检查，不另存一份可执行规则正文 |
| 项目仓库 | 保存 linter 配置、checker、正反例及版本；检查入口使用当前项目采用的实现 |
| 工程图谱（可选） | 通过普通属性／关系连接来源、规则 ID、适用对象、实现路径／版本和检查结果，不给 Core 加业务类型 |
| 既有任务与协作流程 | Agent 在实现任务时同步补检查，将结果作为工程证据；通过不等于人的最终验收 |
| 既有消息链路 | 需要协作时发送诊断摘要和获准引用，按需读取；不把原始私聊或完整 lint 输出灌进每个会话 |

公开 Git 只保存归纳后的公共要求、代码和虚构样例。真实原话、消息 ID、私人链接与来源关联留在获准的私有存储；公开 checker 可引用公开规范。现有通信 refs 支持代码的 Git 定位，通用原话引用 resolver 仍未接通，不在这里声称已实现。

图谱关联是按需的轻量使用约定，不成为运行 lint 的前提。SQLite 无需为本轮新建规则数据库。规则的可执行版本跟随仓库，原话库和图谱关联它，避免两处各自维护一份“当前规则”。代码提交与项目接受、用户验收仍分别判断。

## 人改口时，检查也要同步改

Agent 必须一并更新或撤掉旧规则及其样例，不能只记录新原话、继续让旧 lint 拦截正确行为。例如先要求所有图片透明，后来限定封面白底，应缩小原检查范围并加入封面例外，而不是累计两条互相冲突的全局检查。

指代不清或同范围要求未能同时成立时，先找全原文；仍有歧义则明确待澄清的部分，不将猜测写成强制检查。诊断若来自过期规则，处理依据是修正规则版本和范围，不是绕过错误提示。

建议将原话采集开关与仓库中已采用的检查分别管理：关闭采集停止新增原话，不自动删除已有 lint；关闭整项可选功能也不应擅自改写项目仓库。规则撤销按项目已有修改流程进行。

## 已有实例：产品名称检查

稳定规则 ID 为 `otoha/product-name`，实现为 `scripts/check-names.py`。它检查活动产品源码、公开入口和文件名，同时保留 docs 历史资料、NOTICE、许可证与无关第三方名称的既有例外。本轮实跑发现对外部 Skill 标识 `system-atlas` 的误报，增加该完整标识的精确例外；同一行的产品旧名及其他复合名称仍会失败，没有豁免整个 Skill 或测试目录。

```sh
npm run check
npm run test:feedback-lint
```

`check` 复用既有 `check:names`；失败诊断给出规则 ID、文件／行号和本节规范。`test:feedback-lint` 通过已有多语言测试入口运行隔离正反例，并纳入 `npm test`。测试证明活动源码误用会失败、许可和历史出处仍通过、修正后消除错误；测试目录没有被整体豁免。

上述 npm 命令是 Otoha 源码仓库的实例。使用 Otoha CLI 的其他项目沿用各自现成的检查命令，不因此要求安装 Node.js、npm 或这套测试环境。

既有 CI 的命名步骤已改用统一 `npm run check`，其后 `npm test` 会运行这些回归样例。当前 CI 仍只通过 `workflow_dispatch` 触发；本轮没有改成每个 PR 自动运行，也未在远端触发 CI。

## 当前完成与边界

2026-11-14 补充开发方向：判断方式不限代码。按具体标准组合结构检查、语义判断与独立实看；确认的问题同样可以阻断交付，不能因为判断较软而忽略。最薄接口、真实样本校准及分阶段接入见[Skills 开发计划](SKILLS-DEVELOPMENT.zh-CN.md#按标准选择检查方法确认的问题可以阻断交付)。通用语义审查器仍未实现；已落实的两项有界检查见[内容审查的可执行检查](../skills/otoha-content-review/references/checks.md)：核 PPTX 实际图片比例，并根据提交的独立报告、逐页覆盖和当前输入版本阻断交付。它们已进入现有测试入口 `npm run test:content-review`，不代替实际看图。

本轮已落实本项目的反馈处理约定、统一检查入口、稳定诊断 ID 和名称规则的隔离回归样例。来源到规则、图谱到检查结果的自动写入，以及每个使用 Otoha 的项目如何暴露自身检查入口，仍属于后续产品接入；未增加自动生成或执行规则的后台服务。

自动采集的人类来源筛选仍有原有宿主缺口，不因本轮 lint 实例通过而改变。lint 通过只证明已编码规则在已检查范围成立，不证明全部人类需求都已被理解、覆盖或验收。
