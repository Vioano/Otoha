# Otoha 首个可用测试版：范围与发布门槛

更新：2026-11-06（Asia/Taipei）。本文件是需求审查给出的首发范围和工程门槛建议。依据为[有效需求及消息证据](REQUIREMENTS-STATE.zh-CN.md)、[通信契约](COMMUNICATION-CONTRACT.zh-CN.md)、[五项原则](PRINCIPLES.zh-CN.md)及主会话转达的最新目标；不改写已有决定。实际测试由主会话与执行代理完成，本次文档审查未使用凭据、运行真实服务或重跑测试。

## 1. 首版要证明的产品价值

用户希望 Otoha 成为团队和企业可默认采用的基础设施，降低前期环境搭建、中期反复对齐、Agent 输出格式转换、Slack/微信群人工转述和调度成本。首版先证明一条完整、低摩擦的协作路径：

**新成员快速加入 → Agent 按引用交接 → 人的修订改变后续执行依据 → 断线后恢复工作。**

这条路径是主会话提出的首版验收建议。渠道数量不单独代表价值；“消息发到了”也不自动证明交接或对齐完成。尚无效率翻倍、企业级可用、摩擦归零或大规模调度收益的证据。

用户进一步要求：队长只发 Otoha 的 GitHub/官网裸链接，成员只把链接交给自己常用 Agent，便能发现说明、安装和准备路径；不绑定一种 Agent 产品，也不靠额外长口头提示。公共产品链接提供发现入口，具体私有项目仍由已有仓库上下文或精简邀请确定。缺项目身份时应指出缺项，不能假装已加入，也不从网页文本取得额外权限。

持续对齐要自然发生，让相关信息在需要时呈现。验收关注每个人为对齐付出的注意力、会议/转述和格式转换成本；不承诺消灭对齐，也不要求人第一次就完整说明所有需求。队长能看清真实进度，成员得到与当前任务有关的更新，后续发现仍能改变共同依据。

## 2. 建议首发范围

| 部分 | 首版开放范围 | 可后置并明确标缺项 |
| --- | --- | --- |
| 分发与运行 | 实际可下载的 CLI；Mac 与 Omarchy/Linux 的已测架构；稳定安装身份、明确依赖、可诊断/启停的后台服务 | Windows、其他架构、自动升级、所有图后端的一体打包；不能把仅源码构建写成已有下载版 |
| 项目 | 裸产品链接可发现说明/安装/准备；已有项目上下文或精简邀请确定接入目标，连通仓库、消息、工作页；输出真实就绪范围和可操作 checkout/origin | 全企业项目目录、通用跨图解析；Graph 尚未接入就明确未就绪，不虚报“四类资源全部完成” |
| 权威端 | 单一中心在线主链路，可运行于服务器或队长电脑；本机待发和恢复沿用既有基础 | 多主、完整成员副本、队长离线时所有成员直接互发及最终汇总；不为首发另造复制体系 |
| 消息 | 完整原件持久保存，默认查收摘要/引用，按 ID 取原件；有界结果能继续读取 | 任意 SQL、全局全文检索、自动 Context 整理；最终命令名不作为门槛 |
| Session | 一个明确列出的真实宿主先通过；普通消息可靠主动扫描即可，紧急 steer 只对已测宿主启用 | 同时实现所有 queue/扫描方式、所有宿主唤醒、无人值守自动调度 |
| 权限 | 保留既有“管理员全库、成员公共＋本人发出/收到”的需求；首版对实际开放功能执行服务端授权 | 若逐条私发尚未通过，可明确限定项目共享频道，关闭私发入口并标未完成完整权限模型；不能把共享消息标成私信 |
| 渠道 | 中心 Client 主链路必备；本轮实际测试已授权的真实 Telegram Channel/Bridge，启用前跑通闭环，失败可明确关闭后先发中心版 | Slack/微信/Discord 适配、Git 消息 Transport 不因出现在旧设计稿就算已实现；GitHub Mailbox 只读收信可单列验证 |
| 工作与反馈 | 同项目发布和更新工作页；人反馈后能记录当前认可修订，并影响下一次 Agent 输出 | 完整图平台、Template 引擎、固定工作页布局、原生 Agent；Skill 保持可选 |

测试版可以限制支持范围；已开放路径中的误投、越权、正文丢失或普通消息打断，不能靠“实验功能”标签放行。未通过的可选路径应关闭入口，不让它混入默认主路径。旧权限/副本细则的最初原话仍有缺口，继续保留旧决定地位，不因此任意扩权。

## 3. 一条完整验收故事

使用同一个隔离测试项目、管理员 A、执行成员 B、同项目另一任务的成员 C，以及无项目权限的身份 X；至少两个真实 Agent Session。C 可读项目公共内容，但不应因此被强制灌入 B 的全部任务上下文；X 不得读取项目内容。成员和消息均为虚构数据，真实渠道只使用已获授权的测试身份。

1. **发现与加入。** 先在干净轻量会话中只给产品裸链接，不给额外自然语言提示，观察它能否找到安装/帮助和接入路径。再在已有目标项目上下文或可发现精简邀请的隔离环境里，只给同一链接，验证准备、加入、正确 checkout/origin、消息和工作页。完全未知目标项目时，正确报告缺项算发现结果，不算加入成功；不得用猜测冒充接入。作者不代写命令或补讲内部路由，遵守宿主既有授权边界。首次安装/系统授权与已安装设备的新项目加入分别统计。
2. **交接。** A 保存一条短摘要、长正文及产物/版本引用，向 B 发普通消息。B 忙时没有被打断；到任务边界查摘要，再按引用取得原件。B 的交接回复引用原消息及其采用的版本，不能只写“收到”。
3. **人的修订生效。** 例如原任务是将样本页按钮写为“加入”，人反馈改为“开始”。经对齐后把修订记录到共同项目依据，保留前一版本和来源；B 在下一次样本输出中读取新依据，实际呈现“开始”。按当前任务与路由把更新交给 B，C 无需参加完整对齐或读全部正文；C 仍可按其权限主动查公共原件。队长能看到这次修订、交接和产物来源，未知进度明确未知。旧消息仍可追溯。可复用已有消息/页面版本和引用，不要求先实现通用图数据库，也不把一条普通聊天自动当作已接受决定。
4. **恢复。** 中心离线时明确显示离线、待发或结果未知；已经接受的原件不丢。恢复并重启客户端后，待发自动收敛，B 能继续查询新依据。再测试“中心已接受但响应丢失”，核对原请求结果，只产生一次已接受效果。

普通与紧急消息还要单独对比：同一忙 Session 中，普通消息等待；有打断权限的紧急消息只送摘要/引用并实际进入当前 Session。不能用模拟页的按钮或宿主 API 返回成功替代窗口观察。

整条故事同时记录：总时长、CLI 调用数、人工动作、人工转述/格式转换次数、重试、首次成功/失败、各成员收到的通知数、与其当前任务无关的强制通知数、摘要与实际取回正文的字节量，以及各段延迟。裸链接还记录找到可用入口的耗时和读取步骤。持续对齐关注获得一条相关修订实际要花多少注意力，不用关闭反馈入口制造低打扰。有可靠模型 usage 才报告 token；消息条数不能代替上下文消耗。没有同场景基线时只报这些观察，不声称已减少某个百分比或取得普遍调度收益。

## 4. 发布阻断项与最小实测

下表是推荐的发布门槛；“通过”需要候选发行物的实际结果。实现正在变化，修复分工和测试文件存在均不能代替复验。

| 门槛 | 最小实际测试 | 阻断情况 |
| --- | --- | --- |
| G1 裸链接发现、下载与加入 | 只给产品 GitHub/官网 URL 的全新轻量会话找到可用安装/帮助；有项目上下文时完成接入，无项目时准确指出缺项。从真实下载位置取得候选物，记录版本/校验和，在声明平台做安装/帮助/加入/doctor | 需要长额外口头提示、入口写死某个宿主、仍需自行编译、成员手动拼内部服务、猜测未知项目已加入、错误仓库 URL、空状态虚报 READY、依赖缺失不说明、必须安装 Skill 才能使用 |
| G2 完整存取与摘要优先 | 保存可区分的摘要和至少一条长正文；默认 list/query 不带正文；按 ID 取回后比较原文；超过 100 条后仍能取较早原件或明确继续读取 | 原件只剩截断摘要、默认扫描全量注入正文、引用失效、缓存裁剪被当作完整历史、接受超过声明上限的数据后静默截断 |
| G3 正确的 Session 时机与内容 | 真实忙/闲 Session 分别测普通扫描或 queue、管理员紧急 steer；观察窗口内容与调用方身份；不支持宿主明确返回未支持 | 普通消息被 steer、通知携带完整正文、普通成员能直接使用管理员打断权、错误 Session 收件、宿主接受即标已读/接手 |
| G4 实际授权与非公开路由 | A/B/C/X 分别查 list/get/history/query/events 和本机缓存；C 可读公共但不得读无关私发，X 无项目访问权；在开放私发时测本人发出/收到；显式非公开消息缺路由时不得转公共渠道 | 只在网页隐藏、把 to_sessions 当 ACL、未授权跨项目读取、以 global owner 通过冒充 project admin 已满足旧权限、私发落入公共渠道 |
| G5 中心主链与正常恢复 | 两机真实发送/查原件/回执；停止仅测试中心，离线待发，恢复并重启 daemon；丢接受响应后按原请求查回 | 已确认原件重启丢失、重复接受效果、未知结果被写成功、需要重新邀请才能恢复、后台只保存却永不重投 |
| G6 真实 Telegram 闭环（启用门槛） | 已授权 Bot A→Bot B→Bridge→中心→接收方查摘要/原件；反向回复沿原链取回。校验项目/来源/目标、摘要引用和正文对应关系；在一条已测宿主链中观察实际通知 | 只有 Bot API 双向成功；Bridge 未入中心；丢掉独立信封语义；实际来源未经登记就被当授权成员；路由错投。未过必须关闭 Telegram 路径 |
| G7 Telegram 入站失败后可恢复（启用门槛） | 中心不可用时让一条虚构消息进入 Gateway；确认本机收纳但中心未接受；恢复中心，再重启 Gateway，最终只接受一次原消息 | 提前写 seen 标记导致失败消息永久跳过；本机有原文却没有待汇入状态；推进 offset 被当作应用接受。未过必须关闭 Telegram 路径 |
| G8 持续对齐改变执行且不强占全员注意力 | 跑第 3 节完整故事；保留旧版本、修订来源、B 的相关通知/读取/后续产物，队长可追踪；记录 C 无须被迫参加的部分 | 反馈只是另存文本、Agent 继续沿旧版本执行、强制全员读所有正文、要求人最初把需求想全、消息已读被直接视为采用、固定页面演示冒充真实 Agent 调整 |
| G9 常驻性能与可诊断性 | 按第 6 节测进程树、命令/消息延迟和恢复；正常无消息时安静，有故障可查原因 | 忙轮询/重复刷屏、明确持续资源增长、连接失败不退避、进程死掉却仍报告运行、关键性能完全未测 |

不能靠关闭所有实用路径绕过门槛。首版至少通过中心主链、一个真实 Session、一次人的修订及一次正常断线恢复。Telegram 的 G6/G7 是该渠道启用条件，不是新增“必须有两条渠道”的产品要求；本轮仍须尽量实测并报告真实 Bot，失败时保留结果、关闭路径，可以先发明确限定的中心版。核心主路径未达时先交内部候选包，写清未过门槛。

### 已定位、应优先回归的源码风险

以下是 2026-11-06 约 06:09 台北时间的只读观察，不是最终缺陷状态；执行代理修复后以候选物复验结论覆盖。

- `apps/cli/internal/otoha/receive.go` 的旧 eligible/deliver 路径未按 class 分流并交给宿主完整 payload；`desktop.go` 先尝试 steer。主会话已安排修复，G2/G3 仍需实测。
- `apps/cli/internal/otoha/telegram.go` 在 sink 成功前保存 SeenUpdates/SeenIDs；失败后重取同 update 会跳过。必须验 G7，不能只检查原文文件存在。
- `apps/cli/cmd/otoha/main.go` 的 Telegram Bridge 目标路由未命中后回退 `Recipients["public"]`。to_sessions 并不自行声明私信，但一旦用户选择非公开范围，该回退不能跨越范围。用 G4 检验，缺路由应明确失败或保持待投。
- 协作服务的项目/频道授权与旧需求两类角色尚有映射差距；默认共享频道测试通过不证明逐条私发模型通过。可关闭未通过的私发，不开放假私信。

## 6. 临时工程目标（建议，不是用户定值或既得结果）

已测小样本是：操作者 join 约 3 秒；固定系统授权后第二次全新 Luna 会话约 39 秒、join 约 3 秒。第一次 Luna 首轮失败，第二次还有内部 Git URL 误用，不能把两次拼成首轮成功率。一次资源快照为 Mac daemon 18.34 MiB、Linux daemon 12.85 MiB/中心 31.96 MiB，CPU 快照 0—0.1%；见上述脱敏结果。这些是建议预算的起点，不能当性能分布或长期稳定证明。

建议固定一个小团队条件：2 名成员、每人 2 个 Session、单项目、中心 RTT 记录在案、小仓库不超过 10 MiB；CLI 与必要运行时已安装，首次系统授权单列。消息延迟使用至少 50 条虚构小消息测 p50/p95/max，长正文另测；空闲资源预热 2 分钟后测 10 分钟，再做 30 分钟包含三次正常断线恢复的观察。平台真实消息与中心负载样本分开，不为凑样本刷 Bot。

| 指标 | 首轮临时目标 | 依据与统计边界 |
| --- | --- | --- |
| CLI 加入与就绪 | 在 RTT≤150 ms、小仓库条件下，5 次干净项目加入均成功，每次 CLI 段≤10 秒并逐次列出 | 约 3 秒样本留出约 3 倍余量；5 次只作冒烟，后续积累样本再报告分布。不含下载/系统授权/模型思考，端到端仍单独报 |
| 新轻量会话 | 5 次独立会话至少 4 次无需作者救场完成加入并发出首条已接受消息；各次总时长目标≤90 秒 | 39 秒试验留约 2 倍余量；这是少量发布冒烟，必须逐次列结果，不宣传为总体成功率或已达 SLA |
| 人工负担 | 已配置机器加入目标≤1 次人工导入/确认，模型 CLI 调用≤5 次；主故事人工转述/手工格式转换和对 C 的无关强制通知目标为 0 | 入口应隐藏内部接线；裸链接学习过程另测入口发现耗时/读取步骤；首次安装与系统授权动作单列，不从统计中抹掉 |
| 本机 list/get | 小团队样本 p95≤300 ms | 单次命令应可交互使用；包含进程启动，排除模型耗时，声明历史量 |
| 中心消息与页面更新 | RTT≤150 ms、正常网络下，中心接受→另一端摘要可查/页面可见分别 p95≤3 秒 | 给现有轮询与路由留余量；中心接受前网络等待另测，不把“发命令”混作接受起点 |
| Telegram 延迟 | 先报告发送→Gateway 收纳→中心接受→Session 呈现各段分布；端到端≤10 秒作为探索目标 | 当前没有足够时延基线；平台抖动与本机处理分开，不对外承诺 10 秒 SLA |
| 空闲资源 | 客户端树 RSS≤64 MiB；中心树≤128 MiB；同机合计≤192 MiB；各树空闲平均 CPU≤单逻辑核的 1% | 现有快照约 13—32 MiB，留约 3—4 倍服务余量。计入受管子进程，重叠进程不重复计；宿主 Agent/浏览器单列 |
| 稳定与恢复 | 30 分钟无异常退出；预热后首尾 10 分钟平均 RSS 增长≤10 MiB；三次恢复均成功，重新可达后待发目标≤30 秒收敛 | 对安静常驻和普通重连的短期工程检查，不证明全天/长期稳定；中心已接受的样本全部可查，无重复接受效果 |

这些数字是当前审查建议。主会话可在开测前按固定硬件、仓库和网络条件调整并记录理由，结果出来后保留原口径和失败。数值未达到时报告是功能阻断、性能退化还是外部条件；没有资源/时延结果时不宣称低资源或快速。功能正确性、访问边界和数据完整性不能为了数值目标降低。

## 7. 可后置能力怎样对外说明

- 未完成成员完整副本，就写“中心权威＋本机待发/有限缓存”；说明离线可做与不可做的动作，不称全量本地库。
- 未完成中心离线互发/管理员汇总，就写“离线先持久待发，中心恢复后续投”；不抹掉旧需求，也不为本版自行决定完整复制协议。
- 私发未过就关闭私发并限定项目共享范围；完整旧权限矩阵标未完成。当前主链仍须拒绝无关成员，不能靠“测试版”放开授权。
- 只测 Codex 就列该宿主和实际忙/闲行为；其他宿主显示未支持，不标“已投递”掩盖未接入。
- Graph 显示未接入或保留兼容实验入口；不能强制所有工作页采用 Graph，更不能把旧固定 Schema 宣称为新自由 Core。
- 不支持的渠道、系统、仓库容量和消息长度明确列出。开放哪条路径，就报告该路径真实测试范围。

## 8. 发布记录与判断

用户已明确发布顺序：**先在私人服务器实际测试，并更新私人 Git 仓库；按本文件门槛与真实证据确认第一版可用后，再更新 GitHub。当前不提前更新 GitHub。** 私有测试只使用已授权的测试范围，原始消息、凭据和运行状态继续留在私有位置。

预发布时可在私人服务器提供同版候选说明页、安装入口和发行物，用单个候选链接测试自主发现与下载；记录它是预发布入口，不把它冒充已经更新的 GitHub/官网。G1 不以先改 GitHub 为前提。正式公开后再核对官方裸链接、版本、下载与校验和是否一致，沿用已测候选物；公开入口的冒烟与发布前真实行为验收分别记录。

主会话给候选版写一页可核对结果：候选版本/下载校验和、平台与进程范围、G1—G9 的通过/失败/关闭状态、原始记录的私有位置、必要脱敏证据、性能逐次结果、剩余缺项。记录真实命令和观察时间；模拟、源码检查、Fake 测试、真实中心、真实 Bot、真实宿主和用户体验分别标明。

## 9. 首发取舍不能破坏的核心机制

1. **共同依据可回到原件。** 摘要、消息引用、产物和当前采用的修订相互可追溯；原件和旧版本保留，收到消息不自动变成共同决定。
2. **注意力按时机使用。** 普通消息等待，紧急消息按权限进入已支持宿主；通知保持精简，接收方按需读正文。
3. **自由受到真实边界保护。** 身份、项目和访问范围由软件执行，消息不产生新授权；不为图谱或调度预设唯一工作流。
4. **人的反馈改变后续依据。** 保留可操作实例、主动对齐及一次真实修订影响执行的闭环；测试通过不代替用户对体验的判断。
5. **复杂性由基础设施承担。** 精简接入、统一项目、可恢复待发与可解释状态，减少人工转述、接线和格式转换。首版范围小，也应跑通一条完整协作路径。
