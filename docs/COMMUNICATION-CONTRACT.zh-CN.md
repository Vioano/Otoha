# Otoha 通信契约：存取、通知与 Session 边界

更新：2026-11-06（Asia/Taipei）。这是供需求实例审阅的目标契约，不是已发布的 API，也不是实现或用户验收声明。需求演化、消息出处与覆盖缺口统一见 [REQUIREMENTS-STATE](REQUIREMENTS-STATE.zh-CN.md)。

## 1. 已确认的核心与证据边界

Otoha 要降低跨用户、跨设备、跨窗口的通信摩擦，让 Agent 保持独立执行，同时能按需取得保存完整的原件。通信由软件承担；不要求 Agent 手写复杂协议、操作聊天软件界面或手工拼接仓库、消息、图谱和工作页。

本轮直接确认了以下要求：

- 消息完整保存，通知与正文分离；摘要和引用帮助接收方决定是否读取原件。
- 紧急消息使用宿主支持的 `steer`；非紧急消息使用 `queue`，或由接收方在适合的任务边界主动扫描消息库。
- 消息必须能实际到达目标 Session；软件收纳、宿主接受和 Agent 阅读分别报告。
- 仓库、消息、图谱和工作页属于同一个 Otoha 项目管理；项目身份与权限不能留给人或 Agent 临时拼接。
- 开发先在明确标注的模拟网站中跑通具体流程，吸收反馈后再决定真实实现。

管理员可见范围、本机副本与权威库的准确关系，旧 [DECISIONS](DECISIONS.zh-CN.md) 有记录，但本轮未取得最初用户原话。它们在第 5、6 节作为**既有记录待补证**保留；不是本轮新确认，也没有被判定为已否定。先模拟这些差异，不据旧记录直接扩展真实权限或复制机制。

## 2. 消息库与 `store_message` / `query_message`

这两个名称先表示用户所说的存取能力，不能只因现有 CLI 命令名不同就判定能力缺失，也不能把现有接口反过来规定为需求。

| 能力 | 要解决的问题 | 应让实例呈现的结果 | 尚未定稿 |
| --- | --- | --- | --- |
| `store_message` | 完整原件脱离临时 Session 后仍可取回 | 一条长正文保存后有稳定引用；通知不搬运整篇正文 | 最终 CLI/API 名称、精确参数、ID 和接受回执格式 |
| `query_message` | 接收方按职责、目标、时间或其他已确认条件取需要的消息 | 查询只返回有权看到的内容；可先看摘要，再取选定原件 | 查询语言、默认返回字段、分页、保留期及上限 |
| 可选 Context 整理 | 把重要消息整理为必读/选读上下文 | 整理结果能回到原始消息，原件继续保留 | 格式、整理角色、更新与接受方式；不要求每队常设该 Agent |

消息库的作用不只是给通知留日志：它让非紧急消息可以等待，让跨 Session 的接收方能自行查收，让摘要能回到原件，也为恢复和权限内查询提供依据。通知渠道只负责传递，不能凭“发送成功”代替库中保存或接收方已读。

保存消息本身不把消息内容升级成工程决定。工程共同状态和授权仍按各自接受规则处理。这里沿用当前项目约定，不新增自动从聊天修改图谱的机制。

## 3. 完整正文、摘要与引用

```text
发送者 → 软件存入完整消息 → 持久原件
                                ↑ 按权限取回
                极简摘要 + 引用 → 接收方 / 目标 Session
```

分离的是存储内容与进入注意力窗口的内容。正文与摘要可以在同一次底层传输中携带，再由接收软件收纳；这不意味着把整个传输 payload 塞进模型上下文。反过来，只推送一个引用也不能证明收件方离线时有可用原件。

发送者、项目、目标、时间与消息引用应让软件可靠补齐和解释，避免依赖模型自行维持身份与路由。具体信封字段仍是接口设计问题。来源文本不产生新权限，也不扩大已有用户授权。

旧文档还记载了“Agent 分别提供摘要和正文”“正文可以为空”“人输入聊天文字、正文是可选附件”“查收可带选定正文并登记已读”。这些细则原话尚未补证，不因本轮回读不到就删除，也不把它们改成已确认的最终参数规范。模拟应保留这些可比较情形。

## 4. 分级通知与宿主接收

| 情形 | 当前要求 | 实例必须说明的边界 |
| --- | --- | --- |
| 非紧急消息 | 留待 `queue` 或接收方主动扫描，不因到达就打断当前任务 | 任务边界和扫描频率可调整，不把固定轮询频率变成原则 |
| 紧急消息 | 通过宿主支持的 `steer` 请求进入当前执行 | 先知道目标和宿主能力；请求被接受不等于模型已经阅读或执行 |
| Session 空闲 | 演示宿主排队、下次启动或唤醒的实际差异 | 原生唤醒是否支持需逐宿主验证 |
| 宿主不支持或结果未知 | 如实呈现未支持、等待或未知结果 | 不把降级写成已打断，不用重复投递掩盖结果未知 |

Otoha 的非紧急消息队列与宿主的 `queue` 是不同层次：前者是待查收消息，后者是宿主安排后续输入的接口。`queued` 字段、消息送到本机或 API 返回成功，都不能单独证明目标 Session 的执行时机符合要求。

下列事实需要分别观察；它们不是要求 Core 内置的一套固定业务状态机：

| 观察 | 它能证明什么 | 它不能自动证明什么 |
| --- | --- | --- |
| 权威端接受存储 | 该端已接受这次消息写入 | 其他副本或 Session 已收到 |
| 本机收到并持久保存 | 接收进程已收纳消息 | 通知进入 Session |
| 宿主接受投递 | 宿主接口接受请求，保留其结果或标识 | 实际窗口可见、模型已消费 |
| Session 窗口呈现 | 在指定会话中实际观察到通知 | Agent 理解、接手或完成任务 |
| 读取正文/读取声明 | 原件被取回或调用方声明已读 | 心理意义上的阅读、接手、交付、验收 |
| 接手、交付、验收 | 各自按相应业务约定记录 | 前一状态自动推出后一状态 |

旧记录要求只有管理员可发打断消息。最新消息确认了紧急/非紧急的接收方式，没有重新确认这一授权细则。模拟应演示“普通成员请求升级”与“接收方按策略提前处理”两种候选；不能借当前服务恰好允许 `interrupt` 就认定普通成员获准打断。

## 5. 可见范围：保留既有记录，先核清再扩展

以下是旧决定记录的含义，不是从现有角色枚举推导出的新需求。具体原话和最初决定时间尚未补证。

| 身份/范围 | 旧记录 | 需要在模拟中核清 |
| --- | --- | --- |
| 管理员 | 可有多个；管理员库完整，包含所有消息，包括成员私发 | 该规则作用的项目范围、项目内管理员与跨项目全局管理员的映射；汇总到达前是否显式显示不完整 |
| 普通成员 | 公共消息、本人发出及发给本人的消息 | 接收者是成员、Agent、Session 还是频道；跨 Session 继承范围 |
| 普通成员本机副本 | 只含本人有权看到的部分 | 完整授权历史、按需缓存和待发记录各保存什么、何时补齐 |
| 图谱、消息、仓库、工作页 | 当前明确要求由同一 Otoha 项目管理 | 共用项目身份与权限依据；不同资源的具体操作权限可不同 |

“发给 B Session”是投递目标，“只有 B 能读”是访问权限，两者不能混同。管理员能查全库也不等于每条正文都应自动进入管理员 Agent 上下文。授权后再查询、聚合与生成本机副本；不要先把私信交给无权成员再在界面隐藏。

## 6. 权威端、本机副本、无独立服务器与恢复

旧记录将权威消息库放在服务器或队长电脑，并保留普通成员可见副本；队长离线期间，成员可经可用渠道互发，之后由 CLI 汇总管理员库。最新消息要求核清这些选择，本轮并未重新确认唯一拓扑。

“无服务器”在这里至少要拆清两种情况：没有独立常驻服务器、由队长电脑承担权威端；以及权威端当前离线但成员仍有某条可用通信渠道。它们都不自动等于完全无权威端、任意副本都能接受全局修改。

模拟应依次回答：

1. 中心在线时，一条消息在哪接受，接收方本机保存哪些内容。
2. 队长电脑关闭时，成员还能否经所选渠道互发；不能时显示待发，而不显示已送达。
3. 管理员尚未汇总的私发记录，如何显示范围和缺口。
4. 成员重启后如何找到尚未收纳的消息；哪些来源当前可用。
5. 权威端已接受但响应丢失时，先查询同一请求的结果，再决定重试。
6. 图谱离线修改只是待提交意图；恢复后仍经过接受流程，消息渠道在线不能替代这一流程。

发件箱、应用层确认、去重键和游标是可供实现的机制，不是恢复已经成立的证据。没有覆盖渠道保留期、双方长期离线和丢失本机记录的实测，不能承诺“永不丢失”。本轮不新增多主复制、CRDT 或自动语义合并。

## 7. 先跑通的一条模拟故事

同一个虚构项目中，管理员 A 邀请成员 B/C。B 有一个正在执行任务的 Session。页面始终明确标注“模拟”，后台库、渠道、本机副本和 Session 窗口分别可观察。

| 场景 | 操作与应观察的结果 | 通过模拟后仍需的真实验收 |
| --- | --- | --- |
| 加入项目 | 用精简材料完成加入，一次呈现仓库、消息、图谱和工作页的就绪/缺项 | 新的轻量模型会话盲测时长、操作数、重试和首轮成功率；不给作者额外口头提示 |
| 存、查、取原件 | 存一份长正文和独立短摘要，按权限查摘要，再按引用取原件；加入超过 100 条历史 | 中央持久化、授权查询、缓存边界与原件往返测试 |
| 非紧急与紧急 | B 忙时普通消息等待；紧急消息显示 steer 请求与宿主结果 | 在真实忙/闲 Session 观察窗口内容和时机，检查未把整篇正文注入 |
| 权限 | 切换 A/B/C 和第二管理员，比较公共、私发、只定向某 Session 的公共消息 | 历史、事件、query、本机副本均执行同一访问边界 |
| 离线与恢复 | 关闭权威端、恢复成员与权威端；显示待发、未汇总和未知接受结果 | 真实跨机重启、回连、回执核对和缺口补齐 |
| 工作页与反馈 | 同项目发布自由网页和可选 Graph 模板，全队采用同一更新；用户改变一条查收规则 | 真实同步、热更新、上下文保留；反馈进入共同需求后才改真实实现 |

指标是硬要求，但本轮没有给接入秒数、操作数、成功率样本量、资源或同步延迟编造门槛。先通过实例形成可判断的目标，再预先固定真实验收条件。模拟跑通、作者测试和真实用户接受分别记录。
