后续开发在 Otoha 仓库进行，参考基线见[已有基础](FOUNDATIONS.zh-CN.md)。下文区分用户已确定的计划、实施建议与实际验证范围。

## 已确定的方向

### 交付聚焦 CLI，Skill 可选下载

项目当前定位收缩为提供可下载的 Otoha CLI。Skill 作为可选配套，由使用者按需选择下载；CLI 的使用不以安装某个 Skill 或整套 Skill 为前提。CLI 承担软件能力，Skill 提供操作与方法指引。正式 CLI 下载发行尚待完成；具体打包方式和 Skill 分发方式待设计。

此前的 App 与原生 Agent 设想保留为后续讨论背景，不作为当前交付目标。

### 常驻协作服务与接入体验（2026-11-06）

CLI 控制常驻后台服务，统一管理通信、图谱与本地网页。用户使用现有 Agent 的语音或文字会话，Agent 通过工具调用操作 Otoha 并把工作呈现在网页上；Otoha 不承担语音模型或自主 Agent。人类界面与 Agent 接口保持简单，复杂的连接、协议和恢复由软件可靠完成。默认安静、操作快速，资源预算以实测确定。

一键接入私有仓库和自部署中心属于核心功能，支持自有/租用服务器与队长电脑。队长关机再开后自动续接，保留身份、游标与发件箱；离线图意图不当作已接受状态。私有 Gitea 承载私有项目和高频协作，GitHub 发布整理后的公开更新。完整功能边界与候选比较见[本轮范围说明](CLI-DAEMON-AND-GRAPH-SCOPE.zh-CN.md)。

### 在后续开发中实际运用需求实例化与持续对齐

接下来的 Otoha 开发要实际使用这两项理念：围绕尚待判断的需求，先呈现低成本、可操作的实例；在用户体验实例和阶段成果后，持续吸收反馈、修订共同需求，并让后续实现采用更新后的依据。不能只完成两份 Skill 就算兑现。

实施建议：选取一项具体需求，保留“需求 → 实例 → 反馈 → 决策 → 实现 → 再反馈”的关联记录。实例的载体和对齐节奏按实际问题选择；先验证一次反馈确实改变了需求或确认了方向，并落实到后续开发，再归纳可复用方法。

### 系统图谱：开放表达、通用修改、按需投影（2026-11-03）

当前采用自由 Property Graph `G=(V,E,s,t,P)`。节点和边有稳定身份，边有端点，Properties 可自由增删改；`type`、`relation`、`status` 等都是普通属性。业务含义、状态机和局部约束交给可选 Template，不预设任务 DAG、统一节点生命周期、父级森林或必填证据。完整定义见[系统图谱数学模型与边界](SYSTEM-GRAPH-MATH.zh-CN.md)。

| 部分 | 负责 | 与其他部分的边界 |
| --- | --- | --- |
| Core | 通用图状态与结构完整性 | 不要求节点先匹配某种业务 Schema 或出现在画布 |
| Mutation | 通用修改、操作前提与事务提交 | 业务复合操作由上层翻译；不自行分配 Agent 或传播失效 |
| Projection | 筛选、分组、商图、展开、追溯 | 结果来自同一原图版本，不维护第二份权威事实；Renderer 另管布局 |
| Template | 可选的词汇、局部 Schema/约束、查询和复合操作 | 不修改 Core 公理，不隐式授予权限或启用自动化 |

优先评估并复用现成图数据库，以数学契约检验其行为。具体产品、值域、部署方式和适配接口未定；不预设从零建设图引擎，也不以多后端框架或完整模板引擎作为首轮前提。JSON 保留为示例与导入导出格式。

这替换了此前 `G=(V,E,s,t,τE)` 和 L0–L6 的固定扩展路线；历史草稿见[旧数学模型](SYSTEM-GRAPH-MATH-v2-minimal.zh-CN.md)。[旧可视讲解器](system-graph-explainer.html)只保留历史推导，不作为当前模型或实现顺序的依据。新数学定义是设计基线，现有 `system.schema.json` 和运行代码尚未迁移。

## 图谱开发阶段与验收（实施建议，2026-11-03）

先完成一个薄闭环，再依据样本增加能力。下表定义阶段与最低验收，不因文档更新而自动完成；本轮已做的小样本初验范围见“当前进度与验证范围”。具体阶段顺序可根据数据库试验结果调整。CLI 下载交付和配套 Skill 可选的方向继续适用。

| 阶段 | 工作与产物 | 最低验收 |
| --- | --- | --- |
| 0 · 契约样本 | 建立小型参考图、修改前后状态和预期投影；收敛值域、删除、重连与身份语义 | 无 Template 也能表达空图、空属性、自环、多重边和自定义 Properties；缺失属性与 `null` 不混淆；正反例说明操作何时被拒绝 |
| 1 · 候选图数据库试验 | 选择一个候选后端，复用其存储、索引、查询和事务；记录适配缺口与 CLI 打包条件 | 同一参考图和操作序列可持久化、重启、往返导出；逻辑 ID、属性和端点不丢失；事务失败不留部分结果。测试结果只证明实际测试的范围 |
| 2 · Mutation 与状态管理 | 将现有权限、版本检查、请求去重和回执能力对照到通用节点、边和 Properties；实现必要的薄适配 | 覆盖一次原子批次、同一属性冲突、相互独立的有条件修改、依赖状态变化后的拒绝、相同请求重试；接受顺序、快照和 Diff 可核对，未知结果可按请求 ID 查证 |
| 3 · Projection 闭环 | 实现 Filter/Traverse、Group、Expand、Inspect 的首轮子集，再补齐；统一 Agent 与网页使用的结构化结果 | 用同一套千级虚构节点样本验证有界读取、分组、边界与按源版本追溯；聚合成员及原始边能查回；商图假路径不作为原图路径；记录实际读取量和耗时 |
| 4 · 最薄 Template 与兼容导入 | 用一个明确作用范围的场景约定验证属性词汇、局部约束和投影预设；设计旧 `system` IR 的导入与视图适配 | 不启用 Template 仍能读写通用图；场景约束不影响范围外对象；保留旧实体/任务/证据的身份与语义；同名 ID 不被误合并；布局不成为 Core 接受前提 |
| 5 · 真实 Agent 场景 | 把人的反馈、相关对象查询和有条件修改用于一项实际授权工作 | Agent 以局部 Projection 决策、必要时查原件、通过 Mutation 回传；人的修订确实改变后续执行；收到通知、读取、接手、交付与验收分别留证 |

阶段 0 的参考状态用于判断后端执行结果是否符合 `UΔ(G)`，不扩大为自研数据库。阶段 1 的选型记录至少比较自由属性及查询能力、端点修改限制、事务与并发接口、历史能力缺口、本地 CLI 部署成本、许可和维护状况；产品特性须在选型时重新核实。一次先试一个实现，不提前搭建通用多后端平台。

首轮状态管理建议使用单一权威接受顺序、必要的前置条件和幂等回执。具体检查粒度及格式待定，不以多主写入、CRDT、复杂分支合并或自动解决任意业务冲突为前提。图事务不包含外部文件或服务副作用。

兼容工作全部先用临时数据和测试身份，保留旧文件、来源、证据范围和接受历史；未经明确迁移范围，不接管真实状态。现有架构 Schema 以 Software Architecture Template 为适配目标，任务板以 Task Template 为适配目标；两者目前都还不是已实现的可插拔 Template。

阶段 0、1 已有[五节点样本与候选初验](GRAPH-DATABASE-EVALUATION.zh-CN.md)。下一步先收敛其已暴露的契约差异，再把一个候选接入最薄 Go CLI/受管进程链路；不同时扩展第二个后端。试验选择 SurrealDB 继续评估，验证版本为 3.3.5；4.0 已发布但未在本轮验证，正式接入前需固定版本并复验。边重连可用同一事务中的删旧边/同逻辑 ID 重建；禁止隐式级联若被采用，则在 Mutation 入口检查。上述行为均须与既有权限、接受历史和回执衔接，不能只暴露数据库原始写接口。

新交互讲解页应围绕同一个样本展示 Core、Mutation、Projection 和 Template 的边界，明确哪些操作只是示例；网页与 Agent 结果必须来自同一投影规则，不能各算一套关系。该页面是阶段成果的需求实例，不作为新 Core 已实现的证明。

## 场景与实现顺序建议

### 两机闭环与通信需求实例（2026-11-06 更新）

接入、工作页同步、反馈回传和断线恢复已完成一部分隔离实机试验，见[两机实验记录](TWO-HOST-LOOP.zh-CN.md)。这没有完成消息可见范围、完整成员副本、分级 Session 接收或通用图后端。原建议顺序保留下来供后续参考；当前先完成以下实例与反馈：

1. 同一条地图更新消息，比较完整存储、摘要/引用通知、query 原件与显式采用；读到原文不自动改变工作依据。
2. 切换管理员与两个成员，比较公共/私发、投递目标与读取权限；项目内管理员的范围是实例设定，不自动成为全局权限规则。
3. 比较普通 queue、主动扫描与紧急 steer；模拟宿主支持边界，然后在真实忙/闲 Session 单独验收。
4. 比较常驻服务器与队长电脑，观察离线待发、成员已收纳但中心未汇总及恢复查证。成员副本、备用渠道和汇总规则按来源状态讨论，不由当前 100 条缓存定型。

实例反馈收敛后的实施建议：先统一存取接口和摘要默认结果，并使历史、事件、查询、本机副本执行同一可见边界；再实现按紧急程度分流的宿主适配；最后补齐离线副本/汇总。每一步以独立测试身份做小样本验收，不把模拟按钮写成已完成能力。

此前的两机扩展建议：

1. Omarchy 测试中心与私有 Gitea → Mac 一次接入，分别核对仓库、项目授权和后台接收；不接管真实 receiver。
2. 接入一个受管图后端与通用 Mutation/有界 Projection → 真实 Agent 更新本地工作页 → 人反馈 → Agent 读取并调整执行。
3. 中心测试进程离线再恢复，以及接受成功但响应丢失 → 用原身份、游标和请求 ID 自动恢复，核对没有重复副作用；记录 CPU、RSS、延迟和恢复时间。
4. 在同一闭环试企业图引用项目图：进入、展开、同名局部 ID、重复引用和目标不可达。建议采用独立逻辑图加显式引用，不把它预先定为新 Core 公理或完整联邦平台。

这些步骤与上表图谱阶段交错推进。两机恢复、真实 Agent 操作、接入完成和人的验收分别留证；八项跨库存储实验不能代替它们。

以下场景根据[五项核心哲学](PRINCIPLES.zh-CN.md)提出，尚未作为完成的产品能力或最终实现方案；用于推进上述计划。

### 从体验反馈到协作修改

用户提出一项有隐含前提的需求。专门的对齐 Agent 先用一个低成本、可操作的实例呈现主要体验，邀请用户指出具体修改，再将反馈整理为共同需求与决策。两个执行 Agent 通过工程图谱读取各自需要的上下文，在明确策略下分工、交接和提交成果。用户体验阶段成果后可以继续修订目标。

过程中安排一次非紧急更新和一次影响当前工作的关键变更，观察接收方是否在合适时机读取原件，以及是否使用更新后的依据。这样能够同时检验实例、对齐、图谱、分级通信与调度是否连成一项实际工作。

场景初期可以在一个受控项目和一种宿主中完成。真实多人、跨机器和第二种宿主分别验收，不由本地模拟替代。

### 实现顺序

1. 选取一个需要通过体验才能判断的具体需求，先制作足够表达问题的实例，并确定反馈怎样回到共同需求。
2. 结合上述图谱阶段，在自由 Core 上用一项最薄的场景 Template 关联需求、实例、反馈、决策、模块与任务；这些是样本的业务角色，不是 Core 强制的类型。复用既有查询、版本和视图基础时，保留导入来源、许可与身份映射，并验证通用模型的实际改动。
3. 用临时状态打通完整内容保存、摘要与引用通知、按范围读取和任务边界查收；借用 Otoha CLI 与 Otoha Mailbox 的适合部分，明确当前调度策略。
4. 接入真实 Agent 宿主，执行上述场景；验证中途需求修订、实际阅读与成果回传，再拓展跨机器和第二种宿主。

这些步骤可以交错推进。最小场景从一开始就包含人的判断与需求实例，避免先把所有通信和状态功能建完才检验核心体验。

## 五项哲学的场景验收

| 核心哲学 | 场景中应观察到的行为 |
| --- | --- |
| 分级异步通信 | 非紧急消息不打断当前工作，在约定边界查收；关键消息按策略及时提示；完整内容可由引用取得 |
| 工程图谱与策略读取 | 人和 Agent 在相同版本、范围内读到一致的关系；执行者能用指定策略取得相关上下文及必要跨边界约束 |
| 持续对齐 | 用户在阶段成果后改变想法，对齐 Agent 能吸收、澄清并将变化传给相关执行者 |
| 需求实例化 | 用户能通过具体操作判断待确认的体验；反馈可关联回需求；模拟范围与真实实现清楚区分 |
| 协议与自适应调度 | 分工、依赖与交接有明确策略；常用协议可以复用，阶段变化后能够有依据地调整组织方式 |

还需检查断线、重启、重复事件和未知投递结果的恢复。实际投递、实际阅读和成果验收各有证据；这些是工程基础，不单独作为第六项特色。
