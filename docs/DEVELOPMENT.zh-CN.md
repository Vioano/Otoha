# 开发起点

后续开发在 Otoha 仓库进行，参考基线见[已有基础](FOUNDATIONS.zh-CN.md)。以下场景和实现顺序根据[五项核心哲学](PRINCIPLES.zh-CN.md)提出，尚未作为完成的产品能力或最终实现方案。

## 建议先打通：从体验反馈到协作修改

用户提出一项有隐含前提的需求。专门的对齐 Agent 先用一个低成本、可操作的实例呈现主要体验，邀请用户指出具体修改，再将反馈整理为共同需求与决策。两个执行 Agent 通过工程图谱读取各自需要的上下文，在明确策略下分工、交接和提交成果。用户体验阶段成果后可以继续修订目标。

过程中安排一次非紧急更新和一次影响当前工作的关键变更，观察接收方是否在合适时机读取原件，以及是否使用更新后的依据。这样能够同时检验实例、对齐、图谱、分级通信与调度是否连成一项实际工作。

场景初期可以在一个受控项目和一种宿主中完成。真实多人、跨机器和第二种宿主分别验收，不由本地模拟替代。

## 实现顺序建议

1. 选取一个需要通过体验才能判断的具体需求，先制作足够表达问题的实例，并确定反馈怎样回到共同需求。
2. 从固定版本选择 System Atlas 的最小图谱与查询基础，关联需求、实例、决策、模块与独立任务；记录导入来源和许可，运行相关测试。
3. 用临时状态打通完整内容保存、摘要与引用通知、按范围读取和任务边界查收；借用 Atlas CLI 与 Team Mailbox 的适合部分，明确当前调度策略。
4. 接入真实 Agent 宿主，执行上述场景；验证中途需求修订、实际阅读与成果回传，再拓展跨机器和第二种宿主。

这些步骤可以交错推进。最小场景从一开始就包含人的判断与需求实例，避免先把所有通信和状态功能建完才检验核心体验。

## 五项哲学的场景验收

| 核心哲学 | 场景中应观察到的行为 |
| --- | --- |
| 分级异步通信 | 非紧急消息不打断当前工作，在约定边界查收；关键消息按策略及时提示；完整内容可由引用取得 |
| 工程图谱与策略读取 | 人和 Agent 在相同版本、范围内读到一致的关系；执行者能用指定策略取得相关上下文及必要跨边界约束 |
| 持续对齐 | 用户在阶段成果后改变想法，对齐 Agent 能吸收、澄清并将变化传给相关执行者 |
| 需求实例化 | 用户能通过具体操作判断待确认的体验；反馈可关联回需求；模拟范围与真实实现清楚区分 |
| 协议与自适应调度 | 分工、依赖与交接有明确策略；常用协议可以复用，阶段变化后能够有依据地调整组织方式 |

还需检查断线、重启、重复事件和未知投递结果的恢复。实际投递、实际阅读和成果验收各有证据；这些是工程基础，不单独作为第六项特色。
