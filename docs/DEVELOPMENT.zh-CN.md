# 开发起点

后续开发在 Otoha 仓库进行，参考基线见[已有基础](FOUNDATIONS.zh-CN.md)。本文件的场景与实现顺序是建议；五条核心原则补全后，应先核对它们是否改变这一选择。

## 建议先打通的一项工作

用户提出一项跨模块修改，在共同项目状态中看到目标、相关模块和任务；两个 Agent 在明确的调度策略下完成分工与交接，提交成果和证据；用户从同一份状态理解结果，并能修改目标、暂停或转向。

这个场景同时检验模型、协议和会话投递是否连得起来。先用一个受控项目和一种宿主完成，再根据暴露的限制选择下一种适配。

## 实现顺序建议

1. 整理五条原则，以实际任务明确输入、真实输出和需要用户介入的位置。
2. 从固定版本运行三个旧项目的相关测试，选择最小复用范围，记录导入来源与许可。
3. 在本地临时状态和模拟投递中打通任务、消息与成果引用，检验失败和恢复行为。
4. 接入一个真实 Agent 宿主，验证实际阅读、接手、交付和意图修订；再做跨机器与第二种宿主验证。

## 首个场景的验收建议

- 人和 Agent 在相同版本与范围内读到一致的任务与系统关系。
- 用户修改目标时，相关 Agent 能看到修改，并能识别旧任务或旧成果受到什么影响。
- 当前调度策略可被解释；交接与依赖有明确记录，任务阶段改变后能够调整策略。
- 断线或进程重启后保留进度，重复事件不导致重复副作用，未知投递结果可以核对。
- 实际投递、实际阅读和成果验收各有对应证据，局部测试通过不被写成完整工作已完成。
