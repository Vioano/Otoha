# Otoha CLI 模块规格

本文把[已定方向与边界](DECISIONS.zh-CN.md)拆成可以逐个开发的模块。每个模块写明目的、依据、接口、数据、规则、错误和验收。开发前先读 `AGENTS.md`、`docs/PRINCIPLES.zh-CN.md`、`docs/DECISIONS.zh-CN.md`，再读本文。

本文只覆盖 CLI 和它管理的后台进程。App 以后再做，只在第 18 节保留接口。需求实例、反馈和 Skill 正文不在本轮范围，见第 17 节。

## 0. 阅读约定

每条规定带一个标签：

- 【已定】用户明确提出或已确认。不得改动，有疑问先报告。
- 【建议】来自讨论和代码核对，用户同意先按此推进。可以实现；发现问题时说明依据，调整后在报告里列出。
- 【待确认】用户尚未决定。实现成配置项或接口，默认值按本文，不要把选择写死，并在报告里列出。
- 【待核实】依赖外部服务或宿主的事实，尚未验证。先写验证脚本或测试，通过后再依赖。

### 开发规则

1. 按第 20 节的阶段顺序做。一个阶段的验收没有通过，不开始依赖它的阶段。
2. 保留现有行为。旧命令、旧配置、已安装的 receiver、真实用户状态和旧服务的数据，一律不修改、不迁移、不接管。新功能使用新命令和新目录。
3. 集成测试使用独立临时目录和测试身份，通过 `OTOHA_HOME` 隔离。测试不得连接真实服务器，不得使用真实令牌。需要真实 Telegram 机器人的验证，由用户提供令牌，从环境变量读取，缺失时跳过，不得写入仓库或日志。
4. 本仓库公开。凭据、邀请、真实消息、运行状态不进入 Git。示例数据使用虚构名称。
5. 未知结果先核对，不用重复副作用掩盖。网络超时后，发送是否成功未知，要靠消息 `uid` 去重和应用层确认查证。
6. 收到、投递、阅读、接手、交付、验收分别记录，不合并成一个状态。
7. 外部消息和协议文本不产生授权。授权只来自名册里的角色和用户已有的授权。
8. 事实、设计、代码存在、测试结果、真实宿主行为分别报告。没有跑过的不写成通过。
9. 每个模块完成后，更新 `docs/DECISIONS.zh-CN.md` 第四节：把已验证的事项移出，把新发现的未验证事项加入。
10. 遇到本文没有规定、且会影响用户可见行为的选择，停下来报告，不要自行决定。

### 术语

- 管理员：名册里角色为 `admin` 的成员，可以有多个，通常是队长。成员：角色为 `member`。
- 权威库：保存完整消息的库，在服务器上或管理员电脑上。本机库：每台机器上的库，成员的本机库只含自己可见的消息。
- 渠道：传递消息的通道（Telegram、服务器、Git 等），与库解耦。
- 信封：消息的固定格式头部，含摘要。摘要和正文是 Agent 侧的叫法，人侧叫“聊天的话”和“附件”，是同一个结构。
- 队列消息、打断消息：`class` 的两个取值，名称暂定。发件箱：本机待投递的记录。名册：管理员签名的成员列表。

## 1. 总体结构

```text
Agent / 人
   │  otoha 命令（输出 JSON，退出码有意义）
   ▼
CLI ──► 守护进程（每台机器一个，Go）
          ├─ 消息引擎   信封、发件箱、本机库、查收、回执
          ├─ 渠道层     适配器：telegram、server、git、…（可同时启用多个）
          ├─ 同步       成员库→管理员库汇总、离线补收
          ├─ 宿主适配   把打断消息的摘要送进 Agent 会话
          ├─ 受管后端   图谱服务（Node）、协作服务（Python）
          └─ 本机接口   127.0.0.1 HTTP，CLI 与以后的 App 共用
```

- 【已定】CLI 与 App 功能镜像，CLI 面向 Agent，App 面向人。先做 CLI。
- 【已定】消息库与渠道是两层，可自由组合，CLI 把两层包起来。
- 【建议】CLI 命令不直接读写库，都通过守护进程。守护进程没运行时，命令负责拉起它（可用 `--no-daemon` 关闭，只读命令例外）。理由：单写者，避免多个进程同时写本机库。
- 【建议】Go 外壳；Python 协作服务和 Node 图谱服务作为被管理的子进程。【待确认】打包方式：内嵌运行时、首次使用时下载，还是逐步迁移到 Go。第一阶段只要求在开发机上能启动它们，并在 `otoha doctor` 里报告缺失的运行时。
- 守护进程崩溃后由系统服务管理器（macOS launchd、Linux systemd、Windows 服务）拉起。已有 `internal/otoha/service.go` 管理的 receiver，沿用其安装方式，不另装第二个。

### 通用命令约定

- 所有命令输出 JSON 到标准输出，人读的提示和日志输出到标准错误。加 `--text` 输出人读文本。
- 退出码：0 成功；1 一般错误；2 参数错误；3 无权限；4 暂时不可用（可重试）；5 结果未知（必须先核对再重试）。
- 每个有副作用的命令接受 `--request-id`，重复使用相同 ID 不重复执行副作用。
- `OTOHA_HOME` 选择私有目录，默认沿用现有逻辑（`~/.config/otoha`）。所有状态在此目录下，目录权限 0700，文件 0600。
- 命令名和参数名使用英文；面向用户的消息文本使用中文，错误码使用英文标识。

## 2. 模块 A：身份与名册

目的：确定谁是谁、谁是管理员，供其他模块做授权。

依据：【已定】权限只分管理员和成员，可以有多个管理员；成员标识要能绑定到发送者，不能由发送者自行声明。

数据：

- 成员身份：成员标识（`[a-zA-Z0-9][a-zA-Z0-9_-]{0,99}`，沿用现有规则）、显示名、公钥（Ed25519）、角色（admin/member）、状态（active/revoked）、各渠道的联系方式（例如 Telegram 机器人用户名，不含令牌）。
- 名册：全体成员的列表，由管理员签名发布，带版本号。成员只接受版本号更大、签名有效的名册。
- 本机私钥：成员在本机生成，存于私有目录，不进入名册和接入包。

规则：

- 【建议】沿用图谱协作的 Ed25519 签名（`packages/graph/team/protocol.mjs` 的 `signed`/`verified` 与规范化 JSON），消息签名使用相同方案，签名域不同（见模块 C）。
- 【建议】信封里的“发送者”由 CLI 从本机身份填写，并用本机私钥签名。接收方用名册里的公钥验证。无法验证的消息标记为 `unverified`，不交给 Agent，除非用户配置了允许。
- 【建议】一台设备上同一成员的多个 Agent 会话共用成员身份，会话标识区分。会话注册沿用现有 `sessions` 概念。
- 【建议】撤销成员：管理员发布新名册，该成员状态改为 revoked，不再接收新消息。已离队成员本机已有的内容无法收回。
- 【待确认】现有服务有“凭据+授权”，图谱协作有“公钥+授权”。第一阶段保留两者，在名册里记录两者的对应关系；合并成一套身份放到接入模块定稿后。

命令：

```text
otoha identity init --member ID --name NAME     生成本机密钥对，不联网
otoha identity show                              显示成员标识、公钥指纹、角色
otoha roster show
otoha roster verify
otoha member list
otoha member role MEMBER admin|member            仅管理员，发布新名册
otoha member revoke MEMBER                       仅管理员
```

验收：

- 签名错误、版本回退、公钥不符的名册被拒绝，有对应测试。
- 私钥文件权限 0600，目录 0700，位于任何 Git 工作区之外（沿用 `initializeIdentity` 的检查）。
- 角色变更只有管理员能做；非管理员发布的名册被拒绝。

## 3. 模块 B：项目初始化与接入

目的：队长一次初始化出项目，成员用接入包加入。

依据：【已定】接入流程五步（见 DECISIONS “团队接入流程”）。队长选择权威库放在队长电脑还是服务器，选择渠道。

命令：

```text
otoha project init NAME --store local|server --channels telegram,git,…  --purpose TEXT
otoha project invite MEMBER --role member|admin  [--days N]  --out FILE
otoha join --invite FILE                         成员接入
otoha project status
otoha project add-channel CHANNEL
otoha project remove-channel CHANNEL

# 当前 Go CLI 已实现的本机团队编排入口
otoha team init NAME --mode local [--data DIR] [--port PORT]
otoha team invite TEAM MEMBER --role member|admin|reader --out FILE
otoha team join --invite FILE
otoha team status [TEAM]
otoha team doctor [TEAM]
```

接入包（【建议】，与旧邀请包不同）：

- 内容：项目标识、周期（epoch）、权威库地址或渠道联系方式、队长公钥指纹、名册首版的哈希、一次性邀请码、角色、已启用渠道的公开联系方式（例如各机器人用户名）。
- 不含：私钥、机器人令牌、长期凭据、任何成员的个人凭据。旧 Atlas CLI 的邀请包带个人凭据且不过期，不沿用。
- 邀请码：一次性，默认 7 天过期，可撤销，兑换失败 5 次后锁定一小时（参考 Hermes 配对码规则）。
- 接入包会经过 Agent 的上下文和聊天记录，所以包里的内容即使泄露，也只能让攻击者在有效期内尝试兑换一次，且兑换需要管理员批准或服务器规则允许。

流程：

1. `project init`：生成项目标识和周期，初始化权威库（本机或服务器），生成队长身份并写入名册，写出项目配置。
2. `project invite`：生成邀请码并记录哈希，写出接入包文件。文件权限 0600，命令输出提醒“通过其他渠道私下发送，不要提交到 Git”。
3. `join`：校验接入包格式，生成本机密钥对，向权威库（或管理员）提交公钥和邀请码，等待批准或自动批准，成功后拿到最新名册，配置渠道（提示成员输入自己的机器人令牌，令牌只写入本机私有目录），启动守护进程。
4. 成员的机器人令牌：只存本机，不上传，不进名册。名册只保存机器人用户名。

规则：

- 【已定】管理员（队长）可以只用自己的电脑，也可以用服务器。
- 【已定】默认每位成员有自己的机器人（用户已确认）。
- 【建议】`project init` 要求先通过 `otoha doctor` 的基本检查（目录权限、网络、所选渠道的凭据）。
- `join` 是幂等的：同一接入包重复执行不会创建第二个身份；已完成的接入再执行，报告当前状态。
- 保留旧命令 `setup`、`project create`、`join KEY`、`import`、`pack`，行为不变。新命令放在新的子命令下，避免与旧参数混淆。【建议】旧命令在帮助里标注为“旧版（Atlas 兼容）”。

验收：

- 用临时目录和测试身份，完整跑通：init → invite → join → 名册同步，不连接真实服务。
- 接入包中搜索不到任何私钥或令牌（测试里对包内容做字符串断言）。
- 过期、已兑换、已撤销、锁定四种邀请码失败路径各有测试。

## 4. 模块 C：消息信封与签名

目的：定义消息的固定格式，是所有消息模块的共同基础。

依据：【已定】摘要和正文分开；进入 Agent 上下文的只有摘要；Agent 只提供摘要和正文，其余由 CLI 补；发送者要区分人和 Agent 并写明成员、Agent、会话；正文可以为空。【建议】信封的具体字段。

信封字段：

```json
{
  "v": 1,
  "uid": "全局唯一消息标识，发送方生成",
  "project": "项目标识",
  "epoch": "周期",
  "ts": "UTC 时间，RFC 3339",
  "from": {"member": "...", "kind": "human|agent", "agent": "...", "session": "...", "device": "..."},
  "to": {"scope": "public|member|channel", "members": ["..."], "channel": "..."},
  "class": "queued|interrupt",
  "kind": "message|task|result|question|status",
  "summary": "一句话摘要",
  "refs": [],
  "reply_to": "uid 或 null",
  "body": {"length": 0, "sha256": "...", "inline": true},
  "sig": "对规范化后的信封（不含 sig）的 Ed25519 签名"
}
```

规则：

- `uid`：【建议】发送方 CLI 生成，格式为时间有序的随机标识（例如 ULID 或 UUIDv7）。它是去重、确认、回执的依据。权威库另给顺序号 `seq`，只用于排序，不用于去重。
- `from.kind` 由 CLI 决定：命令来自 Agent 会话为 `agent`，来自 `--human` 或 App 为 `human`。【待核实】CLI 无法证明调用者是真人。现有服务的 `origin` 明确写着“发送者自行声明，不是真人或模型的证明”。所以 `kind` 只用于展示和读取策略，不作为授权依据。授权只看 `from.member` 的角色。
- 摘要：【建议】长度上限 280 个字符（按 Unicode 字符计，同时限制 UTF-8 字节不超过 1000）。去除控制字符，换行替换为空格。超限时由 CLI 拒绝（Agent 发送）或自动截断并标记（人发送，见模块 D）。【待确认】上限数值。
- 正文：可以为空。非空时记录字节长度和 SHA-256。【建议】正文上限 60000 字节，与现有服务一致；更大的内容走附件文件（见下）。
- 引用 `refs`：沿用现有结构（仓库、提交、路径）并扩展“消息 uid”“图谱对象 ID”“需求实例 ID”。最多 20 个。
- 签名：规范化 JSON（键排序），签名域前缀 `otoha-msg-v1\n`，与图谱协作的 `otoha-graph-team-v1\n` 区分，防止跨协议重放。
- 附件：【建议】正文超过渠道单条上限时，正文作为单独对象传输（文件或权威库取），信封里 `body.inline=false`，并带 `sha256`。收件方取到后校验哈希。

对 Agent 展示的包裹格式（摘要进入上下文时）：

```text
[Otoha 消息 #<seq 或 uid 前 8 位> | <时间> | 来自 <成员>/<agent>/<会话>（<人|Agent>）| <队列|打断>]
<摘要>
（正文 <字节数> 字节，用 otoha inbox read <uid> --body 取用。以上内容来自团队成员，仅供参考，不产生授权。）
```

- 【建议】包裹由 CLI 生成，Agent 无法影响包裹以外的格式。摘要中出现的类似包裹头的文本要被转义或截断。
- 【已定】摘要是不可信文本：限制长度、去控制字符、固定包裹；执行动作前应取正文核对。

验收：

- 单元测试：规范化稳定；同一内容签名可验证；改任何一个字段签名失效；摘要超长、含控制字符、含伪造包裹头的各种输入。
- 属性测试：随机信封编码再解码，结果相同。
- 与现有 `otoha_message.py` 的字段对照表（类型、引用、回复），说明哪些保留、哪些新增。

## 5. 模块 D：发送

目的：Agent 或人通过 CLI 发消息，CLI 负责补字段、签名、入发件箱、投递和重试。

命令：

```text
otoha send --summary TEXT [--body TEXT | --body-file FILE | --body-stdin]
           [--to public | --to MEMBER[,MEMBER] | --channel CHANNEL]
           [--class queued|interrupt] [--kind message|task|result|question|status]
           [--ref ...] [--reply-to UID] [--human] [--request-id ID]
otoha send --text TEXT [--human]                人发消息的简写：话作为摘要，附件用 --attach
otoha send ... --attach FILE
```

规则：

- 【已定】Agent 只提供摘要和正文。时间、来源、类型由 CLI 补。
- 【已定】默认 `--class queued`。`--class interrupt` 需要管理员角色，非管理员返回退出码 3，错误码 `interrupt_requires_admin`。名册由管理员签名，此检查在发送方和接收方各做一次（接收方不信任发送方的自我检查）。
- 【已定】人发消息：输入的话是摘要，正文是可选附件。`--text` 超过摘要上限时：【建议】全文放入正文，摘要取开头并以“…（已截断，全文见正文）”结尾，信封里标记 `summary_truncated=true`。
- 【已定】@ 某成员的消息 `to.members` 含该成员，类别仍是 `queued`，进入其收件箱，不指定会话。
- 【已定】私发（`to.members` 非空）不得发到群：渠道层选择点对点投递路径；渠道不具备点对点能力时，命令失败并说明，不降级为群发。
- 发送流程：校验 → 补字段 → 签名 → 写发件箱（`pending`）→ 返回 `uid`。写入发件箱即视为命令成功，不等待网络。守护进程异步投递。
- 命令默认立即返回，输出 `{"uid":..., "state":"queued_local"}`。`--wait` 等待到权威库确认或超时，超时返回退出码 5 并说明“结果未知，用 uid 核对”，不重复发送。
- 投递状态逐条记录：`pending → sent(渠道) → acked(收件方应用层确认) → failed`。渠道发送成功不等于收件方已收到，必须等应用层确认。
- 重试：指数退避加抖动，上限 2 分钟；`retry_after` 小于等于 5 秒时原地等待，更长的放回队列由调度器重试（参考 Hermes）；永久错误（无权限、收件人被撤销）不重试，标记 `failed`。
- 去重：以 `uid` 为准。重复发送同一 `uid` 或同一 `--request-id` 不产生第二条。
- 限流：【已定】在通信层做，不依赖 Agent 自觉。按渠道的能力声明执行，每个渠道/聊天一个令牌桶，发送和编辑共用额度，普通消息排队等待，不丢弃。
- 循环保护：【建议】对来自 `kind=agent` 的消息，自动回复深度上限默认 3，同一对 Agent 之间短时间内的消息数有上限，超限暂停并报告，参考 Telegram 官方对机器人互发的警告。【待确认】数值。

验收：

- 断网时发送成功入发件箱，恢复后自动投递；进程被杀后重启，发件箱不丢、不重复。
- 同一 `uid` 重复提交只有一条。
- 非管理员发 `interrupt` 被拒；伪造管理员身份的消息在接收方被拒。
- 私发在不支持点对点的渠道上失败，不发到群。
- 超长摘要、含控制字符的摘要、空摘要的行为有测试。

## 6. 模块 E：本机库与权威库

目的：保存消息，按权限给出可见范围。

依据：【已定】权威库在队长电脑或服务器，保存完整；成员本机只存自己可见的部分加公共部分；本机库明文存储；管理员的库是完整的，可以有多个管理员。

本机库（SQLite，位于 `OTOHA_HOME`）：

- `messages`：`uid`（主键）、`seq`（可空，权威库给出后填入）、信封 JSON、正文（可空，按需拉取）、正文哈希、接收时间、来源渠道。
- `delivery`：逐条状态，每条消息每个会话一行：`seen`（摘要已交给 Agent）、`read`（取过正文）、时间。
- `outbox`：待投递记录，含重试次数、下次重试时间、最后错误。
- `cursors`：每个渠道、每个同步对象的游标。
- `roster`：当前名册及签名。
- `dedup`：已处理的外部事件 ID（渠道 update ID），保留 24 小时以上，落盘，重启后仍有效（参考 Hermes 的回执文件）。

规则：

- 【已定】成员本机只存可见的消息：公共消息；发件人是自己的；收件人包含自己的。管理员的库存全部。判断可见性的规则只有一处实现，发送、接收、同步都调用它。
- 【建议】权威库在服务器模式下使用现有协作服务（Python）；在队长电脑模式下，队长的守护进程内嵌同样的库逻辑。两种模式对外接口一致。第一阶段可以让队长电脑模式也启动 Python 服务，第二阶段再内嵌。
- 【建议】权威库为每条消息分配 `seq`（频道内递增），用于排序和增量拉取。现有协作服务的消息 ID 已有此语义。
- 【建议】逐条记录“已读”，向权威库上报时再汇总为现有的高水位回执，不修改旧回执接口。
- 数据库迁移：用版本号和迁移脚本，只增不删；打开时检查版本，高于自己则拒绝写入。
- 并发：只有守护进程写。使用 WAL 模式，事务内完成“写消息+写去重记录”，保证先持久化再确认渠道。
- 容量：消息保留策略【待确认】，默认不删除。正文可以按年龄或大小清理，信封保留。

验收：

- 可见性规则有表格式测试：公共、私发给 A、A 发给 B、管理员视角、被撤销成员，每种组合一行。
- 崩溃测试：在“写消息”和“确认渠道”之间终止进程，重启后无丢失、无重复。
- 迁移测试：旧版本数据库升级后可读。

## 7. 模块 F：渠道层与适配器接口

目的：把各种传递通道统一成同一个接口，渠道可同时启用多个，增减不改其他模块。

依据：【已定】渠道可选、可多个；先做 Telegram，优先机器人互发；参考 Hermes 的插件做法；没有 Telegram 的成员要有其他渠道。

适配器接口（Go）：

```go
type Channel interface {
    Name() string
    Capabilities() Capabilities
    Connect(ctx context.Context) error
    Close() error
    Send(ctx context.Context, out Outbound) (SendResult, error)
    Receive(ctx context.Context, sink func(Inbound) error) error   // 阻塞，直到 ctx 结束
}

type Capabilities struct {
    DirectToMember   bool          // 能否定向投递给指定成员
    PrivateChat      bool          // 成员之间能否私聊
    Broadcast        bool          // 能否群发/公共
    Retention        time.Duration // 离线未读保留多久，0 表示不保留
    History          bool          // 能否拉取历史
    MaxTextBytes     int           // 单条文本上限（字节）
    MaxFileBytes     int64
    RateLimit        RateLimit     // 每聊天、全局
    DeliveryReceipt  bool          // 渠道自身是否有送达回执
}
```

- `Inbound` 带渠道自己的事件 ID（用于去重）、原始发送者标识、载荷。适配器只负责收发，不解析信封、不做授权。
- 【已定】适配器把渠道里的发送者映射到名册里的成员，由渠道层的公共代码完成，适配器层不产生授权。映射表来自名册里记录的各成员联系方式（机器人用户名、用户 ID）。映射不到的发送者，消息丢弃并记录，不交给上层。
- 能力决定用途：`DirectToMember && PrivateChat` 的渠道可承担私发；只有 `Broadcast` 的渠道只用于公共消息和通知。
- 每个渠道有清单（`channel.yaml` 或 Go 结构）：名称、显示名、所需配置项（名称、说明、是否机密）、可选配置项。`project add-channel` 的向导按清单逐项询问；机密项不回显，存入私有目录。
- 渠道注册：编译期注册即可（Go），不需要动态插件。【建议】预留外部适配器进程协议，第一阶段不做。
- 路由：发送时按“收件人 + 类别 + 能力”选渠道；有多个可用渠道时按优先级尝试，失败回落到下一个。公共消息可同时走多个渠道，以 `uid` 去重。
- 渠道的凭据（机器人令牌等）只存在本机私有目录，不写入名册和接入包。

要实现的渠道，按顺序：

1. `telegram`（模块 G）。
2. `server`：连接 Otoha 协作服务（HTTP），作为权威库的访问通道，不是普通渠道，见模块 H。
3. `git`：沿用 `GitTransport` 的做法，只承载公共内容（模块 I）。
4. 第二个社交渠道：【待确认】候选 Matrix、Discord、Slack、ntfy。选择前必须先核实它能否让两个机器人定向私聊（DECISIONS 第四节）。选定后按同一接口实现，用来检验接口抽象是否站得住。

验收：

- 提供 `FakeChannel` 测试替身，支持注入延迟、丢包、重复、乱序、限流错误，模块 D、E、H 的测试都用它。
- 增删渠道不重启守护进程也不丢消息。
- 能力不满足时（私发走不支持私聊的渠道）有明确错误。

## 8. 模块 G：Telegram 适配器

目的：第一个真实渠道。

依据：【已定】先做 Telegram，优先机器人互发；每位成员有自己的机器人；私发走机器人私聊，不发到群；一个令牌只能有一个轮询者；不经它发送密钥或敏感内容。

事实（已核对）：

- 机器人互发：Bot API 10.0（2026-05-08）起，私聊里传对方 `@username`，双方都需在 @BotFather 开启 Bot-to-Bot Communication Mode。群里需要命令加提及或回复。官方警告会形成无限循环。
- 文本上限 4096 字符（取自 Hermes 适配器，官方页面未抓到原文）；通过 HTTP URL 发文件 20 MB，上传 50 MB，图片 10 MB。
- 未确认的更新保留 24 小时。

【待核实】必须先做的验证脚本（`scripts/telegram-probe`），由用户提供两个测试机器人令牌，环境变量读取，缺失则跳过：

1. 两个机器人开启模式后，A 用 `@B` 发私聊，B 的 `getUpdates` 能否收到，消息里发送者的 `is_bot` 和 `username` 字段是什么。
2. B 离线一段时间再上线，能否补收；离线超过多长时间会丢。
3. 实际的限流行为：连续发送时何时出现 429、`retry_after` 的大小。
4. 4096 的单位（字符或 UTF-16 单元）和中文的实际行为。
5. 机器人下载文件的大小上限，托管服务器与本地 Bot API 服务器的差别。

验证结论写入 `docs/evidence/` 并更新 DECISIONS 第四节。验证没有通过前，模块 G 的私发能力标为实验性。

实现要求：

- 使用长轮询 `getUpdates`，不用 Webhook（成员电脑没有公网地址）。`allowed_updates` 只要消息类型。
- 先持久化再确认：收到更新后，在同一事务里写入本机库和去重记录，成功后再推进 `offset`。参考 Hermes 的回执文件，去重记录保留至少 24 小时。
- 网络错误：指数退避加抖动，重建连接；遇到轮询冲突（409，另一个进程在轮询同一令牌）时停止并报告，不抢占，不删除 Webhook。
- 发送：每个聊天一个令牌桶，默认间隔不低于 1 秒；遇到 429 遵守 `retry_after`，≤5 秒原地等待，更长放回队列；长文本超过上限时分片并带序号，或改发文件。
- 私发只走机器人私聊。收件人的机器人用户名来自名册。群只用于公共消息，且【建议】默认关闭，需要时由管理员启用。
- 发送者身份：只信任 `from.id` 与名册登记一致的消息；信封里声称的成员与渠道发送者不符时丢弃。
- 机器人互发的循环保护：参考模块 D。
- 令牌：只在本机私有目录，日志和错误信息中脱敏。令牌泄露的处理：`otoha channel rotate-token telegram`。
- 能力声明：`DirectToMember=true`（待核实后确认）、`PrivateChat=true`、`Retention=24h`、`History=false`、`MaxTextBytes` 按核实结果，`RateLimit` 按官方建议保守取值。

验收：

- 用 `FakeChannel` 风格的 Telegram API 模拟服务器（本地 HTTP）测试：重复更新、乱序、429、409、网络中断、超长文本。
- 有真实令牌时，端到端：A→B 私发、B 离线补收、循环保护触发。无令牌时这些用例显示“跳过”，不是“通过”。

## 9. 模块 H：权威库访问与服务器模式

目的：队长选择“服务器”或“队长电脑”后，成员怎样读写权威库。

依据：【已定】权威库位置由队长初始化时选；服务器模式下服务器保存完整库，服务器上的 CLI 负责只把消息发给该收到的人。

规则：

- 【建议】服务器模式：成员 CLI 通过 HTTP(S) 访问协作服务。现有接口 `/v1/messages`、`/v1/receipts`、`/v1/events` 等沿用，新增字段（摘要、类别、收件人、`uid`）按向后兼容的方式扩展：旧客户端发的消息，摘要缺省时取正文首句。
- 【建议】新增 `uid` 与现有 `client_id` 的关系：`uid` 作为 `client_id` 写入，保证现有的 `UNIQUE(actor, client_id)` 能做去重。
- 【建议】服务器按名册和角色过滤读取结果：成员只能读公共、自己发出和发给自己的；管理员读全部。过滤发生在服务器查询里，不是查完再删（沿用旧项目 personal-atlas 的 `docs/通信权限与读取策略.md` 的做法，不要先读全库再过滤）。
- 【建议】队长电脑模式：队长的守护进程提供相同接口，监听本机并通过渠道（Telegram 等）或隧道对外。队长关机时，成员消息留在发件箱（模块 D），队长上线后补投。成员之间的消息此时走渠道直接投递，并在队长上线后由 CLI 汇总（模块 J）。
- 【已定】汇总有时间差，管理员库在汇总完成前不含该私发消息。【建议】发送私发消息时可选抄送管理员（`copy_admin`，默认开启），渠道层向管理员的机器人额外发一份信封，上报作兜底。
- 认证：沿用现有凭据机制，第一阶段不改。【安全】图谱网页服务通过网络暴露之前必须加认证（见第 14 节）。
- 事件流：沿用 `/v1/events` 的服务端推送，客户端断线后用最后事件 ID 续传。

验收：

- 在测试用的临时服务实例上，成员 A、B 和管理员，验证三者各自读到的消息集合与可见性表一致。
- 旧版协作服务的数据库升级后，旧消息仍可读；不修改旧部署。

## 10. 模块 I：Git 渠道（公共内容）

目的：没有服务器、没有机器人时，用 GitHub、GitLab、Gitea 的私有仓库传递公共内容和图谱变更。

依据：【已定】不用 Issue 做高频通信，提交专用的交流文件变更，对方拉取解析；这类平台只承载公共内容，不做私发，暂不开发加密协议。

规则：

- 沿用 `packages/graph/team/transport.mjs` 的安全做法，用 Go 重写或调用现有 Node 实现：只存数据文件；不检出、不合并、不执行；关闭钩子；路径白名单；快进推送重试三次；单文件大小上限。
- 路径：`otoha/<member>/messages/<yyyymm>/<uid>.json`（信封加内联正文）。【建议】每个成员只写自己的目录；按月分目录，避免单目录条目过多（现有实现超过 10000 条会报错）；旧月份可归档。
- 只允许 `to.scope=public` 的消息；`member` 范围的消息发往此渠道时拒绝并报错。
- 读取：定期 `git fetch`（默认 30 秒，可配置），解析新增文件，校验签名和名册后写入本机库。
- 频率：【已定】避免触发封控。合并同一时间窗内的多条消息为一次提交；单仓库提交频率有上限，默认每分钟不超过一次推送；遇到服务端限流退避。
- 认证：使用成员自己的账号和已配置的 Git 凭据助手；Otoha 不保存 Git 令牌。
- 敏感内容：Git 历史不能真正删除，发送前扫描明显的密钥模式（令牌、私钥头），命中则拒绝并提示。

验收：

- 用本地裸仓库做远端：两个成员互发公共消息、并发推送冲突、重复文件、签名错误文件、路径越界文件。
- 私发消息发往此渠道被拒绝。

## 11. 模块 J：收件箱与查收

目的：Agent 做完一轮任务后自己查收；人也能查看。

依据：【已定】队列消息存入数据库，等当前任务做完后自己去查收；公共消息同理；查收命令可以选择同时带上正文，带上的同时记为已读；CLI 启动时自动查找尚未查收的消息。

命令：

```text
otoha inbox check [--since CURSOR] [--limit N] [--class queued|interrupt] [--body] [--mark seen]
otoha inbox read UID [UID...] [--body]           取正文，记为已读
otoha inbox list [--unread] [--from MEMBER] [--limit N]
otoha inbox ack UID [UID...]                      仅标记已看（不取正文）
```

规则：

- `check` 默认只返回摘要（包裹格式，见模块 C），并把返回的消息记为 `seen`。【待确认】用户说“直接带上”，本文解读为命令支持带上选项：`--body` 一次带上全部正文，也可以对指定 UID 带上。默认不带，避免长正文一次性进入上下文。
- 带上正文的消息同时记为 `read`（【已定】）。
- `read` 是指定消息的专门读取，输出正文并记为 `read`。
- 排序：默认按 `seq`（无则按接收时间）升序。打断消息优先。
- 去重：同一会话不重复返回已 `seen` 的消息，除非 `--all`。
- 会话：【已定】@ 某成员的消息进入成员的收件箱，不指定会话。同一成员的多个会话共用收件箱，每个会话各自记 `seen/read`（`delivery` 表按会话分行）。
- 自动查收：守护进程启动或重连时，向各渠道和权威库拉取“发给我且我尚未收到”的消息（按游标），写入本机库；有未读队列消息时，状态里提示。
- 回执：`read` 向权威库上报时，逐条状态汇总成现有的高水位回执（模块 E）。

Skill 需要教会的用法（供 Skill 编写时参考）：每轮任务结束时执行一次 `otoha inbox check`；看到摘要后按需 `inbox read` 取正文；执行动作前先取正文核对。

验收：

- 分别有：只有摘要、有正文、正文需向权威库拉取、正文校验失败、重复查收、多会话各自状态。
- 无网络时 `check` 只读本机库，不报错。

## 12. 模块 K：打断消息与宿主适配

目的：管理员发出打断消息时，把摘要送进接收方 Agent 的当前会话。

依据：【已定】打断消息的摘要直接插入当前工作窗口；只有管理员能发。【待核实】其他宿主能否做到。

规则：

- 宿主适配接口：

```go
type Host interface {
    Name() string
    Capabilities() HostCaps  // CanInterruptBusy, CanQueueIdle, CanReportRead
    Deliver(ctx context.Context, session SessionRef, text string, id string) (DeliveryResult, error)
}
```

- 【建议】把现有 `codex.go`、`desktop.go` 的 steer/queue 逻辑整理成 `codex` 宿主，行为不变：忙时用 steer，空闲时用官方 queue；每条投递有日志；结果未知时先核对，不重复投递；队列接受不等于 Agent 已读。
- 其他宿主（Claude Code 等）：【待核实】先写探测脚本，确认有哪些方式（钩子、MCP、文件）能在不打扰用户的情况下把文本带入会话，再决定实现。没有验证通过的宿主，统一降级为“下一次 `otoha` 命令执行时在输出里附带提示”。
- 投递结果必须区分：`delivered_interrupt`（确实插入了当前会话）、`delivered_queued`（排在会话之后）、`degraded_hint`（降级为下次命令提示）、`failed`、`unknown`。【已定】不能把“已发出”当作“已打断”，结果写进投递记录并回传发送方。
- 摘要进入会话时使用模块 C 的包裹格式，并声明“不产生授权”。
- 打断消息不自动取正文。会话中的 Agent 需要时自行 `inbox read`，此动作记为 `read`。
- 防滥用：打断消息有每管理员频率上限；接收方可配置“勤务中不接收打断”的窗口【待确认】，默认不启用。

验收：

- 用模拟宿主测试：忙、空闲、宿主不可用、结果未知、重复投递。
- 对 codex 宿主，现有 `steer_test.go` 等测试全部通过，行为不变。
- 真实宿主的行为（Codex 桌面版等）单独记录为“真实宿主验收”，在没有人工验证前报告为“未验证”。

## 13. 模块 L：同步与离线补收

目的：成员本机库与权威库、成员与成员之间补齐缺失的消息，汇总到管理员库。

依据：【已定】CLI 下次启动时自动查找发给自己且尚未查收的消息；汇总私发消息到管理员的库由 CLI 完成。

规则：

- 同步对象：权威库（服务器或队长电脑）、其他成员的发件箱（通过渠道）。
- 增量依据：每个同步对象一个游标（权威库的 `seq`；渠道的事件位置）。游标只在数据持久化后推进。
- 补收顺序：先渠道上的待收消息（有保留期限制），再向权威库请求 `seq > 我的游标` 且我可见的消息，再向发送方请求其发件箱里未确认的消息。
- 汇总：成员 CLI 把本机库里“管理员尚未确认”的消息（自己发出的私发消息、别人发给自己的私发消息）上报给管理员库，管理员库以 `uid` 去重。【建议】上报的是信封加正文，经过已认证的通道；若只能通过 Telegram，则只上报信封，正文在管理员需要时再请求【待确认】，因为 Telegram 不适合承载大量正文。
- 应用层确认：收件方收纳后回一条小确认（`ack`，含 `uid` 和时间，签名），发件方收到后把发件箱里的记录标记为 `acked`。离线超过渠道保留期时，由发件箱重发，直到被确认或被撤销。
- 冲突：消息是追加的，不存在内容冲突；`uid` 相同而内容哈希不同视为异常，保留两份并报告，不覆盖。
- 管理员库的一致性：多个管理员时，各自汇总，互相同步；以 `uid` 合并。

验收：

- 模拟网络分区：A、B 在队长离线时互发，队长上线后管理员库补齐，无重复、无遗漏。
- 24 小时保留期过期的情形：渠道已丢，发件箱重发后仍能送达。
- 游标回退、乱序、重复到达的处理有测试。

## 14. 模块 M：守护进程与受管服务

目的：每台机器一个常驻进程，管理消息、渠道、同步，并启动图谱网页服务，支持各端热更新。

依据：【已定】每个队友在自己电脑端热更新；CLI 持续服务，Agent 方便管理。【建议】一个守护进程；扩展现有 `service`，不另起第二个 receiver。

命令：

```text
otoha daemon start|stop|restart|status|logs [--follow]
otoha daemon install|uninstall              系统服务注册（launchd/systemd/Windows 服务）
otoha graph serve [SYSTEM.json] [--port N]  启动并托管图谱网页服务
otoha graph stop|status
otoha doctor                                自检并给出下一步
```

规则：

- 守护进程只监听 `127.0.0.1`，端口写入私有目录；本机接口使用会话令牌认证（令牌存私有目录，权限 0600）。
- 自检 `doctor`：目录权限、数据库版本、各渠道连通与凭据、名册签名、运行时（Node、Python）是否存在、端口占用、时钟偏差、旧 receiver 是否存在（只报告，不处理）。每项给出“通过/警告/失败”和一句修复建议。
- 保留已有 receiver：升级和恢复不能靠启动第二个 receiver 代替。检测到旧 receiver 运行时，守护进程报告并拒绝重复接管，由用户决定迁移。
- 图谱服务：【建议】由守护进程作为子进程启动并监管，崩溃重启；退出码与日志可查。
- 热更新：守护进程拉到新的接受版本后，通过现有 `/api/events` 的服务端推送通知本机浏览器。【已定】页面采用新版本时保留选择、视角、展开状态和焦点（TapTap 的验收标准）；对现有 viewer 做验证，不满足则列为缺项报告，不在本模块里改 viewer。
- 仅 Git 渠道时靠轮询，不承诺实时。有服务器时事件推送。
- 【安全】图谱服务目前只绑定回环地址，GET 接口无认证，POST 靠会话令牌，且 `Host` 校验写死为本机。任何通过网络暴露（隧道、网关）的方案，必须先加认证并重做 `Host` 与来源校验；本轮不暴露。
- 网络可达：【建议】做成可替换的“可达性提供者”（局域网、自有中继、Tailscale、Cloudflare Tunnel、frp）。本轮只实现 `lan` 与 `none`，其余留接口。`otoha doctor` 说明当前走哪条路径。Otoha 不自己实现穿透。现有 `gateway.go`（HTTPS 反向代理，上游限回环）与路由回退逻辑可作基础。

验收：

- 杀掉子进程后被重启；守护进程重启后消息状态不丢。
- 两个守护进程（模拟两位成员）在同一台机器上用不同 `OTOHA_HOME` 运行，互不干扰。
- `doctor` 在各种缺失情形下的输出有测试。
- 图谱热更新：修改接受状态后，已打开的页面在设定延迟内收到事件；记录实际延迟和是否保留视角，结果写入报告。

## 15. 模块 N：权威状态同步（图谱）

目的：团队共享同一份接受后的图谱状态。

依据：【已定】没有服务器时队长电脑保存权威状态，队长关机期间队员的变更排队；【建议】单写者，队长（或服务器）签名发布。

规则：

- 沿用 `packages/graph/team` 的 `TeamLeader`/`TeamMember`、签名请求、字段版本冲突检测、`GitTransport`。本模块只负责让守护进程调用它们并把状态变化通知给其他模块，不改协议。
- 成员的变更请求在发件箱式的队列里等待；队长上线后处理并发布新的接受版本；成员拉取。
- 队长不在时成员读最近的接受版本，页面标明版本和获取时间。
- 【建议】按对象或字段指定负责人，使负责范围内的修改不经过队长。这是对现有字段级授权的使用方式，不改协议。【待确认】
- 与消息的连接：接受版本变化时，向相关成员发一条系统消息（`kind=status`，`from.kind=agent`，发送者为守护进程），摘要写明变化的对象和版本，引用图谱对象 ID。这条消息走模块 D 的普通流程。

验收：

- 沿用现有图谱协作测试；新增：队长离线期间成员提交变更，队长上线后发布，成员拉取到新版本；版本冲突被拒绝并有明确错误。

## 16. 模块 O：Agent 接口（命令输出契约）

目的：Agent 通过命令行使用 Otoha，输出必须稳定、简短、可解析。

规则：

- 所有命令输出 JSON，字段名稳定，版本化（`"schema": 1`）。新增字段不破坏旧解析。
- 输出体量控制：`inbox check` 默认最多返回 20 条摘要；超出时给出 `has_more` 与游标。大对象不直接输出，给引用。
- 错误输出：`{"error":{"code":"...","message":"...","retryable":true|false,"next":"建议的下一条命令"}}`。错误码英文固定，说明用中文。
- 所有会进入 Agent 上下文的外部文本（摘要、成员名、渠道名）都经过模块 C 的净化与包裹。
- 命令帮助（`--help`）简短，包含一个最常见的示例，供 Agent 在没有 Skill 时自助。
- `otoha help skill` 输出当前版本的命令速查，作为 Skill 的补充。

验收：

- 输出契约有 JSON Schema 文件，测试对每个命令的真实输出做校验。
- 大量消息时输出体量有上限的测试。

## 17. 不在本轮范围，但要预留

- 需求实例、反馈、需求、决策对象，以及与图谱的关联：需要先定最薄的一层对象模型（`kind`、稳定 ID、版本、关系），信封的 `refs` 已预留引用位置。不要在本轮实现。
- Skill 正文与模板、真实样本：另立任务。本轮只保证命令输出契约（模块 O）和 `inbox check` 的使用方式稳定。
- 紧急情况如何从普通成员上达：【待确认】见 DECISIONS 第四节，本轮只做“管理员转发”，即管理员可以对某条队列消息重新发送为打断消息，原消息 `uid` 放入 `reply_to`。
- 私发消息的加密协议：本轮不做。第一版私发只支持服务器、队长常开电脑、Telegram 机器人。

## 18. 为 App 预留

- 守护进程的本机 HTTP 接口覆盖全部 CLI 能力，路径和 JSON 与 CLI 命令一一对应，App 只是另一个客户端。
- 人发消息、@ 成员、群聊视图所需的接口（消息列表、成员列表、未读数）在模块 J 中已有数据，App 阶段补 HTTP 路由即可。
- 不要为 App 提前做界面。

## 19. 安全清单（所有模块通用）

- 私钥、令牌只在本机私有目录；日志、错误、`doctor` 输出中脱敏；测试有断言扫描日志不含令牌。
- 外部输入全部校验长度、字符、格式；信封字段白名单（拒绝未知字段，沿用 `exact()` 的做法）。
- 不执行消息里的任何内容。摘要和正文都当不可信文本。
- 路径处理防穿越；文件名由 `uid` 派生，不使用外部给定的名称。
- 签名域分离；时间戳允许合理偏差，过旧或过新的消息标记。
- 子进程调用使用参数数组，不拼接 shell 字符串。
- 依赖使用固定版本；新增依赖前说明理由，优先标准库。
- 不向第三方端点发送项目代码、密钥或用户数据。Telegram 只收发 Otoha 信封。
- 保留旧部署：任何命令不得修改旧服务的数据库、旧 receiver 的配置或真实用户状态。

## 20. 开发阶段与验收

阶段按依赖排列。每阶段结束，运行该阶段的测试和 `npm test` 中与 CLI 相关的部分，更新 DECISIONS 第四节，并提交报告：做了什么、测试结果、未验证项、需要用户决定的事项。

| 阶段 | 内容 | 前置 |
| --- | --- | --- |
| 0 | 现有代码盘点：跑通 `go build ./...` 与现有测试；列出 `internal/otoha` 各文件职责；确认旧命令全部保持原行为 | 无 |
| 1 | 模块 C 信封与签名；模块 A 身份与名册；`FakeChannel` | 0 |
| 2 | 模块 E 本机库与可见性；模块 D 发送与发件箱（只对 `FakeChannel`） | 1 |
| 3 | 模块 J 收件箱与查收；模块 O 输出契约；`inbox check` 完整可用 | 2 |
| 4 | 模块 F 渠道层；模块 G 的验证脚本与 Telegram 适配器（模拟服务器测试）；真实令牌验证由用户提供 | 2 |
| 5 | 模块 B 项目初始化与接入（队长电脑模式）；模块 L 同步与离线补收 | 3、4 |
| 6 | 模块 H 服务器模式（扩展协作服务）；模块 K 宿主适配（codex 整理 + 降级提示） | 5 |
| 7 | 模块 M 守护进程与受管服务；模块 N 图谱状态同步；热更新验证 | 5 |
| 8 | 模块 I Git 渠道；第二个社交渠道的核实与实现 | 4 |

阶段 0 到 3 不需要任何外部服务，可以完全离线开发和测试。阶段 4 的真实验证需要用户提供两个测试机器人令牌。阶段 6 的宿主验收需要用户在真实宿主上操作。

### 完成的定义

一个模块完成，需要同时满足：

1. 规格里的规则都有对应实现或明确标为未实现。
2. 验收里的每一项都有自动化测试，或者明确标为“需要人工/真实环境验证”。
3. 不破坏现有测试；旧命令行为不变。
4. 没有凭据、真实消息或运行状态进入 Git。
5. 报告里区分：已实现、测试通过、真实环境验证、用户验收，不把前者当作后者。

## 21. 待确认事项汇总

开发时按默认值实现为配置项，不要写死，并在报告里提醒用户。

1. 摘要长度上限（默认 280 字符且 ≤1000 字节）。
2. 查收时是否默认带正文（默认不带，`--body` 带上）。
3. 机器人互发循环保护的数值（默认回复深度 3）。
4. 附件与正文大小上限（默认 60000 字节内联，更大走附件对象）。
5. 消息保留策略（默认不删除）。
6. 打包方式：内嵌运行时、首次下载或迁移到 Go。
7. 现有两套身份体系合并的时机。
8. 第二个社交渠道选哪个。
9. 普通成员紧急情况的上达方式（本轮仅管理员转发）。
10. 勤务窗口内是否拒收打断消息（默认不启用）。
11. 成员消息抄送管理员（默认开启）。
12. 私发正文经 Telegram 汇总到管理员库的方式（默认只汇总信封）。
13. 按对象或字段指定负责人的使用方式。
