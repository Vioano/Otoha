# 跨项目自用与产品反馈

demonstration、需求解释／实例和开发计划网站可通过 `otoha-visualize` 复用已有 Otoha 工作页。各项目使用自己的授权团队与页面，同一话题复用入口。

## 统一存储与隔离

反馈复用部署者已有的中心和消息数据库，通过 owner 私有项目与频道隔离。团队别名、频道、身份和中心地址由私有配置提供；示例中的 `FEEDBACK_TEAM` 必须替换为已配置且获准的目标。真实配置、消息、待发和回执不进入公开仓库。

普通项目消息仍留在自己的项目和频道。无需把数据库放进 Git 工作区，不增加第二套通信服务或反馈表。反馈消息与图对象按引用关联，不强制物理同库。

## 只有明确要求才发送

用户明确要求提交 Otoha 产品或 Skills 的体验、问题或改进时，才发送指定反馈。普通报错、完成任务、读取消息和一般开发不自动写入反馈库，也不自动汇集所有聊天和日志。

只附理解问题所需的最少来源与成果引用，区分原话、Agent 解释和建议。由 Agent 转送的内容保留 Agent 来源，不冒充宿主直接采集的人类事件。

```sh
otoha message list --team FEEDBACK_TEAM
otoha message get MESSAGE_ID --team FEEDBACK_TEAM
```

下列发送命令仅适用于用户已明确授权的反馈，不作为初始化或探测：

```sh
otoha message send --team FEEDBACK_TEAM \
  --summary 'Otoha 产品反馈：具体问题' \
  --text '获准发送的反馈；另列必要上下文、复现和建议' \
  --request-id 'feedback-STABLE_ID'

otoha message status --team FEEDBACK_TEAM --request-id 'feedback-STABLE_ID'
```

未知结果沿同一请求 ID 查证，不以新 ID 重发；不向普通团队频道试发。

## 处理与核验

按需读取相关反馈原件，并关联受影响的需求、模块和改进任务。消息保存内容，图谱保存关系与采用状态，不用摘要覆盖原件。

中心接受、接收方收纳、实际阅读、接手、实现与用户验收分别记录。反馈不授予修改其他项目、公开资料或向其他人发消息的权限。配置建立、私有隔离和端到端处理须在具体部署中验证，本文不宣称某个真实入口已经配置或通过。
