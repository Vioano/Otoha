# 架构起点

本文件是基于三个旧项目源码提出的初始架构建议。它没有替代尚待补全的五条核心原则，也没有将技术栈或调度形式定为最终方案。

## 需要连接的三个部分

System Atlas 帮助人和 Agent 理解同一个系统；Team Mailbox 约定成员怎样交流与交付；Atlas CLI 把项目接入、消息接收与 Agent 会话连接起来。Otoha 的价值需要通过它们共同服务的一项真实工作来证明。

```text
人类界面                         Agent 接口
    │                               │
    └──────── 共同项目状态 ───────────┘
              │ 系统模型、任务、版本、证据
              │
        协作协议与调度策略
              │ 责任、依赖、交接、阶段变化
              │
         消息与会话适配
              │ 寻址、接收、投递、阅读回执
              │
        外部 Agent 与工程工具
              │
         结果、来源与验证
```

这是职责关系，不是已经实现的数据流，也不要求每个部分成为独立服务。

## 状态与视图

人类界面和 Agent 接口应读写同一个被接受的项目状态，避免各自维护一套进度。系统结构、独立任务、消息和执行结果具有不同语义，可以通过稳定 ID 关联，不必全部变成图节点。

原始代码、测试输出和运行结果仍是对应事实的来源。项目模型负责组织引用与版本，不能通过一次状态编辑使未经验证的结论成立。缓存、看板和图是投影，不能形成另一份需要人工同步的权威状态。

## 协作协议与调度策略

协作协议约定身份、寻址、上下文、交接和结果如何表达；调度策略决定当前阶段谁先做什么、哪些工作可以同时进行、何时重规划。传输与宿主适配负责把消息送到正确的会话。

协议应积累可复用的常用部分，并允许项目补充。策略可以随任务和阶段变化；调度形式仍待具体场景检验。负责人字段、看板列和在线会话列表都不能单独代替调度策略。

## 交付与授权

至少区分消息持久保存、交给客户端、Agent 实际阅读、接手任务、提交成果和成果验收。不同适配器可以返回不同的能力范围；不支持的阶段应明确表达。

身份认证、项目权限和用户对本次工作的授权需要分别判断。收到消息本身不增加执行范围。操作标识和持久游标用于恢复与核对；网络超时后的未知结果不能直接当作失败并重发副作用操作。

## 还需要决定的边界

- 共同项目状态如何扩展 System Atlas 的接受模型，同时容纳意图修订与协作记录。
- 首个完整场景选择哪种调度策略，以及何时允许更换策略。
- 消息后端是否沿用既有服务，还是先使用更小的本地实现。
- 首先接入哪些 Agent 宿主，以及如何在真实宿主验证忙时和空闲时的行为。

这些问题应由[首个场景](DEVELOPMENT.zh-CN.md)逐步收敛。
