# 架构起点

本文件将[五项核心哲学](PRINCIPLES.zh-CN.md)转为初始架构建议。职责划分与数据关系供后续实现检验，尚未确定技术栈、部署拓扑或接口格式。

## 围绕持续形成的需求组织系统

用户提出的目标经过对齐 Agent 与具体实例得到发展，再进入共享工程状态，供多个执行 Agent 按范围使用。开发成果回到用户面前，可能带来下一轮需求修订。因此，对齐与实例化从首个场景就需要参与；通信、图谱与调度要支持这个往返。

```text
人  ◄──────────────►  对齐 Agent
                         │     ▲
                   形成与修订  体验反馈
                         ▼     │
                      需求实例
                         │ 确认的设计与修改
                         ▼
                共享工程图谱与原始内容
                   │             ▲
              策略化读取       成果与新问题
                   ▼             │
                多个独立执行 Agent

分级通信：让通知和内容在合适时机流动
协作协议与调度策略：组织角色、依赖、交接与阶段变化
```

此图表达职责与信息关系，不表示已经实现，也不要求每个部分成为独立服务。需求实例可能由对齐 Agent 制作，也可能交给其他执行者制作。

## 五项哲学对应的职责

| 职责 | 初始设计方向 | 已有基础与待补部分 |
| --- | --- | --- |
| 分级通信 | 原件持久保存；极简摘要与引用通知；紧急读取和任务边界查收 | Atlas CLI 的接收、游标和宿主适配可参考；通知分级与读取时机仍需设计 |
| 工程图谱与策略读取 | 对象和文件关系显式存储；按职责、一阶依赖等策略生成上下文 | System Atlas 提供稳定 ID、查询和接受版本；更完整的工程关系模型待扩展 |
| 持续对齐 | 专门 Agent 长期理解人的意图，主动吸收反馈并传递需求变化 | 需要在 Otoha 新增，不能由看板或消息回执代替 |
| 需求实例化 | 用网页、场景图或小型真实实现承载判断，反馈关联具体需求 | 需要建立实例、反馈、需求与执行之间的关联 |
| 协议与自适应调度 | 规划时选择策略，复用常用协议，随阶段调整 | Team Mailbox 的协议和既有协作经验可参考；策略选择与切换待实现 |

## 共享状态与原始内容

人类界面和 Agent 接口读取同一被接受的项目状态。需求、系统模块、独立任务、决策、文档和实例通过明确关系关联。各类对象保留自身语义；共享图关系不要求把每段文字或每次界面操作都变成图节点。

完整消息和文档保存在可回查的原始内容中，图谱组织它们与工程对象的关系。查询策略负责返回相关对象、原件引用及必要的边界信息。缓存、看板和图的视觉布局是投影，不能各自形成另一套需要人工同步的决策。

原讨论中的地图版本反例提供了具体约束：把“使用哪版地图”的决定发成消息还不够，它需要成为相关 Agent 可以查询和核对的共同工程状态。将来的版本检查与任务前提失效机制是实现这一要求的设计方向。

## 对齐与实例的往返

对齐 Agent 持续接收想法和阶段反馈，将歧义转为可以判断的问题。实例负责呈现待判断的体验，反馈需要关联到实例中的对象、操作和对应需求。确认后的修改再进入工程状态，并影响相关任务。

例如，用两张图模拟冲浪游戏的转向可以先帮助判断视野和场景；真实相机运动与性能需要后续实现另行验证。实例要标明表达范围，使人能判断设计，又能分清模拟与实际能力。

## 协议、策略与适配器

协作协议约定身份、寻址、上下文读取、任务交接和结果表达；调度策略决定当前阶段怎样组织工作。轻量中心是一种候选：协调者读摘要和必要全局信息，执行者读局部细节并自主推进。策略也可以采用其他组织方式，并随阶段变化。

传输与宿主适配负责把通知交给正确会话。它们应提供实际能力范围，使策略能够利用宿主支持的忙时和空闲行为。扫描方式和频率可以替换，无需固化为整个产品的唯一工作循环。

Otoha 将兼容现有 Agent，也保留开发原生 Agent 的长期方向。MCP、插件和 Skill 提供接口与操作指引；状态管理、消息保存和协议约束需要有对应的软件实现。

## 工程基础

消息保存、客户端接收、Agent 实际阅读、接手任务、提交成果和成果验收分别表达。身份认证、项目权限和用户授权也有各自作用。网络超时后的未知结果要可核对，不能简单重发副作用操作。

接口与依赖尽量在开工前明确，开发中传播变化，集成时验证实际结果。这些支持五项哲学，不另扩张为核心特色或逐步审批流程。

## 首个实现需要收敛的问题

- 如何记录需求、实例反馈与决策，并与 System Atlas 的模块和独立任务关联。
- 先实现哪些读取策略，怎样让接收者发现相关变化而不加载整个工程。
- 第一种通信分级与任务边界读取怎样接入现有宿主。
- 第一个场景采用什么调度策略，何时及如何改变它。
