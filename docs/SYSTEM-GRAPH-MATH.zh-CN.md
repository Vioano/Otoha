# Otoha Graph：Core、Mutation、Projection 与 Template

> 2026-11-03 更新。本文是当前采用的数学模型与职责边界；具体操作协议、数据库和迁移方式仍待验证。文档更新不表示新 Core、通用 Mutation、Projection 或 Template 已经实现。

设计依据：[《构建系统图谱模型》讨论](https://chatgpt.com/g/g-p-6ad87e33003881919e41568cb06c56b8-agent-orchestration/c/6ae08392-bd88-83e8-8398-2fdaa7d9de1e)。本文整理讨论中形成的方向，区分已采用的抽象、候选操作与尚未确定的实现；不把对话中的数据库建议当作已验证的选型。

## 采用的结构与职责

Otoha Graph 采用自由 Property Graph：节点、边和属性提供通用表达能力，具体业务含义由使用它的 Agent 和可选 Template 约定。数学模型既是理解共享状态的心智模型，也是后续数据库实现和 Agent 接口的对照契约。

| 部分 | 回答的问题 | 职责边界 |
| --- | --- | --- |
| **Core** | 图状态由什么构成？ | 保存节点、边、端点和自由属性；保证结构有效，不预设业务本体 |
| **Mutation** | 图状态怎样改变？ | 定义通用修改及其前提；通过事务接受变化，不内置任务分配或失效传播 |
| **Projection** | 当前需要观察什么？ | 筛选、遍历、分组、聚合、展开和追溯；生成派生结果，不改写原图 |
| **Template** | 这些数据在某个场景下是什么意思？ | 可选的属性词汇、局部约束、查询预设和复合操作，不改变 Core 的数学结构 |

```text
Agent / 人 ──提出修改──→ Mutation ──接受提交──→ Core 中的图 Gʳ
                                                    │
                                             Projection Πθ
                                                    ▼
                                            同一份结构化投影
                                             │           │
                                         Agent 输出   Human 画布

Template 提供上述操作可选的业务约定与预设。
数据库实现存储、事务和查询；Renderer 实现布局、颜色和交互。
```

这些是职责边界，不要求分别建立四个服务。身份、权限、接受版本和回执属于共享状态管理基础设施，不由可选 Template 授予，也不必加入图的数学元组。

## 1. Core：自由 Property Graph

\[
G=(V,E,s,t,P)
\]

- `V`：有限节点集合，每个节点有稳定身份。
- `E`：有限边集合，每条边有独立身份。
- `s,t:E→V`：分别给出每条边的起点和终点。
- `P:V⊔E→Map_fin(K,D)`：给每个节点和边提供有限属性字典。`⊔` 表示节点和边的身份空间可区分；字典内的键可以缺失。

这是有向多重属性图。同一对端点允许多条边，也允许自环和一般的环；空图、空属性字典都合法。无向关系可通过双向边或 Template 约定编码，多元关系可借助中间节点表达；这些编码的解释和查询规则由使用方给出。

### 1.1 自由属性不预设业务字段

`type`、`relation`、`status`、`owner`、`weight`、`source` 都可以是普通属性。它们没有全局必填清单或固定枚举；关系名也不再是独立必需的核心函数 `τE`。例如：

```text
V = {a, b}
E = {e1, e2}
s(e1) = s(e2) = a
t(e1) = t(e2) = b

P(a)  = {"label": "接口约定"}
P(b)  = {"type": "task", "status": "doing"}
P(e1) = {"relation": "uses"}
P(e2) = {"relation": "questions", "weight": 0.8}
```

这是建模示例，不是已实现的交换格式。Core 能保存两条不同的边及其属性，但不会自行解释 `weight`，也不会因为 `status=done` 就认定产出正确、允许执行新动作或提升另一个对象的成熟度。

`D` 是实现能够可靠序列化和往返读取的值域；自由指属性名称和业务含义开放，不表示可以存储任意可执行对象。具体值类型、数值精度、大小上限和编码在接口与数据库试验中确定。缺失属性和显式 `null` 必须能够区分。

### 1.2 只保留通用结构不变量

1. 节点和边的身份可明确引用；重命名标签、改变布局不会改变身份。
2. 每条边恰有一个起点和一个终点，两个端点都在 `V` 中。
3. 属性的所有者必须存在；同一对象的同一键在一个状态中至多有一个值。
4. 属性可增、改、删；空字典有效。属性字符串不自动成为受 Core 管理的引用，例如 `"source":"a"` 的引用含义需要约定。

Core 不要求根节点、父级森林、节点必须出现在画布、统一生命周期或 DAG。需要时，由 Template 在明确范围内约束某一类关系。

图谱显式组织项目中值得共享的对象和关系，原文件保留完整内容。把代码、文档或人的判断整理进图，是建模与同步过程；Core 不会自行推断这些关系，Projection 也不能从缺失信息中生成可靠答案。

## 2. Mutation：通用状态改变

对图状态提出修改 `Δ`，定义部分状态变换：

\[
U_\Delta:\mathcal G\rightharpoonup\mathcal G,
\qquad G^{r+1}=U_\Delta(G^r).
\]

`𝒢` 是上述合法图状态的集合，`UΔ` 描述逻辑图变换。在实际接受层，只有操作前提、权限及已启用的局部约束满足时，事务才可提交；拒绝的请求不产生新接受状态。`r` 标识接受历史中的版本，属于状态管理，不是每个业务节点必须拥有的属性。

### 2.1 基本修改指令候选

下表是逻辑操作候选，不是已经发布的 CLI/API。精确参数、失败行为和版本检查粒度需与数据库试验一起定稿。

| 指令候选 | 改变的部分 | 核心前提或待定选择 |
| --- | --- | --- |
| `NODE_ADD(v)` | `V` | 创建一个没有占用的节点身份，初始属性可为空 |
| `NODE_REMOVE(v)` | `V`、该节点的属性 | 删除有关联边的节点如何处理，需明确契约；首轮建议拒绝隐式级联，显式移除关联边后再删除 |
| `EDGE_ADD(e,u,v)` | `E,s,t` | 边身份可用，两个端点存在 |
| `EDGE_REMOVE(e)` | `E,s,t`、该边的属性 | 删除明确的一条边，不删除其端点 |
| `EDGE_REWIRE(e,u,v)` | `s,t` | 候选：保留边身份、替换端点；是否采用取决于边身份语义和后端能力 |
| `PROP_SET(x,k,value)` | `P` | 对象存在，创建或覆盖一个属性值 |
| `PROP_UNSET(x,k)` | `P` | 撤去属性键，区别于把值设为 `null` |

在有限图、属性值可整体替换、允许保留边身份重连的前提下，这七类操作能表达任意两个合法 Core 状态之间的改变：先补齐目标需要的新节点，重连保留身份的边，再移除旧边、删除无关联的旧节点、添加新边，最后调整属性。它不是唯一或已证明最少的 API；也不保证每个 Template 都允许这条变换路径。

若决定端点属于不可改变的关系身份，则去掉 `EDGE_REWIRE`，改为删除旧边并创建新身份。`ASSERT/RETRACT` 可用于解释事实集合的增减，不必另做一套客户端指令。

### 2.2 修改意图、事务与提交

- **Mutation**：准备做什么修改。
- **Transaction**：一次不可分割的操作组合；读者不能看到其中一半已生效。
- **Commit**：通过检查并进入权威接受历史的变化。

业务操作如“分配 Agent”“拆分任务”“标记下游需复核”，由 Template 或上层策略翻译成通用修改。更改分组属性后，Projection 重新派生分组结果，不需要额外修改一个存储中的“聚合节点”。

### 2.3 状态管理的实施建议与边界

首轮建议沿用单一权威接受顺序：多个 Agent 可以并发提出修改，权威端依次校验和提交。不以多主复制、CRDT 或通用语义自动合并为前提。

- 请求 ID 和持久回执处理未知结果与重复提交；有条件修改保护 Agent 实际依赖的状态。
- 冲突返回目标、预期与当前值等信息，Agent 重读后重新决策；不把更新版本号后覆盖当成解决冲突。
- 写入不同属性不必然意味着意图相互独立。例如修改 `status` 的判断可能依赖另一个 Agent 刚修改的 `owner`。允许声明必要的前置条件，但不要求记录每次读取的全部上下文。
- 可交换性是分析安全重排的工具，不要求每次接受提交都证明它与所有历史操作可交换。提交时仍要检查当前结构及适用的 Template 约束。

字段或对象版本、前置条件的格式、ID 删除后复用规则、无效/重复操作的处理均待契约试验确定。数据库事务不能自动提供 Otoha 的完整版本历史、应用层回执或业务冲突判断；图事务也不包括外部文件修改、Git 提交或 Agent 已执行的动作。

## 3. Projection：按需观察同一个图

\[
\Pi_\theta(G^r)=(H,\mu_V,\mu_E,m)
\]

- `θ`：筛选、遍历、分组、聚合、展开等规则及其执行顺序。
- `H`：派生的投影图，可以比原图小，也可以包含代表多个对象的聚合节点与边。
- `μV:V_H→2^V`、`μE:E_H→2^E`：投影节点和边对应的原始成员集合，可用可继续查询的引用实现，不要求一次返回所有 ID。
- `m`：源版本、读取范围、规则、边界与完整性信息。

原图不变；投影可缓存，但不能成为另一份独立接受业务修改的权威状态。

### 3.1 第一组通用读取能力

| 操作 | 作用 | 保留的边界 |
| --- | --- | --- |
| **Filter / Traverse** | 按属性、边条件、邻域或路径选择局部范围 | 区分被选中的边和跨范围边，不把节点筛选误当成所有内部边都已返回 |
| **Group / Quotient** | 按 Property 或分组函数，将节点分区并形成聚合图 | 原始成员、跨组边和被折叠的内部边仍可追溯 |
| **Expand** | 展开聚合节点的成员与相关边 | 在同一源版本中展开，保持与外部对象的连接 |
| **Inspect** | 读取某个原始节点、边及其 Properties | 取回原始身份和内容，不用摘要替代原件 |

这些是首轮实现建议，不是永久封闭的算法列表。按 Property 分组时，缺失值和多值属性怎样处理必须由 `θ` 说明。标准商图先使用分区；重叠分组是另一种投影需求，不能未经说明当成等价类。

设两个分组为 `A,B⊆V`，跨组原始边集合为：

\[
E_{AB}=\{e\in E\mid s(e)\in A,\ t(e)\in B\}.
\]

聚合边可显示数量或保留这些边的引用。权重取和、最大值还是其他统计，由投影规则或 Template 解释，Core 不替使用者决定。

### 3.2 压缩后的结果必须能正确解释

```text
原图： A → b₁        b₂ → C    （b₁ 与 b₂ 之间没有路径）
分组：      b₁、b₂ 合并为 B
商图： A → B → C
```

商图中的路径不保证能提升为原图路径。需要精确可达性、阻塞或路径见证时，应在原图或经验证的等价表示上计算，再投影结果；成员映射本身不证明两图的全部性质等价。

查询和分页应绑定同一源版本，说明范围、被省略的边界及是否完整。分组与筛选的顺序可能改变结果，不能静默调换。存在权限过滤时，应先限定可见源数据，再聚合。

Renderer 决定布局、颜色、镜头和操作方式；Agent 输出决定结构化文本的格式。两者在相同源版本和规则下应消费同一投影结构。若用户编辑聚合对象，必须先明确原始目标与影响范围，再转换为 Mutation；不能默认广播给全部成员。

## 4. Template：可选的业务约定

Template 可以提供：

- 属性名称、值的含义及场景所需的 Schema；
- 有作用范围的约束，例如只要求某类任务前置关系无环；
- 常用查询、Projection 预设和展示配置；
- 翻译成基本 Mutation 的业务复合操作，以及另行明确启用的推导或自动化规则。

不安装 Template 仍可创建、修改和查询普通节点、边、Properties。模板中的任务、模块、Agent、证据和成熟度都使用同一 Core 表达；任务和模块可有不同业务语义，不需要成为两种不可互通的底层存储结构。

必须区分推荐写法、提交时强制校验的局部约束和会产生修改的自动化。启用某个词汇或视图不能隐式启用状态传播；自动化执行仍受真实权限和已有用户授权约束。Template 不能通过 `owner` 等属性自行授予写权限，也不能代替基础设施身份校验。

会产生图状态修改的规则也应生成 Mutation 并经过事务提交，不直接写入 Core；单纯读取或计算 Projection 不触发这种写入。

Template 的约束只作用于明确采用它的范围。组合模板时，相同属性名的含义冲突需要显式映射或报告冲突，不静默覆盖。模板格式、加载与组合协议尚未设计；先用一个小型场景约定检验边界，不以完整模板引擎或社区市场作为 Core 可用的前提。Template 也不同于可选 Skill：前者约定数据和行为，后者指导 Agent 使用软件。

例如，同一节点增加 `owner` 属性后，调度 Agent 可按负责人分组，架构 Agent 可按 `subsystem` 分组。两者不必复制节点或更换 Core；某个团队若约定任务状态，则通过其 Template 解释 `status`。

## 5. 数据库与数学契约

开发方向是优先评估并复用现成图数据库。数据库负责存储、索引、基础查询和事务能力；Otoha 明确对外 Mutation、Projection、权限、接受历史与回执的行为。图数据库已有的能力应尽量复用，缺口用小范围适配补足。

数据库产品、部署方式、属性编码及客户端接口尚未选定。先用一份小型参考图和同一组操作比较候选后端，检查：自由 Properties、多重边、自环、稳定逻辑 ID、删除/重连语义、事务和有界投影是否满足契约。完整历史和回执应按实际实现分别验收。

数学模型不要求从零开发数据库，也不要求先建设多后端框架或重新发明通用查询语言。先用一个候选实现最小闭环，再依据实际差异确定薄适配边界。JSON 可作为示例、导入导出和交换格式，长期权威存储不再默认是一份整图 JSON 文件。

2026-11-03 UTC 的[候选调研与最小试验](GRAPH-DATABASE-EVALUATION.zh-CN.md)已比较五个候选，选择 SurrealDB 继续试用；3.3.5 在 Mac 与 Linux 的同一份小样本初验通过，并确认原生重连和删除行为需要适配。这不是正式选型或通用后端迁移；上述数学契约继续独立于数据库产品。

## 6. 与已有实现的关系

跨项目组合的 2026-11-06 [候选方案](CLI-DAEMON-AND-GRAPH-SCOPE.zh-CN.md#6-b-的最小数学解释)建议让每张逻辑图继续满足本文 Core，用稳定图身份、普通引用节点、显式解析与跨图 Projection 连接它们。命名/定位在单图元组之外；不新增递归包含、全局父级森林或跨图原子事务公理。这是待实施建议，不改变本文已采用的数学基线。

本次采用的是设计基线。现有 [system.schema.json](../packages/graph/schemas/system.schema.json) 和 [校验器](../packages/graph/design/model.mjs) 仍运行原有模型：固定的架构类型、关系枚举、必填职责文本和四轴成熟度、`parent` 森林、视图、独立任务和证据集合。这些是已实现的工程模型，尚未成为可插拔 Template。

| 既有结构 | 目标归属与迁移方向 |
| --- | --- |
| 实体类型、职责、输入输出、成熟度 | Software Architecture Template 的业务属性和局部校验 |
| 固定关系 `kind` 枚举 | 普通边 Properties，由约定解释 |
| `parent` 单父无环 | 架构模板的局部关系或属性约定，不成为 Core 的全局森林 |
| 独立 `tasks` 和任务—模块关联 | Task Template 中不同角色的普通节点与边；保留任务身份及多对多关联 |
| 文件哈希、验证和运行证据 | 证据模板、核验机制及其范围；不要求每个节点绑定证据 |
| 根视图、placements、坐标和路径 | 既有 Renderer/视图配置；不再是新 Core 接受一个节点的前提 |
| 接受游标、有界查询、历史、签名变更 | 可复用的状态管理与读取基础，需要验证向自由 Properties 的泛化 |

这张表是迁移计划，不是已经完成的字段映射。既有实体、任务和证据允许使用各自的 ID 空间，导入统一图时须保留来源类别与明确映射，不能按相同字符串把不同对象合并。布局和工程含义分别保存。迁移只在独立临时状态中试验，旧文件、来源和真实接受状态保留；不自动升级协议、搬动用户数据库或放宽既有权限。

## 7. 后续需要定稿的少数问题

1. Properties 的可移植值域、编码和大小限制。
2. 端点是否属于边的固定身份；删除、缺失目标和重复操作的准确行为。
3. 事务前置条件、冲突检查粒度、接受历史与回执如何映射到候选数据库。
4. Projection 的成员引用、边界、聚合规则和分页接口。
5. 一个最小 Template 的作用范围、启用方式和约束检查位置。

以上问题先通过具体样本解决，再决定是否需要增加底层结构。实现阶段与验收见[开发计划](DEVELOPMENT.zh-CN.md)。旧的 [L0–L6 草稿](SYSTEM-GRAPH-MATH-v2-minimal.zh-CN.md) 和[早期提案存档说明](SYSTEM-GRAPH-MATH-v1-proposal.zh-CN.md) 仅供回溯，不再定义当前 Core；旧讲解网页的七层路线也不再作为实现顺序。
