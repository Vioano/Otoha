# 首次链接到全队可用：验证记录

2026-11-07。验收标准见[五分钟接入体验](ONBOARDING-EXPERIENCE.zh-CN.md)。以下只报告实际样本，不代表所有模型、平台和网络均已通过。

## A：RC1，未通过

候选：`0.1.0-alpha.3-rc.1`，冻结源提交 `e971eb9bcfea7145fe6b91d24c86d6c645268d88`。两台不同的 Linux x86_64 主机、新建普通账号、独立且没有 Otoha 的 Home。队长在没有公开团队入口的私有机器运行中心；队友在默认中继所在的另一台公网虚拟机以隔离普通账号接入，仍通过真实 HTTPS 路径访问中心；不代表第三处网络或双端均在家庭 NAT 后的测试。系统已有 Git、curl、tar 和 user systemd。未预装 Otoha、frpc、SurrealDB 或中心运行时。

队长与队友分别使用全新 `deepseek/deepseek-flash` 会话，provider metadata 为 DeepSeek V4.1 Flash，关闭思考；禁用额外 Skill、MCP、作者上下文和已有模型会话。队长最初只收到产品 GitHub 链接与普通协作意图。队友通过模拟转交工具取得队长真实生成的个人邀请；没有作者补命令。问题回答和及时转交由程序模拟，不能等同真实人类可用性测试。

**结果：FAIL。** 独立验收只完成 19 项中的 9 项：双方身份和角色、常驻服务、真实 HTTPS 前缀访问、仓库 checkout 及相同团队绑定。没有观察到这些操作失败，但其余 10 项图谱双向读写、正文、Git 推送读回和权限拒绝检查未能在剩余时间完成，全部保持未验证，不能用进程存在或 join ready 替代。

耗时原因：队长两次固定等待 45 秒和 60 秒；第二次等待期间确认消息已到，造成约 47 秒额外滞后。之后继续重复已成功的诊断和仓库探测。测试装置还存在两项局限：Home 位于临时目录，引出了模型询问迁移位置；模拟人对任选扩展验证、打开页面等问句仍重复团队事实，未贴合问意，导致队友继续额外检查。这些时间保留在首次总耗时内，不倒扣后改判通过。

原始时间线、模型输出、模拟人回答、命令、公开下载 URL、邀请内容哈希与独立检查保存在私有测试证据中，未将邀请、token 或完整 profile 放入公开仓库。

## B：RC2，未通过

候选：`0.1.0-alpha.3-rc.2`，冻结源提交 `8ef3ba7d58dce7e87a085a36ae1a0a73fa6ef7ae`。同样两台主机，重新创建普通 `/home` 下的两个账号，没有 Otoha 或下载缓存，使用另一组虚构姓名。两模型仍是全新 DeepSeek Flash 会话、thinking 设置 off，工具、权限、及时转交方式和 19 项独立检查不变。

主要根因：已有双向确认后，队长仍修改 README 并推送，要求队友再拉取和回执；已经结束的外部 Agent 不会仅因新 Otoha 消息自动再次处理，队长一直等到截止。只改文字指引不能提供足够明确的产品终点。

测试装置也发现一处实际错误：对报告整篇匹配“请…确认”，把引用的队长原话误当成向人提问，重复事实后引出约 14.85 秒额外复查。该耗时保留，不能从成绩扣除。另发现旧 settled 标志在同一 peer 收到新材料时未立即清除的风险；本轮没有提前启动验收，但后续装置修复它并增加回归测试。原脚本快照、结果和复盘均保留。

## C：RC3，待测

RC3 将四项本机资源检查的提交和全员初始化等待放进 CLI：成员成功接入后提交自己的检查报告，队长通过 `team wait` 得到预期成员的明确检查结果。报告注明来源、自报性质和 `user_accepted: false`；它不替代独立操作验收，也不冒充仍然在线或人类验收。初始化不再要求 Agent 自行创造多轮消息、README 推拉回执来决定何时结束。
