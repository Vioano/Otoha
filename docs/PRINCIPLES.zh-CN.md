# Otoha：五项核心哲学

Otoha 面向长期、复杂、跨 Session、跨设备、跨成员和跨 Agent 框架的工程协作。它要让独立工作的 Agent 保持自主性，又能围绕共同的工程状态和持续发展的人的意图协作。

本文根据[《设计多 Agent 基础设施》完整讨论](https://chatgpt.com/g/g-p-6ad87e33003881919e41568cb06c56b8-agent-orchestration/c/6ad849b5-8cdc-83e8-953a-b5aa5c9528d4)整理，于 2026-10-24 回读前面的逐项讨论、具体例子及后续修正。下文是设计依据的整理，不是逐字稿，也不是已实现的功能清单；对话可能需要原账号权限才能访问。各项保留用户明确提出的目标、机制和例子，实现方案仍可继续发展。

## 1. 分级异步通信：保护 Agent 的注意力

**把通知与内容分开，让接收方按紧急程度和当前任务决定何时读取。**

这一点来自实际带队开发的体验。少量 Session 由一个 Session 协调时，原生互发消息很方便；扩展到十几个、二十多个 Session，尤其跨设备和队友后，大量消息容易变乱。Agent 还可能被中途到达的不相关内容打断。这里的 Session 数量是用户的经验描述，不是适用于所有系统的性能阈值。

用户提出的方案保留通信，但改变信息流动方式：完整内容先存入共享数据库或共享存储；跨 Agent 的通知只携带极简摘要和引用。最初设想的摘要是一句话以内，引用可以是原文链接或用于取回内容的查询表达。接收方自行取得完整原件，不经过多个 Agent 层层转述，也不把发送方的整段上下文直接灌入当前工作。

读取有两种典型时机。紧急消息可以触发立即查看原件；不紧急、但属于接收方职责范围的消息先留在共享存储，等当前任务完成或到达合适边界时再扫描和处理。例如，B 有一项需要 A 后续处理的更新，先持久保存给 A；A 完成手头工作后查收，无需为了这项更新中断当前任务。

扫描放在现有 Agent 的工作循环、外部接收进程，还是 Otoha 原生能力中，并不是这条原则的核心。用户明确允许借用已有实现，也提出扫描策略本身可以被调度：不同 Session 可以采用不同频率，空闲后可以停止扫描或转为间隔扫描。具体时机、频率和优先级规则需要随任务调整。

通信还必须与工程状态连接。原始讨论中的反例是：已经发出了“使用指定版本地图”的信息，另一个 Session 开发时却仍用了自己搭建的另一版地图。消息发出并不保证执行依据一致。因此，第一项负责让信息适时流动，第二项负责让决策有独立于聊天记忆的共同来源。

## 2. 全局工程图谱：策略化读取上下文

**完整组织全局工程知识，用可复用策略生成各 Agent 所需的局部上下文。**

用户把“策略化读取”称为这一方向的精髓：全局权威状态可能非常长，但并不是每个 Agent 都需要读完整份。系统保存全局，执行者按职责和当前任务读取适当范围；全局一致与共享全部上下文是两回事。

工程信息需要显式的图关系。需求、模块、任务、依赖、决策及文档不能只散落为一堆 Markdown 文件。文件仍可保留完整内容，但共享存储或数据库要表达它们之间的关系，使系统能够按关系查询。单纯把文件放进 `docs/`，再要求 Agent 自己每次重新推断关系，没有兑现这个构想。

读取策略应积累为常备能力。例如，读取与自己最相关的对象，或读取某个对象及其一阶依赖。用户设想以数据库语句或脚本表达这些高频策略，每种策略具有明确的读取含义，能够复用，并可按新任务增加。重点是把“怎样读”做成基础设施能力，减少每个 Session 临时拼上下文的成本。

图谱同时提供共同的决策定位。沿用地图例子，Agent 应能找到当前被认可的地图版本、它与自己任务的关系，以及后续修改对自己的影响。全局图谱由此既服务于定位，也服务于跨 Session 的共同理解。

这一要求确定了显式图关系与策略查询的方向，但没有决定数据库产品、查询语言或存储引擎。Otoha Graph 的稳定 ID、共享接受模型和有界查询是可复用基础；Otoha 如何扩展为更完整的工程图谱，仍需实现与检验。具体设计应说明版本、读取范围与被省略的边界关系，让局部读取仍有可靠上下文。

## 3. 持续人机对齐：动态演化需求

**让专门的对齐 Agent 在开发全过程中持续理解、确认和更新人的意图。**

用户最初明确提出，开一个专门的 Agent Session 负责需求对齐。它通过主动提问、选择题和前端网页展示，发现长提示词中仍存在的隐含前提和歧义，再把得到的理解传递给其他 Agent。执行 Agent 之间也要围绕这个理解持续对齐。

对齐不能在项目启动时做完。用户随后强调，人很少能凭空构想出完整的产品形态；很多功能是在开发中突然想到的，很多决定是在看到阶段成果后改变的。因此，对齐 Agent 要主动、持续地邀请人反馈，不能只等用户自己想起来补充需求。新需求可能是探索中形成的，不能一概归因于最初表达不清。

单靠终端或聊天窗口中的文字仍然不够。用户希望通过更多模态进行交流，尤其是可以直接操作的网页。图、HTML 和 SVG 可以帮助说明，但进一步的目标是让人操作和体验，然后就具体结果反馈。提问也可以细到区分“功能正确但美术不对”和“风格合适但交互需要修改”，从而定位偏差发生在哪里。

这与第四项紧密联系，但仍是两个研究对象：持续对齐负责人的意图如何被理解和修正；需求实例化负责把什么放到人面前，使其能够有效判断。

用户认为这一方向具有长期价值，因为模型越来越会猜测意图，并不意味着人能在一开始就把复杂项目想得面面俱到。这是对 Otoha 研究方向的判断，不是对未来模型能力的实证结论。专门对齐的职责应被保留；提问节奏、交互载体和具体 Session 组织可以继续改进。

## 4. 需求实例化：先体验，再实现

**尽早把抽象想法变成低成本、可操作、可评价的实例，用体验指导后续开发。**

用户给出的第一个例子是网站。先做出像样的页面和主要体验，不必先开发所有真实功能；可以用页面上的覆盖提示说明“点击这里预期出现什么”，让人直接判断并指出修改。功能和视觉风格可以分别询问，反馈应落到具体对象与操作上。

第二个例子是海上冲浪游戏。此时可以先不决定 Godot、Unity 或其他引擎，先用网页展示海水颜色、模型形态和操作路径。昂贵的 3D 场景暂时不完整搭建：先用生图展示向前走会看到的场景，再用另一张图展示向左转后的场景。两张类似连环画的场景图加上交互，就能帮助开发者判断预期效果；连续的真实 3D 转头和模型制作留到后面。

这个例子的关键是，实例可以在技术实现之前承载足够具体的体验。它不需要为了表达某个设计就先支付正式实现的全部成本。选择何种载体，取决于它能否让人判断当前最重要的未知问题：可能是网页、场景图、模拟交互，也可能是很小的真实可运行实现。

实例化要指导开发。人在实例上指出的颜色、场景、交互或行为修改，应返回到共同需求，并成为执行 Agent 可以查阅的依据。原型、反馈和开发不能成为三套彼此断开的材料。新的阶段成果又会触发新的理解与实例，形成持续往返。

实例仍要说明所表达的范围。两张图能帮助判断转向后想看到什么，不能证明实际 3D 运动、性能或物理行为已经成立。只有实例足以表达当前问题时，低成本近似才有价值。

## 5. 协议驱动的自适应协作与调度

**在规划时明确协调策略，复用常用协议，并允许组织方式随任务和项目阶段演化。**

这一项在讨论中经历了重要修正。早期方案保留轻量中心：调度 Agent 只读摘要和必要全局信息，负责协调，不亲自写程序，也不承担阅读大量详细文档的负担。简单任务可以由对齐 Agent 同时协调，复杂任务按需另设调度 Agent。这样，希望理解人的职责不会被大量执行细节挤占，执行 Agent 又保有自主性。

用户后来明确澄清，轻量中心化未必最优，不同任务适合的调度方式可能不同。真正要坚持的是“至少得有一种调度策略”。从实际体验看，完全没有策略的多 Agent 协作会很混乱；因此，前期规划就要有构造协调策略的意识，并考虑做到后续阶段时怎样改变它。

调度策略需要回答当前工作的实际问题：角色怎样分工、依赖如何衔接、哪些工作可以并行、信息如何交接，以及遇到变化时怎样调整。轻量中心、分层协作或更分布式的组织方式都可作为候选。原来的轻量中心方案应保留为可研究的策略，而非所有工程必须遵循的固定拓扑。

用户还提出，不要每次临时任务都重新搭建一整套协议。经常出现的通信、任务交接、上下文读取和接口协作约定，应积累为通用基础；具体开发只需对现有协议修改、组合或增加。协议的可复用性降低的是每次启动和调整协作时的协调成本。

协议与策略相互配合：协议提供可以重复使用的协作语义，策略决定在当前任务和阶段如何组织它们。具体协议库、运行时检查和策略切换机制，需要在后续开发中逐项设计，而不是仅凭哲学表述就声称已经存在。

## 五项之间的关系与长期定位

第一、第二、第五项组织独立 Agent 之间的信息、共同认知和协作方式；第三、第四项让人能在创造过程中不断形成与校准想法。这五项需要共同作用。例如，一次实例体验改变了地图需求，对齐 Agent 将改变整理为共同决策，相关执行者按图谱关系取得更新，通知和调度再决定何时调整各自工作。

Otoha 的长期方向也包含开发自己的原生 Agent，同时兼容 Codex、Claude Code 等已有 Agent。插件、MCP 和 Skill 是接入和操作说明的形式；用户在最初讨论中明确说，Skill 不是系统本体。系统的核心能力需要由实际软件提供，不能只靠一组说明文档构成。

Otoha Graph、Otoha CLI 和 Otoha Mailbox 是继续开发的代码与经验基础；新项目名称统一为 Otoha。已有实现、待开发能力与具体架构建议分别见[复用记录](FOUNDATIONS.zh-CN.md)、[架构起点](ARCHITECTURE.zh-CN.md)和[开发起点](DEVELOPMENT.zh-CN.md)。

## 工程基础与五项特色的边界

讨论曾尝试把验证、合并、冲突预防与一致性保障列为第六项。用户最后明确判断，这些更像日常开发习惯，前五项更重要、更独立，因此没有把候选第六项保留为核心特色。

相关要求仍应执行：开工前优先明确接口和通用协议，Agent 主动处理用户不熟悉的技术细节，并就影响产品与协作的重要选择与人对齐；开发中同步变化，最后进行集成验证。它们是实现五项哲学所需的工程基础，不应取代五项本身，也不应扩张为每一步都需要人审批的流程。
