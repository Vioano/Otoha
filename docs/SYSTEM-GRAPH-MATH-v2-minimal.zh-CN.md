# Otoha 系统图谱：从最小图开始

> 状态：设计建议，正在迭代。本文先定义最基本的图，再逐步加入只有在真实需求中证明必要的结构。上一轮提案的存档说明见 [SYSTEM-GRAPH-MATH-v1-proposal.zh-CN.md](SYSTEM-GRAPH-MATH-v1-proposal.zh-CN.md)；旧版讲解网页保存在 `system-graph-explainer-v1.html`。

## 1. 先把“图”说清楚

最小的图只有两类东西：

- **节点**：我们想谈论的对象。
- **边**：两个节点之间存在某种关系。

因此第一步只写成：

\[
G_0=(V,E)
\]

其中 `V` 是节点集合，`E` 是边集合。若先采用最简单的无向简单图，则：

\[
E\subseteq\{\{u,v\}\mid u,v\in V,\ u\ne v\}.
\]

这句话只保证三件事：节点存在，边连接两个节点，同一对节点最多有一条边。它还没有规定：

- 节点是需求、模块还是任务；
- 边有没有方向；
- 边代表依赖、实现还是反馈；
- 节点和边有什么属性；
- 图怎样分版本、怎样显示、怎样绑定证据。

这些都先不放进 `G₀`。这样我们不会把当前的工程习惯误写成数学必然性。

## 2. 用一个小例子理解 `G₀`

先只画四个节点：

```text
V = {需求, 预览, 反馈, 模块}
E = {{需求, 预览}, {预览, 反馈}, {反馈, 模块}}
```

此时我们只能说：这些对象之间有连接。我们还不能说“需求产生预览”或“反馈改变模块”，因为那需要方向和关系含义。

这一步的用途很小，但很重要：它让我们先检查对象是否应该放进同一张图，以及哪些对象之间确实需要表达联系。

## 3. 逐步增加结构

每次扩展只回答一个新问题。扩展不是默认开启的能力；如果一个真实场景不需要它，就停在更简单的层级。

### L0：节点与边

\[
G_0=(V,E)
\]

能回答：哪些对象相连？某个节点有哪些邻居？

不能回答：关系方向、关系种类、层级和属性。

### L1：边有方向

如果需要区分“需求影响预览”和“预览影响需求”，给每条边增加有序端点：

\[
G_1=(V,E,s,t),\qquad s,t:E\to V.
\]

` s(e) ` 是起点，` t(e) ` 是终点。此时一条边可以表示 `需求 → 预览`。

方向只在业务语义需要时加入。它不自动表示时间顺序、运行时因果或任务完成。

### L2：边有关系名

如果同一对节点之间可能有不同含义，增加关系名函数：

\[
G_2=(V,E,s,t,\tau_E),\qquad \tau_E:E\to T_E.
\]

例如：

```text
需求 --instantiates--> 预览
预览 --responds_to--> 反馈
模块 --implements--> 需求
```

此时 `T_E` 只是项目声明的一组名字。第一版不预设完整词表；只有当某个关系要被查询、校验或跨人复用时，才把它纳入共享词表。

### L3：节点也可以有类别

如果需要区分对象的基本角色，增加节点类别函数：

\[
\tau_V:V\to T_V.
\]

例如 `需求` 可以属于 `requirement`，`模块` 可以属于 `module`。类别首先是一个帮助解释和筛选的标记，不自动带来额外约束。

只有当某种类别反复需要相同规则时，才为它增加约束。例如，`implements` 的起点必须是 `module`。这属于下一层，不由类别名称自动推导。

### L4：属性

当节点或边需要携带文字、时间、外部引用等信息时，再增加部分属性映射：

\[
A:(V\cup E)\times K\rightharpoonup Val.
\]

`A(x,k)` 未定义表示没有这个属性；它不等于空字符串。属性可以先作为展示信息存在，只有需要稳定查询或校验时才为属性声明值域。

第一批可考虑的属性很少：`label`、`description`、`created_at`、`external_ref`。暂不引入成熟度、证据、权限或负责人字段，除非真实任务证明它们必须成为图的语义。

### L5：特定约束

当某种关系反复需要结构保证时，才为它声明约束。比如把 `contains` 作为一种关系，并要求：

- 每个节点最多一个父节点；
- `contains` 不能形成环。

这两个条件只适用于 `contains`，不能推广到所有边。`depends_on` 是否允许环，应该由具体使用场景决定。

### L6：视图和证据

最后才处理两个工程问题：

- **视图**：从图中选择一部分节点和边并安排布局。视图是投影，不改变 `G`。
- **证据与版本**：记录某个对象或属性来自哪里、在什么版本被接受。它们帮助维护工程状态，但不属于最小图的定义。

这一步可以使用现有 Otoha Graph 的接受游标、来源哈希和有界查询；它们是工程实现层，不应反过来定义“图是什么”。

## 4. 当前暂定的最小核心

为了开始真实试验，当前只暂定下面这个核心：

```text
G = (V, E, s, t, τE)
```

也就是：节点、带方向的边，以及边的关系名。暂不固定：

- 节点类型的完整清单；
- 属性清单；
- `contains`、`depends_on` 等关系的全局约束；
- 证据、成熟度、权限和版本字段；
- 某一种存储格式或数据库。

之所以暂定到 `τE`，是因为 Otoha 的核心任务不是只知道“连没连”，而是要区分“实现”“反馈”“交接”等关系。节点类别和属性仍然可以先放在项目数据或视图层，等出现重复规则后再提升为模型的一部分。

## 5. 加入一个要素前，先问三个问题

任何新结构都先通过这三个问题：

1. **它表达了最小图无法表达的哪一个具体事实？**
2. **这个事实是否会被两个以上的查询、校验或协作场景重复使用？**
3. **如果暂时不加入它，哪一个真实操作会失败？**

只有第三个问题有明确失败案例时，才进入下一层设计。新增结构还要写出一个反例，说明不加它会产生什么歧义。

## 6. 当前样本怎样映射

同一个“需求→实例→反馈→模块”的样本，在不同层级表达不同信息：

```text
L0  需求 —— 预览 —— 反馈 —— 模块
L1  需求 → 预览 → 反馈 → 模块
L2  需求 --instantiates--> 预览
    预览 --responds_to--> 反馈
    模块 --implements--> 需求
L3  为节点增加 requirement / instance / feedback / module 类别
L4  再为需要查询的对象增加少量属性
```

每一层都能独立讨论和测试。高层表达失败时，可以退回低层，而不是通过增加更多字段掩盖概念没有说清楚。

## 7. 与现有实现的关系

当前 `packages/graph/schemas/system.schema.json` 面向带布局的 `system` 渲染 IR，包含实体、关系、视图、证据和任务等字段。它可以继续用于展示和兼容旧样本，但暂时不把它当作数学定义。

下一步应先做一个很小的 canonical 样本，只包含 `V`、`E`、端点和关系名，并用它验证：

- 人和 Agent 能否得到相同的邻居和路径；
- 不同视图是否仍引用同一节点 ID；
- 增加或删除布局是否不改变语义图；
- 关系名不足时，具体哪一个场景会失败。

验证这些问题之后，再决定是否加入节点类型、属性和约束。数学定义、存储 Schema、渲染 IR 和查询 API 继续保持可分离。

## 8. 当前未决问题

- 基础图是否必须一开始就有方向，还是从无向图开始再升级？
- 是否需要允许自环和多重边？如果需要，最小结构应从简单图升级到带边 ID 的端点函数。
- 关系名是否足够，还是需要关系的属性？
- 节点类别是共享语义，还是仅仅是筛选标签？
- 哪一个真实场景会迫使我们加入属性或约束？

这些问题留给后续样本和你的具体要求回答，不在当前版本预先决定。
