## 一、用户明确提出的方向

### 范围与形态

- 现阶段只做基础设施层，不开发自主 Agent 产品。限制不要过严，核心约定保持精简。
- 2026-10-26 03:20:46 用户明确“开放一个CLI让他们下载，然后skill是选择性下载的”（Codex《通信做好了吗？》，P01，详见[出处](REQUIREMENTS-STATE.zh-CN.md)）。提供可下载 Otoha CLI，Skill 可选，CLI 使用不以安装 Skill 为前提；原生测试版的发行范围见[0.1 发行说明](RELEASE-0.1.zh-CN.md)；独立 Skill 分发方式仍待完成。
- 此前提出 CLI 加 App（GUI）、两者功能镜像及原生 Agent 的方向。2026-11-01 用户在[《邀请开发者合作撰写》](https://chatgpt.com/c/6ae7507f-0398-83e8-a148-046dfe137f2b)明确“目前没有开发成类似 coding agent 的计划”；当前聚焦可靠通信、底层调度和兼容现有 Agent。App 与原生 Agent 保留为历史/后续背景，不作为当前交付承诺。
- 使用者通过自己的 Agent 操作 Otoha CLI。仓库、消息、图谱和工作页属于同一个 Otoha 项目管理，共用项目身份与权限依据；软件发现并连接相应资源，不能让人或 Agent 手工拼接产品。这不要求物理同库、同进程或单仓库。
- Skill 教 Agent 操作 CLI、提供方法和模板，属于可选配套。MCP 留到以后。

### 常驻服务、简单操作与恢复（2026-11-06）

- 长期目标是成为团队与企业可默认使用的基础设施，降低环境搭建、反复开会对齐、格式转换、工作群转述和调度的成本。效率提升是待验证目标；首版用完整的小协作流程检验，不能只统计渠道数量。
- 入口目标是队长只发 GitHub/官网链接，成员把裸链接交给常用 Agent 后，自行发现安装、接入和工作路径，不绑定宿主，也不以 Skill 为前提。具体私有项目由已有仓库上下文或精简邀请确定；公共产品链接不凭空授予项目身份。
- 持续对齐应让相关信息在需要时自然呈现，减少每人承担的注意力、人工转述和格式转换。后续修订仍能改变共同依据，不要求人第一次就完整说明所有需求。
- CLI 启动并控制常驻后台服务，统一承担通信、系统图谱和本地网页服务。正常时安静运行，操作要快，长期运行可靠，CPU 与内存占用合理；具体门槛以实测确定。
- 人可以通过现有 Codex、Claude 等 Agent 产品的语音会话指挥，由该会话调用 Otoha 更新本地网页、呈现工作和读取反馈。Otoha 不开发语音 Agent，不绑定一种调度策略；实际接入取决于宿主会话能否调用 CLI 或等效工具。
- 人类界面与 Agent 接口都要简单、自明。连接、恢复和协议处理的复杂性由软件承担，不能要求人或 LLM 反复手动接线、阅读长规则才能操作。
- 队长只给短凭据或精简文件。接入时长、操作数和首轮成功率是硬指标；用新的、干净的轻量模型会话盲测首次理解和加入，不用已熟悉实现的作者会话代替。具体目标值与样本量尚未定，不能把命令存在或单次成功写成接入效率已达标。
- 工作页只规定后台发布、实时热更新和全队同步能力；不限制布局或网页形态。Otoha Graph 是一种可选模板，不是工作页的必需外壳。现有 HTML 能力和最终同步体验分别核对，不能用一个固定样本代表全部产品形态。
- 一键接入私有仓库和自部署中心是 CLI 的核心功能。中心可以是自有服务器、租用服务器或队长电脑；管理员首次配置与普通成员加入分别设计。
- 队长电脑重启后自动续接，沿用身份、项目、游标和待发内容，不需要重新邀请。离线图修改作为待提交意图保存，不等于共享状态已接受；消息渠道可用不等于图谱权威在线。
- 私有 Gitea 承载私有项目和高频 AI 协作；GitHub 发布整理后有明确意义的公开更新。私有仓库不自动提供成员间私发隔离，Git 提交不替代消息读取或图谱接受回执。
- “让团队效率翻倍”是目标，尚无量化验证。以减少人工转述、接入排错、上下文重建和返工作为真实场景的观察依据。

功能边界、跨项目图谱候选和两机验收建议见[CLI、常驻服务与跨项目图谱](CLI-DAEMON-AND-GRAPH-SCOPE.zh-CN.md)。其中用户要求按本节记录；候选架构与命令细节仍属于实施建议。

### 团队接入流程

下面保留原流程结果，接入材料按 2026-11-06 的精简要求收敛，不把原“接入包”固化为长文件和手工接线。

1. 队长告诉自己的 Agent：用 GitHub、GitLab 还是自建服务器，要开发什么产品，哪些成员接入。
2. Agent 通过 CLI 建立统一项目并生成短凭据或精简文件，补问必要的缺项；使用者选择安装 Skill 时，按需读取其中指引。
3. 队长通过其他渠道把这份接入材料交给队友。
4. 队友对自己的 Agent 说要接入该项目，Agent 操作 CLI 完成接入。
5. 之后各成员本机同步，页面热更新。App 手动接入保留为后续背景，不作为当前 CLI 接入前提。

### 部署方式

以下是既有决定记录；最新消息继续要求服务器优先、队长电脑和无独立服务器路径可用，没有否定这些模式。准确副本与接受边界仍按[通信契约](COMMUNICATION-CONTRACT.zh-CN.md)核清。

- 队长可以搭独立常驻服务器，也可以只用自己的电脑（可能关机），也可以使用 GitHub、GitLab 或自建 Gitea。
- 没有服务器、也不用 Git 托管时：队长电脑保存权威状态。队长关机期间，队员的变更排队，等队长上线后处理。

### 通信

本节保留旧文档记录为用户已定的通信边界。库位置、两类权限、多管理员、本机明文副本、离线互发与汇总的最初用户原话，本轮在可见 ChatGPT 消息及已定位早期 Codex 来源中仍未补到；保留决定地位并明确取证缺口，不把它们改成新的自由选项。2026-11-06 用户要求核清这些关系，并直接重申摘要/本体分离、紧急 `steer`、非紧急 `queue` 或主动扫描。

- 通信渠道与消息数据库解耦。GitHub、GitLab、中心服务器、Telegram 等都只是渠道。
- 权威消息库的位置在初始化时由队长选择：队长电脑，或服务器。队长（或服务器）保存完整库。
- 权限先只分两种。管理员的库是完整的，包含所有消息；可以有多个管理员，一般由队长担任。普通成员只能看到公共消息，以及自己发出和别人发给自己的消息。更精细的权限管理以后再做。
- 每个成员本机的消息库明文存储，只有本人能读取，不做静态加密。普通成员的库只含自己可见的部分。
- 消息库与渠道是两层，可自由组合，渠道可同时配置多个。CLI 把两层包起来：对上提供统一命令，对下对接各种库位置和渠道，更换其中一层不改协议和 Skill。
- 队长关机时，成员之间仍然可以互发消息，建议用 Telegram 一类机器人作为渠道。CLI 把渠道收到的消息写入本机库。直接发给对方机器人的消息不加密。
- 私发消息的汇总由 CLI 完成，不由 Telegram 完成：各成员的 CLI 把本机库中的消息汇总到管理员的库，管理员因此能看到全部消息。
- 收件方离线或 CLI 未运行时错过的消息，在 CLI 下次启动时自动查找发给自己且尚未查收的消息，并及时查收。
- 加密只在经过公共信道传消息时才需要。使用私有中心化服务器时，服务器保存权威完整库，服务器上的 CLI 负责把消息只发给应该收到的人。
- 第一版的私发消息只支持三种情况：私有中心化服务器、队长常开的电脑、Telegram 一类机器人。GitHub 这类公共平台只承载公共内容，不支持私发消息，也暂不开发加密协议。团队协作中私发消息很少用，不值得为它先做一套加密协议。
- 渠道是可选项，不绑定 Telegram。初始化时由用户选择要启用的渠道，可同时启用多个，之后可以增减。参考 Hermes 的做法：每个渠道是一个插件，清单声明名称、所需配置项（是否机密）、可选配置项，由命令行向导按清单逐项询问。
- 除 Telegram 外还需要支持其他渠道，供没有 Telegram 的成员使用。不考虑成员完全没有任何社交媒体的情况。实现顺序：先做 Telegram，并优先做机器人之间可以互相通信的方式，其他渠道随后。

### 人与 Agent 的消息

摘要/正文细则、管理员打断权、人的 @ 路由等沿用旧决定记录，原话补证边界同上。下文“进入上下文”指通知阶段；Agent 主动取出的正文仍会进入其读取上下文。传输、存储和注意力窗口是三个不同边界。

- 消息发送者分两类：Agent 和人。人可以通过 CLI 或 App 发消息，走与 Agent 相同的通信通道，两者在消息里必须能区分。
- Agent 发消息必须遵循固定格式，写明是哪位成员的哪个 Agent 的哪个会话发出的。
- 人的消息形态类似聊天群：可以群发、私发，也可以在群里 @ 某人。整体像一个轻量的办公软件。
- 通信的主要使用者是 Agent，目标是自动化和高效率。人使用聊天的机会较少，这部分只做轻量，不做复杂。
- 开发顺序：先完成 CLI，App 之后再做。
- 消息先写入数据库，再让 Agent 读取。Agent 之间只发摘要和索引（引用、链接或查询），完整内容在数据库里。
- 一条消息分为完整正文和摘要两部分。通知阶段进入 Agent 上下文的只有摘要：一句话概括，加固定格式的字段（时间、来源等）和引用。正文留在库里，Agent 需要时再取；取正文不依赖其他 Agent 层层转述。
- 摘要和正文随同一条消息一起经渠道传递，不分开传，这是旧记录的传输约定，不是允许将完整 payload 注入 Session。摘要与正文的拆分和解析由 CLI 完成。经 CLI 之后，非紧急消息等待 `queue` 或主动查收；紧急消息只把摘要与引用交给支持相应能力的宿主。
- 发送流程：Agent 通过 CLI 发消息，只提供摘要和完整正文。时间、来源（成员、Agent、会话）、消息类型等固定字段由 CLI 自动补上，之后的封装、投递、重试都由 CLI 负责。
- 接收流程：CLI 收到消息后拆成摘要和正文，先收纳完整消息。紧急通知通过宿主支持的 `steer` 请求进入当前执行；非紧急通知使用 `queue`，或等 Agent 到任务边界主动查收。实际窗口效果按宿主验证，不能把软件收到或宿主接口接受直接写成已阅读。
- “摘要”和“正文”是便于描述的简称，同一条消息的两部分在不同使用者眼里叫法不同：Agent 这边是摘要和正文，人这边是聊天的话和附件。正文可以为空，只有摘要的消息是合法的，类似只写了邮件标题的邮件。
- 人发消息时，默认把输入的话当作摘要，正文作为可选附件，符合人在聊天软件里的习惯。
- 查收命令可以选择同时带上正文。带上正文的那些消息，同时记为“已读”。
- 读取分两种。队列消息是默认类型：留在库里，由宿主安排后续输入或接收方在任务边界主动扫描属于自己的消息，公共消息同理。紧急消息经宿主支持的打断路径送摘要与引用，接收方再查原文。“队列消息”是用户暂定的称呼，“打断消息”是本文暂用的对应称呼，二者可改；Otoha 消息队列与宿主 `queue` 接口不是同一层次。
- 发送打断消息需要管理员权限，通常由队长使用。普通成员只能发队列消息。人在群里 @ 某个成员的消息默认也是队列消息，进入该成员的收件箱，由其 Agent 在下次查收时看到，再决定交给哪个会话。
- 不用 Issue 做高频通信。旧 Team Mailbox 频繁提 Issue，有触发 GitHub 封控的风险。使用 GitHub 一类平台时，改为提交专用的交流文件变更，对方拉取后解析。这类平台只承载公共内容。
- 自建服务器可以直接搭中心化通信服务。
- Telegram（以及 Discord 等）可以作为通知渠道。设想为一个常驻网关，一个 Bot Token 服务本机所有 Agent 会话，统一收发、解析、路由，并在脚本层限流。参考 Hermes 的网关实现。

### 系统图谱数学模型与分层（2026-11-03）

依据[《构建系统图谱模型》讨论](https://chatgpt.com/g/g-p-6ad87e33003881919e41568cb06c56b8-agent-orchestration/c/6ae08392-bd88-83e8-8398-2fdaa7d9de1e)及本次更新要求，采用以下设计方向，完整定义见[系统图谱数学模型](SYSTEM-GRAPH-MATH.zh-CN.md)：

- **Core：开放表达。** `G=(V,E,s,t,P)` 是通用有向多重 Property Graph；节点和边有稳定身份，边有有效端点，Properties 可自由增删改。`type`、`relation`、`status`、`owner`、`weight` 均为普通属性，不设全局业务类型枚举、必填属性、统一生命周期或 DAG/父级森林约束。
- **Mutation：通用改变。** 基本操作只改变节点、边、端点与 Properties；一次事务与被接受的提交分别表达。任务分配、失效传播等由上层转换成图修改，不进入通用基本指令。七条候选指令及端点可变性仍属于待试验的操作契约。
- **Projection：按需观察。** 同一原图可按属性、范围和粒度筛选、分组、形成商图并展开；保留源版本、原始成员/边的引用、边界和完整性。投影是派生结果，不是第二份独立权威状态；商图路径不自动证明原图路径。Agent 与网页在相同版本和规则下共用投影结构，Renderer 负责布局和显示。
- **Template：可选业务约定。** 用模板提供属性词汇、局部 Schema/约束、查询与投影预设、复合操作。可预制常用模板，允许社区贡献和团队定制；无需 Template 也能使用 Core。模板不产生身份、写权限或新用户授权；词汇、校验与产生修改的自动化要明确区分。模板机制与可选 Skill 各有职责。
- **优先复用图数据库。** 数学模型用于理解、接口契约和实现对照，不以从零编写图引擎为默认目标。具体数据库产品和部署方式未选定，先用同一参考样本验证候选；JSON 保留导入导出用途。
- **既有模型分离适配。** 现有架构 Schema、独立任务、证据和成熟度保留兼容，以后分别适配到场景 Template 和视图。它们不再定义通用 Core；本次是文档与计划更新，不代表数据、协议或实际运行已经迁移。

## 二、设计建议（待用户确认）

以下是工程分析与实施建议，不整体升级为用户硬性需求。已获历史实施授权的范围与仍待定的细节分别按[证据记录](REQUIREMENTS-STATE.zh-CN.md)判断；当前先经网站模拟形成具体流程，再决定真实实现。平台上限、版本和外部方案在本节保留为旧调研记录，本轮未重新核实，不作为当前保证。

- **图谱状态管理的首轮实现。** 建议复用单一权威接受顺序、必要的条件检查、原子事务和持久幂等回执。多个 Agent 可并发提出修改；冲突返回后重读决策，不默认覆盖。版本/条件检查粒度、删除和重连语义、ID 复用规则需结合候选数据库确定；不预设多主写入、CRDT 或任意业务冲突的自动合并。
- **图谱迁移与模板的首轮范围。** 建议先做小型契约样本和一个图数据库试验，再接通 Mutation、Projection 与一个最薄 Template。旧模型导入保留身份空间和来源，先在临时数据中验证；不先建设多后端框架、完整模板引擎或社区市场。阶段和验收见[开发计划](DEVELOPMENT.zh-CN.md)。
- **图数据库候选初验（2026-11-03 UTC）。** [调研与样本](GRAPH-DATABASE-EVALUATION.zh-CN.md)建议继续试用 SurrealDB；验证固定为 3.3.5，4.0 已发布但未测。它在 Mac 与 Linux 的同一虚构样本中均完成 28 项预期检查，含重连与删除限制的反例。建议先接一个受管后端与最薄 Go CLI，再接状态管理；正式产品选型、分发许可、版本与生产迁移仍未定。不得把它写成用户已经选定的唯一后端。
- **跨项目图谱（2026-11-06）。** 建议每项目独立逻辑图，在企业图中用普通引用节点表示，显式解析后按需 Projection；稳定 GraphID 与数据库位置分开，不改变单图 Core，也不要求每图一个进程。其他候选、数学边界和 Gemini/Opus 评审取舍见[方案比较](CLI-DAEMON-AND-GRAPH-SCOPE.zh-CN.md)。Linux 上三库虚构样本已通过八项存储边界检查；真实 Resolver、跨图权限与一致性、CLI 集成、性能和用户验收未完成。

- **发件箱与离线缓冲。** 成员发送时先写入本机发件箱，不等待网络。权威库可达时投递，由权威库给出正式 ID 和顺序。队长关机期间，消息留在发件箱，等队长上线后再投递。
- **发送确认要在应用层做。** 渠道的发送成功不等于对方的守护进程已收到。收件方收纳后回一条应用层确认，发件方在收到确认前保留发件箱里的记录。Telegram 对未确认的更新只保留 24 小时，收件方离线超过一天时，由发件箱重发或由权威库上线后补齐。
- **长消息。** Telegram 单条文本上限 4096 字符，超出时分片或改发文件。
- **接受状态按归属分担。** 旧建议按对象或字段指定负责人，使其权限范围内的修改不必逐条经队长人工批准；这不同于绕过权威接受流程。与下文单写权威的组合方式、旧字段级授权可复用范围仍待确认，不据这两条建议分别建立相反的接受规则。
- **对现有服务的影响。** 单中心接受模型是可复用基础。旧建议曾要求新增摘要、逐条状态、发件箱等；这些已有不同程度的实现，当前差距以第五节和[通信对照](COMMUNICATION-CONTRACT.zh-CN.md#8-当前实现对照只读快照)为准，不按旧清单重复开发。成员完整可见副本、多渠道与离线汇总仍需具体核对。
- **私发走机器人私聊，不走群。** 群内分发不能仅靠本地隐藏实现私发隔离。旧方案使用机器人之间的私聊；默认每位成员有自己的机器人这一条旧记录为用户已确认，本轮尚未补到最初原话，继续保留而不擅自扩为全队共享凭据。接入材料携带所需寻址信息，不含他人令牌。公共消息可以走群。
- **汇总有时间差。** 汇总靠各成员的 CLI 上报，管理员库在有一方上报之前不含该私发消息。要更及时，可以让发送方发送时同时给管理员的机器人发一份副本，再以上报兜底。服务器模式下所有消息都经过服务器，库是完整的。
- **离线补收的上限。** 旧调研记载 Telegram 的未确认更新保留期为 24 小时，本轮未重新核实平台限制。候选恢复方式是 CLI 启动时先取渠道待收，再向管理员库和发送方发件箱补齐更早的记录；相关来源都离线时需要等待来源恢复。发送方保留未确认记录是恢复依据，不是无条件“不会永久丢失”的证明；完整副本与恢复行为仍需按具体场景验收。
- **Git 通道承载项目共享内容。** 公开远端只放公开内容；2026-11-06 明确的私有 Gitea 可放授权项目成员共享的内容，不自动支持成员间私发。每人追加自己的记录，避免修改他人记录；具体批量、分支和归档策略待测。密钥和个人凭据不进入 Git。
- **权威状态单写者。** 权威状态由队长（或常驻服务器）签名发布。队员提交签名的变更请求，队长上线后处理。队长不在时队员读最近的接受版本。代理人机制暂不做。
- **接入包不带长期密钥。** 只含项目标识、托管地址、队长公钥指纹、一次性短期邀请码和角色。队友在本机生成密钥对，由队长或服务器批准。使用 Git 托管时，队友使用自己的账号。旧 Atlas CLI 的邀请包带有个人凭据，不沿用。
- **统一守护管理。** 候选实现是每台机器一个管理入口，管理图谱网页服务、消息接收和状态同步，复用已有 `service` 与 receiver。用户已授权统一 doctor/daemon 服务管理；一个管理入口不等于禁止受管子进程，也不把未来 GUI 列为当前前提。
- **热更新的候选实现。** 各端守护进程取得新接受版本后，通过 SSE 等方式更新本机浏览器，保留选择、视角、展开状态和焦点。具体推送/拉取机制可替换；旧“服务器秒级”是目标而非实测保证。仅 Git 轮询存在延迟限制，是否足以满足当前实时全队同步目标需要实例与测量判断。
- **网络可达做成可替换的提供者。** 局域网直连、自有中继、Tailscale、Cloudflare Tunnel、frp 等。提供诊断命令说明当前走哪条路径。Otoha 不自己实现穿透。
- **读取回执。** 摘要插入会话只算“已投递”。接收方取原文才算“已读”。
- **打断的实际效果取决于宿主。** 管理员发出打断消息后，能否真正插入接收方的当前会话，取决于该宿主是否支持。不支持时降级为下一次工具调用时提示。是否降级要写进投递记录，不能把“已发出”当作“已打断”。
- **普通成员遇到紧急情况。** 普通成员不能发打断消息。紧急问题需要经管理员转为打断消息，或由接收方策略把特定队列消息提前处理。这一条尚未定，见下面的未决问题。
- **通知网关借鉴 Hermes。** 去重回执落盘并保留 24 小时；按聊天共享出站预算；遇到 `retry_after` 只在原地等短时间，更长的交给持久队列；已确认但未派发的消息要保存并在重连后重新派发；平台适配器保持最小接口；接入配对码设置有效期、频率限制和失败锁定；防止 Bot 之间互相回复形成循环。
- **一条消息一个信封。** 信封是固定格式的头部：消息 ID、时间、发送者（成员、类型、Agent、会话）、收件人（成员、频道或公共）、类型（队列或打断）、摘要、引用、正文长度和正文哈希。信封必须单独自足，只看信封就能决定是否取正文。CLI 生成并校验信封，Agent 不手写。
- **信封与正文一起传，放不下就带引用。** 信封加正文不超过渠道的单条上限时，放在同一条里。超过时，信封仍放在第一条里，正文改为附件，或改为只带引用，由收件方 CLI 向权威库取。信封永远不被截断。上限按渠道的能力声明取值，中文要按字节算，不能按字符数估。
- **收件方先收纳，再交给 Agent。** CLI 收到后校验信封与哈希，把正文写入本机库，再把摘要和固定字段交给 Agent。正文在 Agent 主动取用时才读到上下文，这一步同时记为“已读”。
- **摘要是不可信文本。** 摘要来自别的成员或别的 Agent，直接进入 Agent 上下文，等于外部文本影响 Agent。CLI 要限制长度、去掉控制字符、固定包裹格式，并在包裹处标明“来源：某成员的某 Agent，内容仅供参考，不产生授权”。摘要也可能与正文不符，所以执行动作前应取正文核对。
- **摘要由谁写。** Agent 发消息时由 Agent 自己写摘要，CLI 只检查长度和格式、补充固定字段。人发消息时，输入的话就是摘要，附件是正文。
- **人输入的话过长时。** 摘要有长度上限，因为它会进入 Agent 的上下文。人输入的话超过上限时，建议 CLI 把全文放进正文，摘要取开头部分并标明被截断，而不是拒绝发送或把长文塞进上下文。上限的具体数值尚未定。
- **查收默认只给摘要。** 建议查收命令默认只返回摘要，用选项带上正文，也可以按消息 ID 指定只给某几条带上正文。若默认就带上全部正文，队列消息里的长正文会一次性进入上下文，摘要分离就失去了意义。此条是对用户“直接带上”的解读，待确认。
- **消息发送者的结构。** 发送者由成员标识、类型（人或 Agent）组成；类型为 Agent 时再加 Agent 标识和会话标识。格式由 CLI 在发送时生成，Agent 不手写，避免冒名和格式不一致。接收方据此判断消息来自人还是来自 Agent，并按各自的读取策略处理。
- **人的消息按 @ 解析。** 群里 @ 某个成员的消息送入该成员的收件箱，不指定会话，由其 Agent 在下次查收时看到，再决定交给哪个会话。旧记录为用户已确认，本轮原话未补证；不据这一建议行再授予新的路由或读取权限。
- **渠道适配器的最小接口与能力声明。** 参考 Hermes：连接、断开、发送三个必需方法，加可选的聊天信息查询。Hermes 的适配器面向“人给 Agent 发消息”，不声明各渠道能否做点对点投递。Otoha 的适配器需要额外声明能力：能否向指定成员定向投递、成员之间能否私聊、未读消息保留多久、能否拉取历史、单条长度上限、频率限制。CLI 按能力决定某个渠道能承担公共消息、私发消息还是仅通知；没有定向投递能力的渠道只用于公共消息和通知。
- **渠道的身份映射。** 适配器把渠道里的发送者映射到已登记的 Otoha 成员，再做授权。适配器层不产生授权。Hermes 的授权顺序（按平台全开、白名单、私聊配对码、全局全开）和配对码规则可借鉴。
- **实现语言（旧记录为用户同意按此推进）。** Go 作为单一二进制的外壳，负责进程管理、渠道、同步、本机消息库和全部 CLI 命令。现有 Python 协作服务暂时作为被它管理的后端保留，逐步迁移；Node 图谱服务作为被它管理的子进程。本轮补证了用户批准相关 CLI/daemon 阶段，没有补到“所有组件必须 Go”的独立要求。使用者不另装 Python/Node 的分发目标尚未解决，打包方式仍未决定。
- **消息稳定身份与顺序。** 发件前已有稳定标识，有利于去重、确认和离线恢复；顺序号与消息身份不能混同。当前中央服务有自增 ID 和 actor/client_id 去重，新原生路径也有 uid。跨成员、跨项目、跨权威端的精确身份约定尚未定，不把候选字段命名写成已发布契约，也不再声称现有消息只有入库后才有身份。
- **已读要逐条记录。** 逐条状态可以表达“读了 5 号但没读 4 号”；高水位不能表达这一事实。当前逐消息回执与旧高水位回执并存，具体命令仍可能走不同路径，应核对接口而不是重复新增。读取声明仍不等于模型消费。
- **历史实施顺序。** 先做常驻守护进程和受管图谱服务是原建议，历史上也获准先补统一 doctor/daemon；2026-11-06 后续要求当前先用网站模拟具体需求与流程。保留实施基础，不把旧顺序当继续扩展真实通信语义的授权。

## 三、必须遵守的安全边界

保留以下安全约束。涉及渠道频率、容量和保留期的数值来自旧调研，本轮不重新宣称已经核实当前平台政策；真实渠道接入前按实际能力核对，不把平台缓存当权威消息库。

- 图谱网页服务目前只绑定 `127.0.0.1`，GET 接口没有认证，写接口依赖会话令牌。通过隧道或网关暴露给他人之前，必须先加身份认证。读取也要认证。
- Telegram Bot API 不是端到端加密，也不承诺长期保存。不得通过它发送密钥、生产凭据或敏感内容。未确认的 update 只保留 24 小时，所以它不能作为离线信箱。
- Telegram 发送遵守官方频率建议：同一私聊每秒不超过一条，群组每分钟不超过 20 条。限流放在通信层，不依赖 Agent 自觉。不通过增加 Bot 或轮换 Token 规避限制。
- 一个 Bot Token 只能有一个轮询者。多个 Agent 会话共享一个网关。
- 私发消息不得发到群里，群内所有成员的机器人都能看到。
- Telegram 发送者身份必须映射到已注册的 Otoha 身份，再做授权检查。消息里声称的身份不产生授权。
- 本仓库公开。凭据、邀请、真实消息和运行状态不进入 Git。

## 四、尚未验证

本节包含旧核对范围；2026-11-06 的源码观察与主会话独立临时样本在[通信契约](COMMUNICATION-CONTRACT.zh-CN.md#8-当前实现对照只读快照)和[需求对照](REQUIREMENTS-STATE.zh-CN.md#7-对照实现具体差距与下一步实例)中单列，不把技术结果改写成需求或用户验收。

- 新图谱已有[独立候选小样本结果](GRAPH-DATABASE-EVALUATION.zh-CN.md)：覆盖 SurrealDB 3.3.5 的指定 Core 行为、事务内条件/回滚、分组与成员查询、重连组合、正常重启和导出导入。通用 Otoha API、权限/幂等回执/接受历史、真实并发、千级 Projection、历史展开、Template 作用范围及旧模型迁移仍未验证。小样本和既有架构图测试不能作为这些完整能力已通过的证据。
- 紧急消息直接插入当前会话：旧 Atlas CLI 对 Codex 做过（忙时 steer，空闲时 queue），其他宿主未验证。做不到时只能降级为下次工具调用时提示。
- 空闲 Agent 的唤醒：旧 Team Mailbox 与 Atlas CLI 的文档都标明未完全解决。
- 只用 Git 轮询时的实际延迟，以及各托管平台的频率限制。
- 国内成员经中继或隧道的实际速度，尚无测量。
- Telegram 机器人互发消息：官方文档已确认存在（Bot API 10.0，2026-05-08 起）；2026-10-24 已用 Bocchi/Nijika 两个真实 Bot 验证双向 API 收发。Otoha Gateway 的真实验证覆盖了发送、长轮询接收、chat→Session 路由和本机状态保存；完整应用层回执、离线补收和反向 Gateway 端到端重试仍待单独验收。
- 旧记录已有两个真实 Bot 的 API 双向收发和 Gateway 小样本，不能同时再写成“尚未测试机器人能否私聊”。本轮只回读了当时用户的测试授权和助手结果报告，没有重跑真实 Bot；应用层确认、长离线补收和完整重连链仍未因此通过。
- 历史核对曾只读图谱协议/传输与协作服务开头；本轮已沿团队接入、消息存取、服务端权限/回执、receiver 和宿主投递继续读取。未穷尽全部插件与历史实验，当前观察范围见下节，不把旧阅读缺口重复写成新事实。
- 普通成员的紧急情况如何上达：只能找管理员转发，还是允许接收方对来自特定成员或特定类型的队列消息设置提前处理规则，用户尚未决定。
- 渠道单条容量（已核对部分）：Telegram 机器人文本消息上限 4096 字符（取自 Hermes 适配器的常量，官方页面未能抓到原文）；机器人上传文件 50 MB，图片 10 MB（官方）。ntfy 默认消息体 4096 字节，附件单个 15 MB，服务端默认缓存 12 小时，重启后内存缓存丢失（官方配置页，默认值是从示例注释推断的）。Telegram 机器人下载文件的上限、各渠道的频率限制，尚未核对。
- 各渠道的定向投递能力：只有 Telegram 的机器人互发在官方文档中确认。Discord、Slack、Matrix、IRC、ntfy 等能否让两个机器人定向私聊，尚未核实。Hermes 的适配器文档不涉及这一点。

## 五、代码核对结果（2026-11-06 只读快照）

本轮沿当前源码读取；主会话另有独立临时 Store 盘点。本审计没有运行真实服务、使用真实凭据或向 Session 投递消息，也不把主会话样本写成自己重跑或用户验收。此前“没有摘要字段/消息等级/逐条回执”等旧结论已由下述现状取代；不继续在有效设计文档中并列相反定义。工作区正在并行修改，具体入口与观察边界见[通信对照](COMMUNICATION-CONTRACT.zh-CN.md#8-当前实现对照只读快照)。

### 协作服务与消息接口

- `services/collaboration/otoha_server.py` 已持久保存完整 payload，包括 `summary/body/text/class/uid`；有中央历史分页、有界授权 query，以及逐消息回执和兼容高水位回执。中央库不是只有 100 条消息。
- `otoha_projection.py` 的 `recent/incremental` 默认 `SELECT *`；新原生 `message list` 也默认返回全文。存在字段分离和 query 不等于默认摘要读取已经兑现。
- `apps/cli/internal/otoha/messages.go` 从 text 首行派生摘要，固定 queued/tool；最近 100 条是新团队派生缓存。旧逐条 inbox、新缓存、待发请求和中央历史是不同持久路径，尚不能合称完整成员可见副本。
- `receive.go` 的旧 chat 投递未按 class 分流，并交给宿主完整 payload；`desktop.go` 先尝试 steer。因此 queued 消息也可能打断，摘要/正文的注意力隔离尚有具体缺口。
- 当前服务按项目/频道授权；`to_sessions` 是投递筛选，不是逐条读取 ACL。global owner 与项目 admin 不同。主会话临时实例还观察到普通 member 可提交 interrupt；这不是用户授予其打断权限的证据。
- inbox 保存、宿主投递结果和读取声明已有不同记录；它们不自动证明模型读到、接手、交付或用户验收。完整离线补收、管理员汇总和成员副本范围仍需按既有决定及具体实例验收。

### 图谱、团队接入与工作页

- `packages/graph/team` 的签名请求、字段授权、GitTransport 和接受状态是既有复用基础；它们不自动成为新 Core 的全部协议。当前架构 Schema 仍有固定类型、必填属性、成熟度和独立任务集合，尚未完成自由 Property Graph/Template 泛化。
- `team.go` 与 `join_managed_repo.go` 已把项目、身份、受管仓库、服务、通信接入串起一部分；readiness 尚未证明图谱身份与权限也完成统一。不能写成全无集成，也不能写成四类资源已全部一体化验收。
- 工作页已支持 `format=html` 的不透明内容和 iframe 展示，不能继续说被固定清单锁死。实际资源/脚本能力、全队同步和热更新体验仍按具体实例核对，Graph 不成为必需布局。
- doctor/daemon、系统服务管理、事件长轮询、待发/回执及重启游标有实现基础。真实资源总量、长期稳定、首次轻量会话接入及各宿主窗口行为没有因这些代码存在而自动通过。
- 既有 Go CLI 还提供本机私有目录、运行时、协作服务、团队健康、SQLite 完整性和受管 receiver 的 doctor 入口，以及 daemon 安装/启停/重启/卸载/状态/日志。server 模式具有固定 HostKey 的 SSH 初始化/启动和 HTTPS/TLS（可配 CA）访问入口。本审计未复验真实主机、证书、系统服务注册或跨机器结果；主会话独立测试按其实际证据另报。
