# CLI、常驻服务与跨项目图谱

2026-11-06。本轮明确产品要做什么，再决定怎样实现。下文把用户要求、实施建议和实验结果分别标明；接口示意不代表命令已经存在。

## 1. 用户明确的产品形态

Otoha 是一套由 CLI 操作的常驻协作服务。它可靠地连接团队、保存通信、提供共同工程图谱，并让 Agent 通过本地网页向人呈现工作。正常时安静运行，故障时给出能采取行动的反馈。

人可以用现有 Agent 产品的语音会话指挥工作；该会话调用 Otoha 的工具，更新网页、读取消息、查询图谱和提交修改。Otoha 提供下面这一层基础设施，不开发自己的语音 Agent。接入条件是宿主会话能调用 CLI 或等效工具；只有语音功能还不够。

```text
人 ⇄ 现有 Agent 的会话（可用语音）
                 │ CLI 调用 / 结构化结果
                 ▼
          本机 Otoha 常驻服务
          ├─ 通信：正文、摘要、引用、发件箱、回执
          ├─ 图谱：Core、Mutation、Projection
          ├─ 接入：身份、项目、私有服务器、恢复连接
          └─ 本地网页：呈现、更新、收集反馈
                 ⇅
       队长电脑 / 自有服务器 / 租用服务器
       Otoha 权威服务 + 可选的私有 Gitea
```

图中的职责不要求拆成多个服务。建议每台机器沿用一个受管 daemon，管理必要的后端和 receiver；一个 daemon 可以服务多个项目。数据库具体打包方式仍待验证。

“团队效率翻倍”是产品目标，不是已测得的收益。先观察减少了多少人工转述、重复接入、全量上下文读取和因过期信息产生的返工。

## 2. CLI 必须完成的六件事

| 用户或 Agent 的意图 | Otoha 必须负责的结果 | 接口应直接说明什么 |
| --- | --- | --- |
| 加入这个团队 | 完成本机身份、项目授权、所选仓库和通信配置，启动必要后台服务 | 哪个项目已可用；哪一步未完成；下一步动作 |
| 启动后继续工作 | 维护连接，重启后恢复身份、游标和待发内容 | 已连接、离线待续接或需要处理 |
| 告诉另一个 Agent | 保存完整内容，发送摘要与引用，按策略查收和读取 | 已持久保存、已投递、已读取分别记录 |
| 看清有关的工程状态 | 有界查询、追溯原件、必要时进入其他图 | 图身份、源版本、范围、边界与缺失部分 |
| 改变共同状态 | 在授权范围内执行有条件的 Mutation，提供可查询的结果 | 接受、拒绝或结果未知；重试使用同一请求身份 |
| 给人看并取得反馈 | 打开本地页面，更新呈现，保存人的反馈并让 Agent 读到 | 哪个页面、对应哪些源对象、反馈是否被读取 |

命令名继续沿用和收敛现有 `team`、`daemon`、`message`、`inbox`、`graph` 入口，不能让使用者在多个后台进程或两套身份之间自行接线。新增页面发布、反馈读取和跨图解析接口时，先验证这六个意图，不先设计一大套组件语言。

短帮助给一个可执行例子。结构化结果有稳定字段、大小上限和必要的下一步入口；细节按需查询。人看到的页面与 Agent 读到的 Projection 使用相同来源，避免各自维护一份事实。

页面中的选择、折叠、布局是视图状态；人的评论是反馈；批准或修改工程对象是业务动作。导航不默认修改工程图；反馈先持久保存，若进一步表示成图中对象，也必须经 Mutation 写入。正常 HTML、SVG 或其他实例也可以呈现，不把固定控件集合变成底层限制。

## 3. 一次接入，之后自动续接

用户要求的一键接入适用于私有仓库、自有或租用服务器、队长电脑。管理员首次部署与队员加入是不同操作：管理员确定服务入口、项目、授权和所选渠道，生成邀请；队员通过一个接入入口完成其余编排。现有 `team join --invite FILE` 是基础，目标是去掉需要人逐项排错的接入包流程。

接入成功应按本项目实际启用的能力判断。Gitea 能拉代码，但没有 Otoha 项目授权或 receiver 不可用，不能报整个团队“已就绪”。缺少可选渠道则不应阻止其他已配置能力使用。邀请只携带接入信息和短期兑换材料，不携带管理员私钥、Bot Token 或其他人的长期凭据。

队长关机后，队员保留本机身份和最近接受状态。消息先进入持久发件箱；图修改可以保存为待提交意图，不能伪装成团队已接受状态。待提交意图是基础设施的操作记录，不要求把每个图节点加上统一 `Accepted` 状态。

队长重新上线后，自动恢复连接并按游标补收。对结果未知的请求，先按原请求 ID 查回执；需要重试时沿用同一 ID，避免重复执行。无需重新邀请或手动重新接入。这里承诺的是同一中心重启后的恢复，不暗含自动选举或多主写入。已撤销授权、失效凭据等确需人处理的情况要明确报告。

多渠道是可选能力。若启用的 Telegram 等渠道仍可达，消息可以继续流转；这不等于图谱权威中心仍在线，也不能据此接受共享图修改。

## 4. 私有 Gitea 与 Otoha 各管什么

用户已明确：私有 Gitea 用于私有项目和高频 AI 协作；GitHub 发布经过整理、有明确意义的公开更新。私有部署使团队能自行控制使用规则，但不取消磁盘、网络和运行成本。

| 部分 | 管理的事实 |
| --- | --- |
| Gitea / Git | 代码、文件版本和配置好的 Git 传输通道 |
| Otoha 通信 | 消息身份、可见范围、正文引用、投递与读取记录 |
| Otoha 图谱状态管理 | 每张逻辑图的权限、接受顺序、条件检查、事务与回执 |
| 本地网页 | 工作呈现、交互状态与反馈入口 |

私有仓库可承载项目内共享的通信记录，不自动提供成员间私发隔离。Git push 成功也不证明消息已读或图修改被接受。Git 历史不能替代 Otoha 的接受回执。高频通信不必一条消息一个代码 commit；是否批量、采用独立数据分支或直接服务通道，应由实际负载决定。

公网接入要由 Otoha 编排可达路径并诊断实际故障层。复用现有网络提供者，不要求普通队员手动理解隧道、证书、Git 和 receiver 的内部组合；也不把公网可达误认为已经有项目权限。

## 5. 把图作为节点：四个候选

先分清三件事：**逻辑图**是独立的工程状态；**数据库**是存放它的容器；**数据库进程**是运行成本。一个项目一张逻辑图，不要求每个项目单独运行一个数据库进程。

| 候选 | 怎么表达 | 适合的条件 | 主要代价 |
| --- | --- | --- | --- |
| A · 一张总图，按范围分项目 | 所有节点边在同一图，项目用属性或关系分组 | 项目共享权限与事务边界，经常一起修改 | 项目独立迁移、授权和局部运维需要额外设计；并非做不到 |
| **B · 独立图加引用** | 上层普通节点引用另一张逻辑图，读取时显式解析 | 项目可独立部署，也需要企业级关联 | 需要解析引用、说明跨图读取范围和不可达状态 |
| C · 原生递归复合图 | Core 规定节点直接包含图，并定义嵌套操作 | 嵌套归属本身就是产品的基本语义 | 需要新增身份、生命周期、修改和共享语义；不必然要求单父，但规范明显变厚 |
| D · 联邦查询层 | 多张图统一查询，结果保留各自来源 | 跨图查询已频繁且需要优化 | 需要处理路由、权限、版本与部分失败；可在 B 上逐步建设 |

**当前建议先试 B，保留 A 和 D 的发展空间。** 关键理由是项目可以独立存在，同时不改变已有 Core。C 的存储快照或导出形式可以有用途，无需先成为所有节点的公理。

## 6. B 的最小数学解释

每一张图仍然是：

\[
G_g=(V_g,E_g,s_g,t_g,P_g)
\]

外层只需能用稳定图身份找到相应状态：

\[
\mathfrak G=\{g\mapsto G_g\},\qquad
\operatorname{loc}(g)=\text{当前存储位置}
\]

这是基础设施中的命名与定位，不是给单图 Core 增加新元素。存储位置可以包括服务地址、namespace 和 database；迁移存储不应改变逻辑图身份。单机如何持久化这份映射，先用最小注册表试验。

```text
企业图 g_org                         项目图 g_pay
┌────────┐      ┌────────┐            ┌────────────────┐
│ 商城项目 │ ───→ │ 支付项目 │ ········→ │ …  Refund API  … │
└────────┘      └────────┘            └────────────────┘
                 普通引用节点             独立权威事实
       实线：企业图自己的边    虚线：读取时解析到项目图
```

在一个**显式启用的示例约定**中，支付节点可以有 `p.ref = {graph_id: "g_pay"}`。这只是普通可序列化属性；`ref` 不是 Core 保留字段，其他普通对象碰巧有同名属性也不能自动触发网络读取。引用不授予目标图的读写权限。具体字段与启用方式待最薄约定试验。

两个企业节点可以引用同一个 `g_pay`，并有不同本地称呼。目标事实只由支付图管理；删除一个引用不删除支付图，修改本地称呼也不改目标名称。引用也可以成环，读取按显式范围和深度停止，不增加全局森林公理。

**进入**是切换到目标图；**展开**是在当前读视图里显示目标的一部分。展开的 Projection 保留每个对象的 `(graph_id, kind, local_id)`、源版本和边界，不复制成另一份权威图。

跨图读取记录各图实际读到的版本集合；这不是一个全局原子快照。一次响应内复用同一源图的读取结果，避免同一目标在两个位置读成不同状态。当前未实现历史读取，不能仅凭记录了版本就承诺日后按该版本重放。

单图 Mutation 保持单图原子性。首轮不提供跨图原子写或跨图条件的原子检查，不级联删除目标，也不承诺自动发现整个企业所有反向引用。目标不可达、不可见或不存在时，按权限政策给出可解释的边界，不能悄悄当作空图。

### 一个具体的跨项目依赖

企业图里的“商城依赖支付”是企业范围的一条声明，不自动证明商城所有模块都依赖支付。

若要表达 `商城.Checkout → 支付.Refund API`，可以在商城图内建一个普通代理节点，引用 `(g_pay, refund_api)`；Checkout 的本地边指向它。依赖声明归商城图管理，Refund API 的实际状态归支付图管理。也可由独立集成图持有这条声明，前提是明确由谁负责它。

这些边可以记录计划、设计声明或观测结果，含义由约定和证据解释；画出关系不等于已经运行验证。内层细节变化如何影响上层，要先查询可见范围和来源，不能从一条粗粒度边推断全部影响。

## 7. 实际验证与模型评审

本轮在 Omarchy Linux 上用现有 SurrealDB **3.3.5**、随机测试身份和临时数据，建立 enterprise、shop、pay 三个 database。最终可复跑脚本与记录见[跨图存储实验](../experiments/graph-composition/README.md)。

八项预期检查覆盖：两个普通节点引用同图；不同库保留同名局部 ID；显式注册表路由读到目标；目标不在本库；原生边不会自动跨库解析；失败边没有持久化；删除一个引用保留另一引用；目标数据不被删除。这里验证的是表示和存储边界，**不是 Otoha Resolver、权限、版本历史、跨库事务或性能已经通过**。

SurrealDB 对象按当前 namespace/database 解释；`USE` 为后续语句切换上下文，不提供自动跨图解析。应用打开逻辑图时应先解析既有注册信息，不能利用数据库隐式创建行为把拼错的图名变成新图。参见[官方多租户结构](https://surrealdb.com/docs/learn/schema-management/multi-tenancy/namespace-and-database-architecture)及 [`USE`](https://surrealdb.com/docs/reference/query-language/statements/use)。

独立图、别名和代理节点也有成熟先例：Neo4j Composite Database 使用图别名，其原生关系不跨 constituent graph；它的能力和产品限制并不直接等于 Otoha 的实现。参见[官方概念说明](https://neo4j.com/docs/operations-manual/current/scalability/composite-databases/concepts/)。

通过 AGY 向 Gemini 4 Argon 与 Claude Opus 5.5 各咨询两轮；Opus 严格限于两次。另用 Gemini 3.8 Flash 审查接入与恢复闭环。原始提示、回答和执行回执保存在本机私有记录中，不进入公开仓库。

评审共同支持 B，强调源状态归属、删除引用不删目标、跨图读取说明版本。这里采用的是经独立判断后的建议：没有采纳首轮就建设全局反向索引、完整历史固定版本、强制摘要发布或固定页面组件语言的扩张；也没有采纳把 Git 提交当作接受历史、把离线意图强制变成业务节点、把 Telegram 永久限定为单向通知的建议。模型意见不代替实验或用户验收。

## 8. 下一轮应先跑通的真实场景

现有代码已有 `team init/invite/join/status/doctor`、受管 receiver、游标和发件箱基础，但尚未把仓库接入、通用图后端、后台恢复、页面反馈和真实 Agent 连接为完整产品。当前失败发件箱仍有显式 `retry` 路径，不能报告成全部自动续发。

建议用现有 Mac 和 Omarchy，先完成下面同一个闭环，避免分别造出互不连接的功能：

1. Omarchy 作为中心并使用私有 Gitea；Mac 用测试邀请接入。区分代码仓已同步、项目已授权和后台接收已就绪。首次管理员配置不计为每位队员都要做的操作。
2. Mac 上一个真实 Agent 读取局部工程图、发送消息、打开并更新本地工作页。人在页面留一条反馈，Agent 按引用读取后修改自己的下一步工作。
3. 停止**本实验的中心进程**模拟队长关机。Mac 保存消息和待提交图意图，仍可查看标明版本的旧状态。另覆盖中心已接受、仅实验响应丢失的情况：重启 Mac 测试 daemon 后按原请求 ID 查回结果。恢复后不产生第二个成员、第二个 receiver、重复消息或重复图修改；网页保留视角，等待期间不做模型轮询。
4. 在同一后端加入企业图引用样本，验证进入、展开、重复引用、目标离线和同名 ID；失败时保留来源边界。先做这一条解析链，不先建联邦平台。

这些是待实施验收，不是本轮八项存储实验的结论。开始前再核对真实服务与测试身份；不通过关掉现有整台服务器或接管真实 receiver 来制造故障。

## 9. 安静与性能如何验收

默认只露出就绪、离线待续接、需要处理的状态。进入详情后可以查到真实原因、待发数量、最近同步、源版本和日志。安静不意味着把失败藏起来。

优先采用事件驱动、持久队列、有界查询、分页和增量更新，空闲时不靠 LLM 轮询。一个后端进程能否服务多个项目应先实测，不把“每项目一图”实现成“每项目一套常驻进程”。

记录下面的基线后，再确定资源预算和性能门槛，不凭空承诺毫秒或内存数字：

| 场景 | 测量 |
| --- | --- |
| 无任务、多个项目接入 | daemon、数据库和其他受管进程分别及合计的 RSS、CPU、唤醒和增长趋势 |
| 常用操作 | CLI 往返、持久入箱、实际投递、局部查询、页面可见更新各自的 p50/p95 |
| 断网、中心重启、进程崩溃 | 恢复耗时、补收完整性、重复副作用、是否需要人工重新接入 |
| 有界数据增长 | 固定机器与样本规模下的读取量、响应大小、队列积压和资源变化 |

浏览器和宿主 Agent 的占用单独记录；数据库文件或二进制大小不当作常驻内存。健康检查、退避和进程监管采用成熟机制，其具体参数由实测决定。
