# Otoha Skills：从推导到成品

2026-11-14。当前为开发与试用基线，不是已经证明普遍有效的发布版。Skills 保持可选；Otoha 的产品主线仍为调度与通信基础设施。

本轮并行发展两条线。第一条复用 `otoha-visualize`、需求实例化与持续对齐，帮助人从具体体验判断需求和开发计划，并检查人的要求是否进入真实产出。第二条增加 `otoha-content-review`，把文稿、PPT、PDF 等作品的整体导演、分层推导与实际成品审查串起来。两条线共享依据与反馈关系，不合并成一个强制管理系统。

## 共同主张

推导过程与实际成品都要审。推导不是事后给坐标编理由，成品也不能只检查溢出和对齐。复杂作品的推导分层：整体目标与体验弧线 → 段落安排 → 页面或场景任务 → 元素位置、尺度和图文关系 → 必要的动画时序。每层决定从上一层的目标和约束中产生，局部漂亮不能抵消整体节奏失败。

通用字体、网格与层级可以明确继承已论证规则；特殊元素保留真实候选、取舍和验证。没有做过的推导标为缺失，重新设计，不补写追认。没有动画需求时不强加动画。

打样同样属于被审查的推导。生图前审提示词是否反映当前适用约束与分层目标；出图后审它是否已经违反这些要求。比较实质不同的候选，记录采用与舍弃，不让错误样图因忠实实现而传播到成品。多打样的数量不能代替这些判断。

打样可随制作多轮循环：当前作品与卡点 → 本轮动态调整的提示词 → 候选与审查 → 真实修改 → 整体回看。每轮保留仍适用约束，并根据最新反馈更新问题与目标，不把首轮提示词变成固定模版；方向清楚时直接实现。

## 开发计划与验收

| 阶段 | 产物 | 通过依据 |
| --- | --- | --- |
| 当前：共同需求与最小接口 | 同一 HTML 入口、两条线的核心思想与试水状态、可用 Skill 草稿 | 人能定位整体与局部推导、当前失败及下一步；不沿用已被反馈推翻的通过结论 |
| 真实试水返修 | 原项目中更新的实例、作品、推导记录与实际观察 | 原失败触发场景和整套体验都重新查看；证据指向修订后的版本 |
| 独立复核 | 普通前端默认由另一较强模型、高推理的独立 Agent 实看并记录中性事实；内容作品继续审推导与实际成品 | 制作侧先自查，宿主轻量 CLI 合并卡点并关联当前修订；原作者返修、原 verifier 复验；未知仍为未验证 |
| 可复用性验证 | 不同题材的新任务试用与最小安装包 | 普通工作目录能找到入口；按适用范围执行；错误和必要例外都保留，不用合成探针冒充真实有效 |

前端线还要分别检查规则快速触达、一次请求到最终交付的有效性，以及需求对齐页 60 秒首次打开与持续更新。任一项通过不能抵消其他项失败。内容线要分别检查内容准确、整体导演、逐元素推导、静态渲染、播放或现场使用；独立 MP4 能播放不证明 PPT 内嵌视频已实播。

## 分工与共享

原项目继续制作与返修，Otoha 侧维护可复用方法和接口，独立 verifier 不参与被审版本的制作。指定作者、模型和工具属于各项目配置，不提升为所有用户的强制要求。沿已有会话和授权链路协作，发送摘要及必要引用；不迁移私人消息到公开仓库。

2026-11-15 更新：普通前端的独立验收已成为当前默认，不再只用于严格项目。制作侧先自查，另一较强模型、高推理的独立 Agent 亲自查看实际成品、操作关键状态并记录中性事实；复用宿主同一轻量 CLI 合并卡点、关联产物修订。首审使用独立上下文，不接收作者自评分或通过结论；原作者返修后由原 verifier 继续复验，作者不能代填或改写独立记录。普通任务不因此启用完整美术选型或后台审查服务。下段历史实测保留当时模型、合同与观察范围，不追认最新要求已经全部复验。

这项默认与真实接入效果分开记录。宿主同一轻量入口已提供独立事实合并和修订绑定；本系列三组虚构示例已实际由制作侧与独立者分别记录，制作侧单独完成被阻断，加入独立记录后才合并通过。独立者指定输入、操作员定向执行、独立者亲自判读原始画面的协作方式须如实标明，不能冒充独立者直接控制浏览器。原项目其他 peer 接入、改版后旧证据失效及不同新任务的最终效果仍须各自实测。这一组局部采用不证明普遍有效；程序也不认证观察的真实性，不代替用户验收。

HTML 工作稿让人连续看作品，并就近展开推导、候选与审查结果。它不替代要求交付的 PPT、PDF 或动画。已有团队可用 Otoha 工作页共享接受版本；未接入时先本地展示，并如实记录团队同步缺口。工程图谱只按需关联，不把写入 Graph 当作草稿展示的门槛。

## Layout 样本积累方向

用户提出素材库可降低重复制作成本。建议先复用已经在做的可操作对照与项目组件，按对比、因果、时序、层级、空间、状态变化组织小型样本索引，再随真实任务积累。每个推荐样本应有适用条件、实际可运行结果与反例；题材、视觉风格和使用范围分开。未验收样本只作探索材料，不作为“照着做就正确”的标准，也不据此固定所有作品的布局。

组件减少实现成本，样本帮助寻找表达方向；当前内容的布局仍需推导与实际审查。暂不新增素材数据库、抓取服务或图谱业务公理。此项是建设方向，尚未形成经过验证的丰富样本库。

真实试水的私人来源、工作页和运行证据保存在获准的工作目录，公共 Skill 只保留通用方法与虚构样例。测试成绩、实际宿主行为和用户验收分别报告。

## 按标准选择检查方法，确认的问题可以阻断交付

用户已明确：所谓软检查描述判断方式，不意味着处理宽松。代码检查、结构与语义结合、独立视觉判断是一组可组合的方法，没有绝对硬软分界。能够可靠编码的部分应编码；尚不能编码的标准仍然有效，不能因为难以自动判断而降级。

2026-11-15 已将评分通过器与题包拆分：[通用审查协议](REVIEW-PROTOCOL.zh-CN.md)采用一份 JSON 定义观察、条件、得分及处置，公共核心按确定性逻辑归并。本机前端 CLI 已接入同一核心，网页目标与独立审查留在适配器；这项复用不证明语义判断的准确性，也不替代以下真实样本校准。

这与当前两条试水直接相关：自报“没有重复”曾被真实页面反馈推翻，独立审阅也曾漏掉整体节奏。角色存在和程序有回执都不足以证明判断正确。本轮继续用已有作者、制作侧、独立审查者及验收入口执行和校准，并已实现下述两项有限检查；跨项目通用接入与语义审查引擎仍是开发计划。

### 本轮已实现的检查与实例

- [实际图片几何检查](../skills/otoha-content-review/scripts/check_pptx_images.py)：读取 PPTX 中嵌入的 PNG/JPEG、实际裁切窗口和图片图框，计算横纵倍率；支持精确到页与对象的显式拉伸例外。不支持的变换、填图或格式保持未验证，几何通过不代表人物裁切、动作语义、审美或原生显示通过。
- [已提交审查结果检查](../skills/otoha-content-review/scripts/check_review_result.py)：读取整体、逐页和过程判定及问题，核对页面覆盖、当前输入 SHA-256 和指定产物绑定；明确失败或未解决的 blocker/major 阻断交付，未知结论或必需证据缺失保持未验证。它不认证审阅者身份、实际读图或判断正确性，也不把审查程序正常退出当成质量通过。
- [三组虚构可操作正反例](../skills/otoha-content-review/assets/review-cases.html)：改变图框宽度比较拉伸与等比；取消遮挡白条观察仍存的骑缝；用编号箭头与单选卡片比较先后流程和并列选择。“先选一项”保留必要约束，不作为辅助废话删除。这些实例只示范指定关系，不代表真实作品或整套审美已通过。

当前两项检查器共有 28 项回归（[图片几何 11 项](../test/test_content_image_geometry.py)、[审查结果 17 项](../test/test_content_review_result.py)），本轮运行全部通过。复跑命令为 `python3 -m unittest discover -s test -p 'test_content_*.py'`。它们验证已编码的比例、结果读取、覆盖和版本匹配行为，不证明通用语义判断有效。命令、输入格式及已支持范围见[可执行检查说明](../skills/otoha-content-review/references/checks.md)；各项目的实际构建或交付接入仍须单独落实。

### 最薄接口

复用项目已有文件和检查命令。一项标准说明适用对象、要观察的关系、所需证据和何种发现应阻断。检查器接收当前要求与实际作品版本，返回具体问题：

```text
输入：适用标准 + 当前文件/构建版本 + 实际画面/操作/播放证据
方法：代码检查 / 结构提取与语义判断 / 独立观看与操作，可组合
输出：位置 + 实际观察 + 对理解或行为的影响 + 标准依据 + 严重性
处理：确认阻断 → 原制作侧返修 → 新版本实测 → 关闭或保留问题
```

发现可能有误时回看同一实际对象和原要求，不让程序把模型置信度当真相。未观察、证据不足、检查执行失败、已确认问题和已复验解决分别记录。已有独立审查者可以执行判断，不必为每条意见另开模型。用户明确否定的结果直接进入返修，不能被模型总分抵消。

### 按具体标准拆解

| 要判断的标准 | 可先用代码取得的事实 | 仍需判断的部分 | 处理 |
| --- | --- | --- | --- |
| 指定比较组件不重复解释关系符号 | 同一组件是否同时渲染符号及同义说明槽位 | 新增说明是否表达符号未包含的必要条件 | 明确重复则移除，复看实际布局 |
| 布局是否表达了关系 | 元素、文字、对齐、连线端点和交互状态 | 观众是否能辨认对象、方向与关系 | 看不懂则重新设计，不能加概括段补成通过 |
| 整套作品的观看任务有推进 | 页序、时间、图文对象和代表状态 | 连续观看时是否有节奏和认知推进 | 整体失效则返修段落规划及受影响页面 |
| 推导是否落实 | 要求、候选、采用决定与成品引用是否齐备 | 选择是否回应上层目标，画面是否支持预计 | 缺依据保持未验证；依据不成立则重新设计 |

这些示例限定检查范围，不成为禁止所有副标题、解释文字或符号旁文字的通用正则。

### 开发与校准顺序

1. 从两条真实试水保留错误放行、正确保留和返修版本，区分开发案例与未见测试；不只用合成观察字段验证。
2. 为各标准选择方法，先在现有审查链路验证问题是否能被准确指出，记录漏报、误报及不确定结果。
3. 将已可靠的结构与行为部分接入项目现有 lint/测试；语义与审美部分继续使用实际作品和独立判断，不复制一套自填通过程序。
4. 将已实现的结果读取器接入各项目的实际构建或交付检查：已确认阻断未关闭则不能宣布完成；必需观察缺失则保持未验证。返修后证据绑定实际新版本，未变且仍适用的证据可复用；跨项目通用接入继续验证。
5. 用不同题材的新任务检验触达、最终效果、成本及误拦。根据证据调整方法，达到可用门槛后再考虑通用 CLI 接入。

Otoha 负责已有权限下的任务、引用、通信与结果共享；上述标准和问题属于可选场景约定，不进入 Graph Core 公理。自动采集全部人类反馈、自动生成检查代码和跨项目通用的语义审查器均未实现，也不是本轮计划的前提。

## 跨项目工作页的正常接入

已有本项目 TeamConfig 时复用其中心与工作页，不发布到反馈项目。新项目通过 `otoha team create project-b --from-team project-a` 登记：认证既有 owner 后，在同一中心创建或核对项目与频道，并保存本机团队配置，引用原身份文件。命令不复制身份、不新建中心或仓库，也不接管 receiver；已有同绑定配置保持原样，冲突与未确认写入返回失败。随后通过 `page publish --team project-b` 使用本项目自己的工作页。

此入口已完成代码、独立审查、临时真实服务集成和一次真实项目登记；登记不等于页面已发布或成员已看到。大页面先自包含并按现有消息限制打包，中心接受、成员同步及实际打开仍分别核验。既有 `init` 继续用于新中心引导，不为普通工作页另造中心。

后续真实换版又暴露阅读状态丢失：同一 HTML 被接受为新 revision 后，宿主重建 iframe，主题、展开、滚动和焦点均回到默认。已在原宿主生命周期实现可选 v1 状态桥，提供最终子文档适配器，并把宿主与子页行为回归接入现有测试。两个实际项目已分别完成同话题换版、不同话题隔离与返回原话题的浏览器复验；其中一项由较强模型、高推理的原 verifier 独立查看前后原图、AX 和可见 DOM 状态。该结果限定于已采用桥的同字节页面和所测循环，不证明无桥旧页迁移、任意内容重排、宿主重启或跨机器状态持久化。使用入口见[阅读状态桥](../skills/otoha-visualize/references/view-state.md)。
