# Mac 与 Omarchy：最小闭环实验记录

2026-11-06（Asia/Taipei）。本轮使用独立测试身份、私有测试仓库、虚构消息和隔离运行目录。实验代码与运行结果不定义产品需求；最新通信语义以[通信契约](COMMUNICATION-CONTRACT.zh-CN.md)和[需求演化记录](REQUIREMENTS-STATE.zh-CN.md)为准。

用户在实验中进一步明确：先核对既有讨论，再用可操作实例模拟和打磨流程，之后决定真实实现。因而以下记录分别说明实机观察、源码实验和仍有偏差的部分，不将本轮描述为完整通信系统已交付。

## 实机观察

| 项目 | 结果与范围 |
| --- | --- |
| 原 Gitea | 经用户授权恢复原挂载和服务，验证原实例与既有身份；没有初始化替代库。只创建独立测试仓库和仅获该仓库权限的测试身份 |
| 仓库接入 | Mac 完成身份兑换、私有测试仓库 clone 与 fetch；同一邀请重复接入保留身份和已有 checkout |
| 后台服务 | 独立 Mac launchd 与 Omarchy systemd 用户服务运行；未接管真实 receiver |
| 全队工作页 | Omarchy CLI 发布后，Mac 浏览器读到相同接受版本；后台更新保留选择和反馈草稿 |
| 反馈来源 | 页面从版本 1 更新到版本 2 时，草稿仍指向版本 1；反馈保存后可由 Omarchy CLI 读回 |
| 真实 Agent | Omarchy 的一次临时 Codex 会话实际读取反馈，再发布调整后的工作页；没有开发语音 Agent，也没有验证语音宿主接入 |
| 中心离线 | 只停止实验中心；Mac 保留已接受页面并显示离线，反馈先进入本机持久队列；Omarchy 的页面发布也先排队 |
| 响应丢失与重启 | 实验中心接受一条反馈后故意丢掉响应，暂缓该请求查回；重启 Mac 测试 daemon 后开放查回，原请求自动收敛为已接受，中心只有一条效果 |
| 主题 | 浏览器检查深浅主题、手动选择记忆、原页草稿与版本提示 |
| 凭据 | Mac 五个既有登录/路由文件与 Linux 一个既有登录文件的内容哈希保持不变；新测试凭据不进入公开仓库 |

故障注入仅作用于临时测试进程和指定测试请求；没有修改机器网络配置或对真实服务制造断线。完整原始消息、邀请、个人路径、服务恢复日志和模型运行记录保存在本机私有任务目录；[脱敏结果](evidence/two-host-loop-20261106/summary.json)不包含这些内容。

## 接入指标与首轮盲测

成员的新主入口是 `otoha join --invite FILE`。服务器按同一项目身份提供仓库访问，成员不需要得到 Gitea 管理员凭据；高级直连选项仍保留。消息、工作页和仓库复用该项目上下文，不要求分别配置产品。

| 观察 | 数值/结论 | 解释限制 |
| --- | --- | --- |
| 邀请文件 | 从 1,539 bytes 收敛到 335 bytes | HTTP 经既有 SSH 路由时不携带无用的 HTTPS CA；真正需要 CA 的部署不能据此删掉信任材料 |
| 一次操作者冷项目接入 | 3.039 秒 | 单次小仓库样本；CLI 已安装、机器网络提供者已配置，系统授权条件未固定，不是统计指标 |
| 首次 Luna 会话 | 31 秒执行区间，首次接入失败 | 发现入口后，clone 失败且消息先排队；后台随后恢复，不能改写为首轮通过 |
| Luna 消息 | 稍后自动接受 | 最后一次状态观察早于后台恢复，不证明持续失败，也不证明模型已读 |
| 第二次全新 Luna 会话 | 39 秒执行区间；join 3.028 秒，无命令重试 | 固定已获网络授权的同一可执行文件、预启动隔离 daemon，再使用全新项目身份；不代表首次安装耗时 |
| 第二次 Luna 结果 | 接入、测试 checkout、本机通信回执通过；中央接受 message 8 | 模型另拿内部仓库 URL 做直接 Git 探测失败；之后只读工作区成功，不算远端探测自主通过 |

该次盲测还暴露了旧 `status` 入口的歧义和错误目录的 Git 读回；后者未作为测试仓库可读的证据。

第二次盲测固定系统授权条件后，模型从帮助找到主入口，完成身份接入、仓库检出和测试消息接受。它也暴露一个具体接口问题：join 输出的 `repository.url` 是由 Otoha 路由解释的权威端内部地址，原生 Git 不能直接使用。事后独立诊断使用 checkout 已配置的 `origin`，远端读取成功，但不能把补验算作模型原试验自主通过。后续应把可操作 checkout/origin 与内部 authority 地址明确区分，并在同样前提下重新盲测；不混合两次试验计算首轮成功率。

系统日志进一步确认，Luna 测试 daemon 在新可执行路径触发了 macOS 的本地网络授权，等待人点击 Allow。这是本轮冷启动结果的重要干扰，不应记成模型理解慢或纯网络延迟。后续先固定安装身份和网络授权条件，再测新会话；测试数据隔离不应要求反复复制并授权新的程序身份。本轮没有关闭系统隐私保护。

接入效率后续至少同时报告：从收到邀请到仓库与通信可用的总时长、CLI 调用数、人工动作、重试、首轮成功率。另记录 CLI 自身耗时、模型交互耗时、网络和仓库传输条件。首次安装/系统授权与已安装设备上的新项目接入分别统计，不混用样本。

## 当前代码的边界

- 后端已有完整消息持久化、历史与查询基础；本轮 `message list` 仍默认返回全文，最近 100 条只是派生缓存，尚不等于完整成员消息副本或已完成摘要优先查询。
- 项目/频道权限、消息目标、逐消息私发隔离是不同机制。现有 `to_sessions` 不构成私发 ACL；不能据字段存在就宣称已满足管理员与普通成员的可见范围。
- 旧 receiver 的 `steer`/`queue` 基础不等于已经按紧急程度正确分流。源码盘点发现旧路径仍可能把 queued 消息 steer 给忙会话；应先在需求实例中核对目标行为，暂不将其用作普通消息的真实部署依据。
- 新增自由 HTML 发布和统一 Git/消息入口已有源码与针对测试；自由 HTML 的端到端浏览器验收未因代码存在而完成。任务列表只是样本，不能变成工作页格式限制；Otoha Graph 可作为一种可选模板。
- 当前仓库通道覆盖 smart HTTP，小测试仓库已验证；LFS 未实现。请求与响应分别有 64 MiB、512 MiB 限制，不能推出任意大仓库容量已验证。
- 自由 Graph Core 的数据库接入、完整权限和接受历史仍按图谱计划推进；本轮工作页数据复用消息/事件，不是通用图后端已经迁移。

## 下一步先判断什么

先用[通信需求实例](communication-requirement-instance.html)核对：一条完整正文怎样存储、谁能查询、摘要怎样进入 Session、正文何时读取、普通消息如何等待、紧急消息如何升级，以及中心离线期间哪些事实尚未补齐。规则来源与待确认点应能就地展开。

本轮已在真实浏览器操作该模拟的 queue→摘要→query→明确采用、无关成员不可见、紧急摘要 steer、队长中心离线待发→恢复→主动扫描，并检查深浅主题与选择记忆。[页面截图](evidence/two-host-loop-20261106/communication-requirement-instance.jpg)记录“已读但尚未采用”的中间状态。以上仅验证实例自身的交互；页面角色过滤不证明服务端 ACL，模拟 steer 不证明真实宿主行为，用户尚未验收需求。

实例确认后，再把目标行为变成小型验收样本和实现顺序。优先复用现有持久化与查询、游标和回执基础；不要为通过界面演示而跳过可见范围，也不要把收到消息直接解释为模型已读、接手或任务完成。
