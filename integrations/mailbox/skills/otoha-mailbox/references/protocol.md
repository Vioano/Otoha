# 通信协议与模式

Otoha Mailbox 面向多人使用不同编程 Agent 的协作。协议规定如何在 GitHub 寻址、交流和交接；Skill 是 Agent 的行为指引，收信脚本是辅助实现。协议不依赖某个模型，也不意味着所有客户端已支持相同的自动唤醒能力。

## 当前通信约定

- **身份和地址**：每人使用自己的 GitHub 账号；所有成员向同一个团队项目仓库通信，用 `@LOGIN` 指定收件人。当前脚本从 checkout 的 `origin` 获取仓库。
- **话题和消息**：一个 Issue 表示一个任务或话题，正文和评论构成消息记录。用 GitHub 原有的 Issue 编号、评论 ID 和 URL 定位原件，无需新增私有消息格式。
- **上下文**：简短问题直接写评论，详细约定链接已推送的任务文件。后续消息延续同一个话题。
- **回复**：收件 Agent 阅读原文后，按本人的已有授权决定回复、拟稿、报告或暂不处理。安装 Skill 不授予自动回复权限。只有实质信息才回复，避免相互确认循环。
- **交付**：代码和文档通过 PR 交付，消息中附固定提交、复现方式和未验证项。遵守团队已有的合并规则。
- **事实来源**：GitHub 保存完整消息，本机缓存只用于提示和去重。收到、读过、接手、完成是不同事实，不能混为一谈。

## 接收与回复分别控制

用户可以只要求查收；也可以允许 Agent 拟稿；还可以提前授权 Agent 在指定项目、话题或任务内自主交流。已有授权范围内的技术问答不必逐条确认。

这些是本地用户授予 Agent 的行为权限，当前没有 `reply-mode` 或 `chat` 命令。Python 收信脚本不生成回复；实际回复由运行中的 Agent 通过 `gh issue comment` 或 GitHub 连接器发送。它可以主动发起讨论，也可以决定某条消息无需回复。

## 当前接收能力

| 模式 | 已实现行为 | 限制 |
| --- | --- | --- |
| 完整历史/任务查询 | `check --full` 全部分页扫描，导出索引和完整话题记录 | 当前项目、当前可访问且仍保留的内容；需逐条读完 |
| 快速查询 | `check` 查最近活动，最多 20 条入口 | 不代表所有消息或所有待办 |
| 工作间隙查收 | 可选 Codex Hook，在 SessionStart、UserPromptSubmit、PostToolUse 检查 | 至少间隔 60 秒；无事件则不检查；需本机信任 |
| 持续接收 | 尚未实现 | 需要独立于当前 Agent 回合的接收进程 |
| 空闲唤醒和连续聊天 | 尚未实现 | 需要接收进程与对应 Agent 的会话接口 |

不要承诺“每分钟收到”或“消息到达就唤醒”。60 秒只是请求冷却时间，网络请求与客户端上下文注入还会带来延迟。Codex 异步 Hook 在没有活动回合时等待下一次用户回合，不会自行开始新回合，见 [Codex Hooks](https://learn.chatgpt.com/docs/hooks)。

Agent 离线时消息仍在 GitHub，用户唤起后可以要求补看。完整查收不依赖 Agent 当时在线，也不依赖本机的最近通知缓存。它以 GitHub 当前正文、评论和指派状态为准，不是编辑/删除/指派事件的历史档案；扫描过程中发生变化时可重试。必须分清“抓取完毕”和“Agent 已读完所有记录”。

## 聊天模式需要补上的实现

以下是设计方向，**当前版本未实现**：

1. **持续接收**：独立进程通过定时增量查询或 GitHub Webhook 获取新消息。Webhook 需要可接收 GitHub 请求的地址；它本身不会把消息放进本机 Agent 的对话，见 [GitHub Webhooks](https://docs.github.com/en/webhooks/about-webhooks)。
2. **本地消息队列**：按 GitHub 消息 ID 去重，断线重连补收，明确记录哪些消息已交给 Agent，避免工作间隙检查和聊天接收互相消耗提示。
3. **Agent 会话适配**：在用户选定的项目与会话中投递外部消息；会话忙时排队或使用客户端支持的输入方式，空闲时按用户设置唤醒。各 Agent 需分别接入并验证。
4. **可选主动回复**：用户分别控制只接收、拟稿和自主回复；自主回复限制在已授权范围，提供暂停、停止与防循环机制。

有这些运行组件，才能支持“对方发消息 → 本地自动收到 → Agent 决定回复 → 对方收到”的持续对话。共享 Skill 只提供行为约定，不能单独替代消息投递与会话运行组件。
