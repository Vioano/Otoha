# Otoha 可视化网站

**调用本 Skill，就是要求把当前讨论的东西做成可视化网站。** 接住用户这一轮及相关上下文中的内容，理解具体要求与真正想达到的结果，直接制作并展示网站。不要停在文字回答、设计建议或计划，也不要让用户再补一句“做成网站”。

复用的是这项调用含义、理解方法、网页制作与交付流程。美术风格、信息结构、交互和技术实现由当前内容决定；不规定配色、字体、卡片布局、章节数量或固定页面类型。

## 需求解释与开发计划：先打开

网站用于解释需求、对齐开发计划时，必须在用户提出请求后 **60 秒内** 在宿主内置浏览器打开当前实例。半成品或渲染错误不阻止首次打开；随后沿同一入口边做边看、修复和继续对齐，默认热更新／热渲染。不要把完整调研、视觉打样、团队同步或最终验收放在首次打开之前。这条时限只适用于这类需求对齐网站，不扩展为所有网站的统一时限。

计时、持续预览和最终验收的共同细则复用当前安装的 `frontend-acceptance` 中 `references/requirements-live.md`，从当前环境的 Skill 清单定位，不复制一套流程。Otoha 的具体启动、发布和自动更新方式见[工作页运行方式](references/otoha-page.md#需求对齐网站的首次打开)。

解释需求、demonstration 与开发计划的具体组织和验证，按需读[需求实例与开发计划](references/requirements-plan.md)：让整体目标推导阶段与页面任务，再落实局部，不让图谱登记或完整规划挡住首次展示。

## Otoha 的特色：团队共享工作页

在团队任务中，默认交付同一授权项目内所有队员都能查看的共享工作页。复用 Otoha 已有中心、项目身份、频道权限和传输链路：发布端通过 CLI 提交网页，中心保存接受版本，各成员的后台服务同步内容，再由各自本机浏览器显示。无需让队员访问发布者的电脑，也无需另开网页公网端口。

- 核对各端连接的是同一权威中心、同一项目与可见频道；本机团队别名可以不同。各成员使用自己的 `otoha page open --team TEAM` 取得入口，不互传带认证信息的 `127.0.0.1` URL。
- 一次发布、成员同步取得同一版本，不要求每个队员重新生成网页。确认共享时比较同一中心范围内的 `page.message_id`、`page.request_id` 与实际内容；发布接受、成员同步和成员实际打开分别报告。
- 页面及内联数据可沿当前消息／事件链路共享。已有 HTTPS、中继或配置好的其他传输由 CLI 处理，不为网页重复配置一套网络。大资源或真实计算后端按实际项目选用共享仓库、文件服务或授权数据接口，不能声称当前 `page publish` 已自动分发它们。
- 共享内容版本不等于所有人的滚动、筛选、输入和操作状态联动。需要共同操作同一个对象时，明确共享状态与写入接口，并按该任务实现、验证；不为普通共同查看引入协同编辑系统。
- 全队共享限于项目既有授权范围。只发布本次任务的成果及必要数据，不把私人聊天、凭据或本地绝对路径一并打包。独立个人展示可按用户意图保留在本机。

运行命令、成员查看方式、断线行为与当前资源限制见 [Otoha 工作页运行方式](references/otoha-page.md)。需求／计划类页面持续热更时，按[阅读状态桥](references/view-state.md)适配并实测同话题的视图、主题、展开、滚动和焦点承接；不把本机存储可用推定为 opaque 宿主也可用。

## 从当前意图开始

- 以当前请求和最近的修正为准。把真实目标、用户提出的一种做法、硬性约束区分开；合理推断目标，但不要把推断写成用户原话或已确认决定。
- 用户指定聊天、文件或数据时，读取与当前问题相关的原件。引用的 Codex 聊天用宿主 `read_thread` 及必要分页读取；标题和摘要只帮助定位，不替代消息。仅在需要时扩大读取范围，不默认扫描全部私人历史。
- 找出用户最需要看清、体验或判断的东西：期望结果、运行机制、关键关系、方案差异、数据中的变化，或一个具体操作产生的后果。让它成为网站的主体。
- 有足够信息就先完成有用的版本。只有缺失信息会实质改变方向时才问；可继续的部分照常推进。没有真实数据时呈现分析目标与方法，或明确标注的虚构演示，不编造分析发现。

## 让内容决定表达

下表是选材提示，不是必须出现的页面、模块或栏目。

| 用户要看清什么 | 可采用的表达 |
| --- | --- |
| 产品或功能最终怎样用 | 直接进入关键场景的可操作原型、用户路径、状态与反馈 |
| 多条编码要求之间怎样配合 | 行为示例、约束关系、输入输出与修改前后对照 |
| 一套方案为什么有效 | 具体例子、关系图、分步运行、因果与取舍对比 |
| 数据分析要回答什么 | 问题与指标的关系、数据到结论的路径；有数据时计算并展示可核对的图表 |
| 参数或选择怎样改变结果 | 有真实关系支撑的控件、情景比较、联动视图 |
| 长讨论里哪些要求仍然有效 | 按主题组织当前要求、修正与未决问题，原话及来源按需展开 |

组合适合当前对象的形式，也可以另选更好的表达。不要把所有任务都做成需求清单、流程图、卡片看板或提示词档案。不要为了“可交互”添加无意义的按钮、滑块和动画。来源用于核对，不能淹没主体；页面不必展示每条原话。

## 复用实现，保持风格自由

1. **先找已有网站。** 同一话题后续调整优先更新原目录和入口，复用当前项目的组件、数据逻辑与视觉语言，尽量保留阅读位置、选择和展开状态。
2. **按需借用其他 Skill。** 从当前环境的 Skill 清单定位并读取所需文件，选能解决当前问题的少数几项，不整套加载。可参考：
   - `web-design-engineer`、`design-taste-frontend` 或 `impeccable`：网页构图、视觉设计与前端实现。
   - `interaction-patterns-components`：交互模式、导航、上下文保留与可访问性。
   - `archify`、`system-atlas` 或 `visual-diagram-qa`：确实需要的关系图、架构探索与图示检查。
   - 数据分析、科学绘图等对应 Skill：有真实数据或领域计算时用于分析与验证。
   - `imagegen`：需要视觉探索、插画或重要界面打样时使用；已有页面的小改动不机械重做。
   这些是可选协作能力，不是安装依赖。缺少某项时用现有能力完成。遵循用户当前约定，不因引用其他 Skill 就增加例行设计审批、固定风格、多方案数量或必填表单。
3. **没有现成工程且适合轻量页面时，可用随附起点：**

   ```sh
   python3 <skill-dir>/scripts/start_page.py --output <page-directory> --title "当前主题"
   ```

   将 `<skill-dir>` 换成本 Skill 所在目录。脚本复制 [starter.html](assets/starter.html) 为 `index.html`，拒绝覆盖已有文件。它只省去基础 HTML、主题切换和响应式的重复搭建。示例内容、布局和视觉均可替换，不能原样充当交付。也可以完全不用它。
4. **默认使用后台共享工作页。** 使用 Otoha CLI 启动或复用常驻工作页服务，通过 CLI 发布新版本，验证成员同步及已经打开的网页自动更新。先读 [Otoha 工作页运行方式](references/otoha-page.md)，按实际版本能力执行。简单内容可以用静态 HTML；团队任务仍要使它经共享链路到达成员，不能只交付自己机器上的文件。独立个人、非常简单的一次性展示可直接交付静态页。页面需要独立资源或计算后端时采用适合的项目服务，不把当前工作页不支持的能力写成已实现。

## 网页设计的共同要求

这些要求约束理解与体验，不指定美术风格。已有项目的视觉语言和用户本轮选择优先。

- **让布局承担说明。** 用位置、分组、层级、控件和状态表达用法。删除重复标题、空泛口号、复述按钮与布局的文案，以及没有帮助识别、判断或恢复的次级标签。保留表单标签、单位、错误原因、操作后果与无障碍名称；关键内容不只放在悬浮提示中。
- **信息关系要落实为布局。** 步骤、对比、因果和状态差异不能全压成一段概括；用位置、连接、对齐和可操作状态承载它们。删除辅助句不等于这些信息已被表达。实际布局看不懂就退回重做，不增加说明段落替它辩护，打样和真实成品均如此。
- **重要视觉方向先打样。** 新界面或重要视觉改版主动使用生成模型探索布局、层次、材质和主题适配，优先展示深色；结合任务与已有风格筛选后落实为真实网页。已有起点的小改动可直接做。生成稿帮助选择方向，不代替可操作界面。
- **提示词和样图都要审。** 生图前核对本次适用的用户约束、分层目标和候选要比较的实质差异；不要把全量规则机械塞入提示词。出图后检查同一组约束，明确采用、修改与舍弃哪些安排。多打样用于比较不同构图或表达，不用换色凑数；违反约定的样图不能因“忠实还原”进入成品。
- **边做边打样，提示词随任务更新。** 打样不限于开头；中途缺少优化方向时，把当前真实画面和具体卡点交给生成模型探索，审查后落实，再回看实际效果。每轮按当前版本、上层目标、本轮问题和最新反馈重新组织提示词，保留仍适用约束、更新已改变要求，不套用过期首轮提示词。局部问题局部探索，方向清楚的小修直接做，不机械增加轮次。
- **让交互服务于理解。** 根据用户任务、使用频率、信息层级和输入设备选择交互。原位展开、方案预览、下钻、分栏、直接操纵或快捷键均按需使用；区分选中、查看详情、展开和进入，处理手势冲突，提供键盘与触控入口，返回时尽量保留上下文。
- **让变化有意义。** 状态、进度、动画和视觉强调对应实际含义；能用图形或操作说明的关系不要只堆文字，能直接说明的简单内容也不强行做复杂画布。
- **验证真实体验。** 在网页上走通主要操作，检查深浅主题、响应式、文字和图示可读性、键盘焦点。解释会影响使用的重要交互取舍即可，不交付一堆实现术语和设计过程文案。

## 交付前默认独立验收

普通前端也默认独立验收。制作侧先自查，再由另一位未参与制作、采用较强模型和高推理设置的 Agent 亲自查看实际成品、操作关键状态并记录中性事实。首审给原始请求、适用标准、必要来源和实际产物，不给作者自评分或“已经通过”的结论。

复用宿主当前的 `frontend-acceptance` 轻量 CLI，按其实际能力关联双方观察、声明范围和产物修订，合并计算卡点；不在本 Skill 另造 CLI、参数或认证机制。缺少独立观察、存在卡点或观察仍指向旧版时，不能宣布完成。原作者修改实际成品后，仍由原 verifier 对当前版本复验；作者不能代填或改写独立记录。独立事实与程序放行仍不等于用户接受，也不证明事实判断永远正确。

普通独立检查复用正常子代理或会话能力，不启动后台审查服务，也不自动启用完整美术选型管线。正式高美术交付或项目明确要求时，再按相应视觉审查流程执行。宿主 CLI 的具体能力及真实任务效果须实际验证，不能以本段流程更新当作已经接入或通过。

## 做完并展示

- 用布局、图形与实际反馈表达关系，保留必要的标签、单位、错误原因和操作后果。删除复述界面的辅助文案。
- 遵循所在项目的主题约定；没有约定时提供深浅主题，默认深色并记住手动选择。风格仍按题材与用途设计。
- 在可用浏览器中实际打开，优先用户指定的浏览器；检查关键操作、键盘与焦点、目标屏幕尺寸及深浅主题可读性。检查范围随页面内容确定。无法完成浏览器验证时说明缺口，不能声称已检查。
- 对模拟交互、虚构数据、假设、计算结果和真实运行状态，在会影响理解的位置明确区分。原型点击不证明正式功能已实现。
- 交付可访问入口和源文件位置，保持入口可用，并留下继续启动或预览的方式。用户要本地网站时在本地运行；没有公开发布授权，不自行上传或公开聊天与数据。

默认运行依托 Otoha CLI 的后台共享工作页，个人静态例外可独立使用；两者都不要求连接 Graph 或登记固定业务对象。在已有 Otoha 项目中按当前约定关联来源和反馈即可；页面展示、用户反馈、接受决定与实际执行分别判断。

## 典型调用

- “`$otoha-visualize` 我想让团队成员只拿一个文件就能加入项目，后续断网还能恢复。” → 制作能看清接入与恢复体验的网站。
- “`$otoha-visualize` 我想分析不同渠道的留存差异，弄清是不是用户构成造成的。” → 根据数据条件呈现分析路径或真实分析与可探索图表。
- “`$otoha-visualize` 就按刚才那几个要求。” → 使用当前上下文制作网站，不要求用户重说要求或重复指定网页载体。
