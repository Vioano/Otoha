# 需求实例与开发计划

用于解释需求、展示 demonstration、对齐方案或开发计划。沿用已有页面、工作目录和团队上下文；先按主 Skill 的快速展示要求打开，再在同一入口迭代。不要等完整计划、图谱登记或所有评审完成才让人看到。

## 先让一个真实问题可判断

从当前请求中找出最值得判断的问题。区分人的目标、暂用方案、硬约束与尚不确定的前提。用一个具体体验呈现它：同一操作的前后状态、两个方案的实质差异、一次失败如何恢复，或一段关系如何逐步形成。无需把所有要求都做成表格；技术已经存在也不等于它符合人的意图。

计划应说明下一步为什么值得做、依赖什么、会改变哪个体验，以及怎样从实际结果判断。开发阶段和顺序由问题决定，不强制套固定栏目。需求变化时更新受影响的体验、计划与验证，保留改变方向的原因。

视觉探索也沿这个循环进行。制作中需要新方向时，以当前真实画面和具体问题发起下一轮打样；提示词根据当前版本、上层目标与最新反馈更新，不固定沿用第一轮。每轮都审提示词和结果，采用后回到真实实现验证，不把错误样图当标准。

## 展示推导，不只展示结论

复杂作品按实际需要展开层级：整体目标与体验 → 阶段或段落安排 → 页面或场景任务 → 局部元素与行为。让人能从一个局部决定回到它服务的上层目标，也能查看整体规划怎样影响局部。

例如，计划讲清一项异步通信机制：先明确观众应区分哪些状态，再决定先演示离线还是先看回执，接着决定每个场景暴露哪些对象，最后决定哪些变化值得动画强调。不要从“需要一张状态卡片”反推人的目标，也不为没有信息变化的地方强加动画。

## 检查实际采用，而不靠自报

对布局与文案，保留帮助识别、判断和恢复的正文、标签、单位与后果。检查涉及的页面模板、章节和主要状态，特别是标题下的 intro、图下注和卡片副文。不能只删首屏一句，或用“不溢出”代替判断。

“这句话有事实”或“是在讲主题”不是标题下概括的保留理由。暂时移除它，查看主要内容、状态和证据是否已经完整表达所需信息；如果没有损失，就删掉该固定模板。独特事实保留在它实际帮助判断的位置，不为每个标题自动补一段问题总结。

关系信息需要积极设计，而不只是删文案。例如“读过规则、运行过检查，成品仍有问题”，可以把过程记录与实际结果分列，分别显示真实状态，并让断开的证据关系可见。它表达的是检查与结果的关系，不用另一段话再解释界面。读不懂关系就重做布局；不能把读者困惑归因于缺一段辅助说明。

关系符号已经表达的含义，不再加同义小字。例如两组结果之间已有 `≠`，不再显示“不能据此放行”；辅助技术需要的名称可以保留。只有符号没有表达的必要条件才补充，不以“保险起见”重复解释。

寻找布局方向时，先复用宿主 `frontend-acceptance` 的 `references/comparison-gallery.md` 索引：教学画布、产品叙事、数据表格、密集编辑器和移动预订各自展示不同关系。再按当前任务推导，不照搬皮肤或固定页型。本系列另有[裁切、图文边界与并列选择的可操作对照](../../otoha-content-review/assets/review-cases.html)；它们是限定条件下的样本，不是所有题材的通用模板。

交付前，制作侧先自查；另一位未参与制作、采用较强模型和高推理设置的 Agent 再亲自查看涉及的页面、章节和关键状态，记录具体文案、对象关系、操作前后结果等中性事实。普通前端也走这条独立验收链，不把它限于严格美术项目。独立首审不接收作者的自评分或通过结论，不能用作者口述、源码或旧截图代替实际观察。

双方复用宿主 `frontend-acceptance` 的同一轻量 CLI，按当前入口关联观察范围和实际产物修订，由公开规则合并计算卡点。不要在本 Skill 复制判定引擎或预设尚未提供的参数。缺项、卡点和旧版证据都不能算当前版本通过；原作者返修后，由原 verifier 接着实看当前版本并复验，保留旧记录，不由作者代填独立事实。

程序能检查已编码的条件及其支持的版本关联，不能证明观察真实或审美成立。宿主未提供合并入口时，双方仍实际检查、保留观察和版本，并明确缺少程序合并验证，不伪造运行记录。普通独立验收不需要后台审查服务或完整美术选型；这些额外流程按项目的实际要求启用。

三项证据分别保留：

- **快速触达**：普通任务能否找到并实际采用本次适用的规则与工具。
- **最终交付**：一次请求到最终结果是否符合要求；内部修复不限，不用“第一次生成”替代最终成品标准。
- **需求页展示**：请求后 60 秒内实际打开，随后内容变化在原入口自动呈现。首次超时保持失败，后来打开不改写计时。

若需要内容作品的整体导演与逐元素推导审查，按需读取 [otoha-content-review](../../otoha-content-review/SKILL.md)。HTML 是查看与判断的工作界面；要求 PPT、PDF 或可播放作品时，还要检查对应真实成品。

## 与 Otoha 协作

沿现有授权项目传递摘要与产物引用。共同页面、需求反馈、执行结果、用户接受分开记录。已接入 Graph 时可关联当前要求、实例、决定和证据；这些是可选场景词汇，不改 Core，也不成为首次展示的前置条件。未接入时保留清楚的来源关系，不声称已完成图谱或团队同步。
