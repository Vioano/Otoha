# 用 Otoha 后台工作页交付网站

使用此路径前核对当前 CLI 的 `otoha page help`。以下是本仓库已有能力：工作页 HTTP 服务与 receiver 同进程、共用后台生命周期；CLI 发布内容，经中心接受后，已打开的网页自动取得新版本。CLI 是控制入口，receiver 是常驻进程。

## 团队怎样共同查看

当前复用的是完整网页内容的分发，不是把发布者的浏览器画面转发出去：

```text
发布端 CLI → 团队中心（保存网页接受版本）
                         ├→ 成员 A 后台服务 → A 的本地工作页
                         ├→ 成员 B 后台服务 → B 的本地工作页
                         └→ 其他有频道权限的成员 → 各自本地工作页
```

网页被保存为 `otoha-page/1` 消息，接收端通过同一中心的事件流还原为本机工作页。沿用该团队已经配置的中心地址、身份与网络传输，包括可用的 HTTPS／中继或已有路由。此功能不需要另建网站分发服务，也不要求将网页服务暴露到公网。

发布端发布一次，各成员在自己机器上执行：

```sh
otoha page open --team LOCAL_TEAM_NAME
```

`LOCAL_TEAM_NAME` 是每端的本机别名，可以不同；它们必须指向同一中心、项目与授权频道。每端得到自己的本地入口与认证信息，不能把某一端的 `127.0.0.1` URL 当成队员共享链接。队员需要已接入 Otoha 并运行后台服务；目前没有“未安装 CLI，仅凭一个中心网页链接浏览”的交付入口。

可读范围沿用项目与频道授权，不自动扩大到别的团队。`reader` 可读取，但不能发布或提交当前通过写消息实现的反馈；有写权限的成员可按频道权限操作。当前没有额外独立的工作页 ACL。发布前确认内容适合该频道的全部授权成员。

验收共同查看时，在发布端和接收端分别运行 `otoha page status`，比较同一中心内的 `page.message_id`、`page.request_id` 与网页内容。仅本机 `publish` 返回 `accepted` 不证明成员已经同步或看过；声称“全员已看到”需要相应成员端的实际结果。

成员离线后，上次已同步的网页仍可由其本机后台服务呈现；后台恢复连接时按持久游标补齐事件。中心不可用时，新发布和可写成员的反馈先在本机排队，等待恢复，不能报告全队已经更新。更换中心或自动切换备用链路不由这个 Skill 自行实现。

共享的是网页及其中实际分发的数据版本：内联的分析结果会跟着页面同步；发布者电脑上的 CSV、图片或计算进程不会自动转移。各人的视角、筛选、输入和脚本运行状态仍各自独立。真实共享数据的修改必须走授权的共同数据接口，不能靠各浏览器的本地变量模拟。

## 默认流程

### 需求对齐网站的首次打开

解释需求、对齐开发计划的网站遵循 [Skill 的 60 秒要求](../SKILL.md#需求解释与开发计划先打开)：先复用同一话题的入口；没有入口时，只做取得当前实例所需的最少准备，立即在内置浏览器打开，随后边做边看。半成品和渲染错误在已打开的页面上继续修复，不等待视觉打样、团队同步或最终验收。如果既有 Otoha 接入暂时受阻，先用项目已有本机预览显示当前内容，继续解决接入；本机打开与团队同步分别报告。

后续修改默认沿同一入口自动渲染。使用下述共享工作页时，每次内容修改后由 Agent 发布下一版本，观察已打开页面自动更新；现有实现不会自动发布磁盘文件的修改。使用项目已有开发服务时，复用其热更新能力。不要为首次预览重建接入、另建同步服务或覆盖其他话题的 current page。

### 沿现有入口继续

1. 识别当前任务所属的已接入团队，检查当前工作页是否属于同一话题。每个团队只有一个 current page，不能为了展示新话题覆盖不相干工作。团队不明、缺少 CLI 或工作页不适合当前网站时，检查项目已有运行方式；不要擅自加入真实团队或假称 Otoha 服务已就绪。需要另建服务时，保留 CLI 接入为明确的未接入项。

   已授权复用既有 owner 与中心、但本项目还没有团队配置时，先核对 `otoha team help`，使用 `otoha team create PROJECT_TEAM --from-team EXISTING_TEAM` 登记本项目。命令沿用原身份引用、补建并回读本项目及频道，不新建中心、身份或仓库。不要手工克隆其他团队配置，也不要借用其 current page。登记后继续下列发布与查看核验，不能把登记成功当成页面已共享。

2. 启动或复用服务，取得 URL：

   ```sh
   otoha page open --team TEAM
   ```

   它可能安装或启动该 Otoha Home 的后台 receiver，不是纯只读查询；不要为了验收操作已有真实 Home。测试使用独立 `OTOHA_HOME` 与测试身份。正常交付在当前授权项目范围内复用已有服务。

3. 将返回的本地 URL 交给用户指定的浏览器，默认优先宿主内置浏览器。不要自动加 `--browser`，该参数会打开系统默认浏览器。URL 含本地认证信息，不写进公开仓库或发布文档。
4. 把网页写成自包含 UTF-8 HTML，发布：

   ```sh
   otoha page publish --team TEAM --file PAGE.html --request-id REVISION_ID
   otoha page operation --team TEAM --request-id REVISION_ID
   otoha page status --team TEAM
   ```

   每个内容版本用一个新 `REVISION_ID`；同一发布结果未知时先查询，并沿用原 ID。`queued` 只表示本机排队，`accepted` 表示中心已接受；在 status 中核对 `page.request_id` 与内容后，再观察已打开的网页是否变化。不能把任一步替代后续验证。
5. 用户要求修改时，继续沿用网站目录和工作页入口，修改后发布下一版本，无需让用户手动刷新。在其他授权成员端检查版本同步；反馈读取按任务需要使用 `otoha page feedback --team TEAM`。

## 已有热更新的实际含义

浏览器当前采用轮询：可见页面约每 1.5 秒请求一次状态，后台标签页约每 8 秒一次；总延迟还包含中心接受与本机同步。新版本会替换 HTML iframe。这是自动内容更新，不是保留任意应用状态的前端 HMR，也不是文件修改后自动发布。

iframe 使用 `sandbox="allow-scripts allow-forms"`：可以运行页面脚本，不能依赖父页 DOM、同源存储或直接读取宿主认证。`localStorage` / `sessionStorage` 可能不可用。需求／计划类页面持续更新时，采用宿主支持的[阅读状态桥 v1](view-state.md)：通过现有 JSON 发布入口声明同话题 `view_state`，在最终子文档内联[适配器](../assets/view-state.js)，为展开项和焦点目标提供稳定 ID；多视图页面显式适配固定视图 ID。先在实际宿主完成同话题换版及不同话题隔离复验，再报告状态承接。

状态桥仅在当前宿主页内存中按 team＋topic 保存主题、展开、滚动、可恢复焦点和固定视图，不包含表单草稿、成员同步或嵌套页面的任意状态。宿主或子页未采用时仍会重建默认视图；不能把静态预览的存储结果当作 opaque 工作页已保留状态，也不能用降低要求代替适配。

HTML 的相对 CSS、脚本、图片和数据文件不会随 `publish` 一起托管。优先内联必要内容；当前文档 JSON 上限 48,000 bytes，编码后的消息请求上限 65,536 bytes。复杂资源或真实计算需要独立服务，不能删掉关键内容以硬塞上限，也不能绕过限制后声称完整发布。

## 静态例外

静态内容也可以通过上述共享工作页分发。仅个人展示或当前不要求团队共享时，几段解释、一张静态图或不需要持续修改的简单展示可以直接使用 HTML 文件；需要 HTTP 预览时仅在明确的网页目录绑定本机地址：

```sh
python3 -m http.server 8000 --bind 127.0.0.1 --directory PAGE_DIRECTORY
```

这种预览不是 Otoha 常驻服务，也不会自动更新浏览器，交付时按实际方式描述。
