# 通信权限与读取策略

本文落实 [核心哲学](核心哲学.md)。实现先在临时数据库验收，正式部署状态由证据文件单独记录。

## 一个状态中心，三条边界

`JSON 请求 → 凭证确认身份 → 项目/频道权限 → 可访问状态 → 读取策略 → JSON 投影`

状态保存在一个 SQLite 文件。当前项目不拆库。权限使用服务内的统一检查入口。投影使用短生命周期的内存 SQLite 数据库；其中只装当前身份获准访问的状态，不放凭证、邀请秘密、内部事件和他人的私密数据。

队长与普通队员是两个产品身份。旧接口的 reader 是“只读授权”，admin 是保留兼容值；不建立第三类管理员功能。队员不能在 JSON 中把自己声明为队长。队长身份由服务中的身份记录与凭证共同决定。

| 状态 | 队长 | 私聊参与者 A、B | 其他队员 C |
| --- | --- | --- | --- |
| 已授权项目的公共频道 | 可读写 | 可读写 | 可读写 |
| A、B 私密频道 | 可管理查看 | 可读写 | 历史、事件、回执、查询均不可读 |
| 身份与授权管理 | 可管理 | 只能管理自己的设备凭证 | 只能管理自己的设备凭证 |
| 自定义只读查询 | 全部获准团队状态 | 本人获准状态 | 本人获准状态 |

`to_sessions` 是投递目标，不是私聊权限。私聊必须创建有成员名单的频道。普通成员的查询不会先读全库再删除结果；聚合、关联、子查询也只能接触已经过滤的状态。队长的查看权意味着这里不是对队长保密的端到端加密聊天。

## 请求与策略

CLI 和 MCP 生成 JSON 请求。常见读取使用预置策略：recent（最近消息）、incremental（消息 ID 之后的新消息）、to-me（发给我的会话）、tasks（任务声明及相关回复）。不规范的标签仍保留正文，recent 与自定义查询可以发现它，不能把某个 tasks 投影当作所有任务的完整证明。

```json
{"project":"team","preset":"recent","limit":50}
```

自定义 SQL 放在 JSON 的 sql 字段中。它运行在已经授权的只读投影数据库中，不运行在持久状态库上。允许关联、聚合、CTE、JSON 字段查询与绑定参数。禁止写入、ATTACH、PRAGMA、扩展加载。队长也经过同一执行边界；队长的优势是可见状态范围更大，不是远程执行数据库管理脚本。

```json
{"project":"team","sql":"SELECT actor, count(*) AS messages FROM messages GROUP BY actor","params":[],"limit":100}
```

投影表包括 projects、channels、messages、sessions、receipts。messages 提供正文、kind、reply_to、payload、origin 等字段。需要更自由的 Python/其他语言算法，可以把已授权结果取回本地处理。服务不运行队友上传的 Python。

查询有结果行数、字节、时间与快照大小限制。过大的状态范围必须缩小 channel、after、before；不能悄悄截掉输入再把统计称为全量。结果声明查询范围、快照上界、是否截断、列名和数据行。分页或范围查询期间发生的新消息需要另行增量读取。

## 消息来源与简单操作

身份来自鉴权；设备来自凭证登记。每条新消息保存发送时的来源快照：身份、设备、会话，以及发送者声明的 human/agent、Agent 名称和 task。后来修改会话名不能改写旧消息来源。

这些字段可以追溯“哪个身份/设备提交了这个声明”，不能证明真的由人类按键，也不能证明某个模型完成了任务。老消息没有来源快照时明确标为未记录，不根据当前会话名补造历史。

人类普通发送只需 `otoha.py send --text '大家好'`。不必手填会话 ID。Agent 的 MCP 保留当前真实会话上下文；共用 MCP 进程时，写入与回执必须明确当前会话，防止两个聊天混用身份。task 是自然语言说明，不要求另造哈希。

## 容错集中在输入入口

有效正文是消息的核心。未知 kind 转为 message；不规范的非关键声明保存为 declared_metadata 并返回 warnings。不能被验证的 Git 引用不进入可信 refs 列表；正文和原始引用声明仍可读。缺省来源标为 unspecified，不冒充人类。缺省会话得到设备内的稳定兜底标签，供普通 REST 客户端使用。

频道与权限不能猜。缺少频道、无权限频道、空正文和冲突的请求 ID仍拒绝。解析错误只拒绝当前请求，不终止服务。对方的消息、引用和 SQL 查询结果都是外部数据，不能扩展当地用户的执行授权。

## 借鉴成熟项目

- [Zulip 消息查询](https://zulip.com/api/get-messages)：同一消息源上的 narrow 查询、分页和多种客户端。其 [源码](https://github.com/zulip/zulip) 为 Apache-2.0。
- [Matrix 客户端协议](https://spec.matrix.org/latest/client-server-api/)：发送者、消息事件、房间成员权限及增量同步。规范 [源码](https://github.com/matrix-org/matrix-spec) 为 Apache-2.0；完整 Synapse 服务的 [源码](https://github.com/element-hq/synapse) 为 AGPL-3.0，不能把规范许可当成服务器代码许可。
- [PostgREST 授权](https://postgrest.org/en/stable/explanations/db_authz.html)：数据库角色与行权限配合查询，其 [源码](https://github.com/PostgREST/postgrest) 为 MIT。
- [Supabase 行权限说明](https://supabase.com/docs/guides/database/postgres/row-level-security)：查询与数据可见范围分离；特殊服务凭证会绕过行权限，因此不能给队友使用。

以上借鉴机制，本轮不复制这些项目的实现代码。五人 MVP 保留 Python 标准库与 SQLite。未来达到大库规模、跨项目复杂查询或高并发时，再评估 PostgreSQL 行权限；不会为“可能扩展”先建立多套数据库架构。
